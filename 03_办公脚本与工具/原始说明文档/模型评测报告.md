- **被测模型**：`xinghai-ultra`（主），`deepseek-v4-flash`（对照组，同网关）
- **裁判模型**：`qwen3-5-397b`（与被测模型不同源，降低自评偏差）

- **原始数据**：`eval_results.json`　**复现脚本**：`evaluate_models.py`

## 2. 分项发现

### 2.1 强项（满分项）

- **工具调用 4/4 全对**，且覆盖了四种不同能力：
  - 正确触发工具（问天气 → 调 `get_weather`，参数含「北京」）
  - 在多个工具中选对（温度换算 → 选 `calculator` 而非 `search_web`）
  - **该不调就不调**（「1+1 直接回答，不要调用工具」→ 返回 `tool_calls=[]`，没有过度调用）
  - 多参数 schema 保真：订机票用例正确产出
    `{from_city:青岛, to_city:上海, date:2026-03-05, passengers:2}`，日期格式与类型都对，`arguments` 是合法 JSON
- **中文能力 3/3 满分**：成语释义与出处（《庄子·秋水》）、文言文翻译（「学而不思则罔，思而不学则殆」两个分句都到位）、
  长文摘要（准确抓住「工具不产生价值／要看是否嵌入工作流」这一核心观点）
- **长上下文 2/2**：在约 3–4k token 的无关文本中定位埋点（数字 `7391`、代号「紫罗兰」），
  且埋点位于文本**中部**时同样命中，未出现「只记住开头结尾」的典型失效
- **代码 4/4**：回文函数、保序去重、SQL 聚合查询均通过；bug 排查题明确指出空列表触发 `ZeroDivisionError` 并给出修正
- **稳定性 5/5**：同一格式题重复 5 次，每次都是合法 JSON，无格式漂移

### 2.2 唯一失分项：硬性字数约束

用例 `if-char-limit`：要求「用**不超过 20 个汉字**说明什么是光合作用，不要输出推理过程」。

```
实际输出：植物利用光能将二氧化碳和水转化为有机物并释放氧气。
实测字数：25 个汉字（超出上限 20）   复测 3/3 次均超限
```

对照组的 `deepseek-v4-flash` 该项通过。说明这不是判分口径问题：
**模型能给出正确内容，但无法遵守「不超过 N 字」这类硬性长度约束**（3 次复现，输出完全一致）。

> 这是很典型的「内容正确、约束失效」失败模式。生产提示词里如果依赖「不超过 N 字」来控制长度，
> 在这个模型上会有稳定偏差。

### 2.3 与对照组的差异

- 对照组在**硬性字数约束**上更稳（100% vs 75%）
- 对照组在**代码完整性**（bug 修复题只给片段，未给出完整修正代码）与**文言文用词精度**
  （把「殆」译成「疲倦」）上失分，主模型在这两项更好

## 3. 评测本身的局限（必须说明）

1. **未测「思考」能力**：当前代理返回的 `usage` 只含 `completion_tokens`，
   没有 `reasoning_tokens` 明细，`reasoning_effort` 参数也未透传。因此本报告评估的是
   **默认（非显式推理）模式**，不代表开启深度思考后的水平。
2. **规模有限**：25 例为快速体检，不等于权威基准。若要与公开榜单（MMLU / HumanEval / GSM8K 等）对齐，
   需要按标准协议在本地重跑。
3. **长上下文只测到约 4k token**：埋点定位通过，但未验证 100k+ 级长文；也**未测多轮对话与指令保持**。
4. **未测安全性与拒答边界**（越狱、有害内容、幻觉率）。
5. **裁判为同网关模型**：虽与被测模型不同源，仍不排除同族偏好；rubric 题的分值应视为参考。
   确定性检查的 19 例不受此影响。
6. **对照组有 1 例因裁判截断缺失**，故 96.0% 与 96.2% 的差距**不具统计意义**。

## 4. 一个需要留意的事实：模型自称 GLM

对 `xinghai-ultra` 反复询问身份（中英文、不同问法、`temperature=0`），回答高度一致：

```
Q: 你是什么模型？请只回答模型名称和开发方。
A: 我是GLM，由Z.ai开发。

Q: What is your model family and who trained you? Be honest and specific.
A: I am GLM (General Language Model), a large language model developed and trained by Z.ai.

Q: 你的训练方是谁？是海信、智谱、DeepSeek 还是别家？
A: 我是由Z.ai训练的大语言模型，与海信、智谱或DeepSeek没有直接关联。
```

三种问法、中英双语、确定性解码下结论一致，**不像随机幻觉**。
这通常意味着两种情况之一：

- `xinghai-ultra` 是以 GLM 为底座做的微调/接入，**未做身份对齐**（最常见）；
- 或网关上 `xinghai-ultra` 这个名字实际路由到了 GLM。

**建议**：向模型/网关提供方确认底座与身份对齐策略。若该模型要对外使用，
身份自称错误会在演示和审核环节成为明显问题；如果只是内部工具使用，影响有限。

（本次未能直接探测上游 `/v1/models` 做交叉验证：直连内网网关时系统代理干扰导致
`SSL: UNEXPECTED_EOF_WHILE_READING`，代理进程因使用 `trust_env=False` 才不受影响。）

## 5. 选型建议

| 场景 | 建议 |
|------|------|
| 中文对话、中文写作、成语/文言文 | ✅ 表现好，可用 |
| Agent / 工具调用（DSH、Claude Code 这类） | ✅ 强项，工具选择与参数 schema 都可靠 |
| 长文档问答、信息定位 | ✅ 通过（测到约 4k token） |
| 代码生成与修 bug | ✅ 通过本集用例 |
| **依赖「不超过 N 字」等硬性长度/格式约束** | ⚠️ 有稳定偏差，建议改为**结构化输出**（JSON schema / 工具调用）来约束，而不是用自然语言限长 |
| 对外演示、需要正确自报身份 | ⚠️ 先与提供方确认底座与身份对齐 |

**一句话**：作为中文 Agent 场景的模型，`xinghai-ultra` 在本评测集上与 `deepseek-v4-flash` 持平且
工具调用与中文能力更稳；主要短板是硬性长度约束。建议后续补齐「多轮对话」「大规模长上下文」
「开启推理模式」三类评测。

## 6. 复现方式

```powershell
cd "$env:USERPROFILE\Desktop\setting"

# 确认代理在跑（DSH/Claude Code 都依赖它）
try { Invoke-RestMethod http://127.0.0.1:8082/health } catch { "代理没在跑" }

# 全量评测（约 10-20 分钟，50 次模型调用 + 5 次稳定性采样）
python evaluate_models.py --workers 3

# 只跑某一类
python evaluate_models.py --category 工具调用
python evaluate_models.py --category 数学 --models xinghai-ultra
```

结果写入 `eval_results.json`，含每题的实际回答、判分依据与 token 用量，便于逐题复核。
