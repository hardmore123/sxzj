一、整体分层（这是骨架的核心）
这个项目本质是一个 "不可信 LLM 驱动的批处理审查系统" 的通用模板，可抽象成 6 层，从内到外：

┌─────────────────────────────────────────────────────┐
│ 6. 前端 (Vite+React)  —— 一体化，被后端 serve         │
├─────────────────────────────────────────────────────┤
│ 5. Web 服务层 (FastAPI, 可选依赖)                     │
│    任务注册表 + 后台执行器 + JWT + 统一错误信封 + 备份 │
├─────────────────────────────────────────────────────┤
│ 4. 知识/规则层  正向规则 + 反向规则 + 多维筛选 + 学习闭环│
├─────────────────────────────────────────────────────┤
│ 3. 流水线层 (核心)  预处理→多路并行→合并→仲裁→输出     │
├─────────────────────────────────────────────────────┤
│ 2. 模型接入层  provider 构建 + 自定义 transport       │
├─────────────────────────────────────────────────────┤
│ 1. 配置层 (Pydantic Config + .env)                    │
└─────────────────────────────────────────────────────┘
最关键的架构约束（决定可复用性）：依赖严格单向。

核心包（1-4 层）零依赖 Web 层，能独立跑 CLI。
Web 层（5 层）只 import 核心，核心绝不 import Web。
Web 对核心的唯一侵入是一个可选回调参数 on_event（进度上报），向后兼容。
这个约束让你能：先在 CLI 里把算法/流水线打磨稳，再套 Web 壳；也能把核心包整个打包移植。你的新项目一定要守住这条，否则会退化成前后端纠缠的泥球。

二、逐层设计细节 + 可复用点
第 1 层：配置层（Pydantic Config + .env）
做法：一个 PdfReviewConfig(BaseModel) 把所有配置（模型端点、并发数、开关、路径）收在一处，字段全带默认值；从 .env 用 dotenv_values 读，映射进 Config。

可复用点：

配置对象用 model_copy(update={...}) 做按任务覆盖（每个 job 有自己的 output_dir/开关），而不是改全局。这是并发安全的关键。
路径解析方法内置在 Config 里（resolved_output_dir() 等），且基于 Path(__file__) 固定推算，不依赖启动时 cwd（他们踩过 cwd 导致数据分裂的坑）。
class MyConfig(BaseModel):
    model_base_url: str = ""
    model_api_key: str = ""
    model_name: str = ""
    concurrency_limit: int = 15
    skip_xxx: bool = False          # 功能开关
    output_dir: str = ""
    def resolved_output_dir(self) -> Path | None: ...
第 2 层：模型接入层（最容易被平台绑死的地方，他们解耦得很好）
做法：build_text_model / build_fast_model / build_vision_model 三个工厂函数，都返回 pydantic-ai 的 OpenAIChatModel。用 OpenAIProvider(base_url, api_key, http_client) 包装。

可复用的两个技巧：

自定义 httpx transport 注入平台专有认证——他们用 _UserKeyTransport 在每个请求 URL 上自动追加 ?user_key=xxx（海信内网要求）。你接任何"非标准 OpenAI"的内网/私有网关时，这个模式直接抄：继承 httpx.AsyncHTTPTransport，在 handle_async_request 里改 request。
优雅降级：fast 模型没配就回退主模型，vision 没配就回退文本模型。让"少配几个模型也能跑"。
你要注意的坑（我们今天就踩到）：不同平台的"专有参数"（如 chat_template_kwargs、vision 的 clientId）会让别的平台 400。把这类参数集中放在 
settings.py
 的常量里（NO_THINK/FAST），换平台只改一处。这是很好的设计——参数不散落在调用点。

第 3 层：流水线层（这是整个项目的灵魂）
run_pipeline(input, config, verbose, on_event) 一个异步主函数，5 阶段：

预处理 → 多路并行审查 → 合并（代码逻辑）→ 仲裁（LLM）→ 输出
可复用的关键设计：

(a) 多路并行 + 全局信号量

sem = asyncio.Semaphore(config.concurrency_limit)  # 防打爆配额
results = await asyncio.gather(*[_run_one(...) for ... ])
把一个大任务拆成 N 个独立子任务（这里是 7 个规则分类 × 2 模型 + 3 视觉路），全并行，用 Semaphore 限流。你的新项目只要有"对同一份输入做多种检查/多角度处理"的场景，这个模式直接套。

(b) 双模型交叉验证 + 置信度分层（最有价值的设计思想） 两个异构模型跑相同任务，用代码（不是 LLM）合并结果：

都报 → high；只有强模型报 → medium；只有快模型报 → low
匹配用模糊策略（同页+前15字符相同或包含关系）
这把"要不要信这条结果"从模型自评变成了系统的客观分层。任何"LLM 判断易误报、需要提高可信度"的场景都适用——用两个模型/两次采样的交并集代替单次输出。

(c) 独立仲裁阶段 初审后，再用一个 LLM 不带规则地去重、删误报、纠正。职责单一。仲裁 prompt 与初审 prompt 分离。

(d) 进度回调 on_event——核心与 Web 的唯一耦合点

def _emit(on_event, **payload):
    if on_event: 
        try: on_event(payload)
        except: pass   # 回调异常绝不影响主流程
阶段边界 emit {"type":"stage","stage":"审查","progress":0.5}。Web 层塞一个回调进去更新任务进度。这个"可选回调 + 吞异常"的解耦模式，是让核心保持独立的关键，务必照抄。

(e) 检查点（checkpoint） 每次跑完把所有中间态（各路结果、合并结果、最终结果、页图路径）落一个 JSON。支持"不重跑 LLM、只重做后处理/输出"。省钱省时，也是结果页数据源。

第 4 层：知识/规则层（把"业务知识"从代码里抽出来）
做法：

正向规则：.md（给 LLM 看的自然语言）+ index.yaml（给代码筛选的多维数组标签）。运行时按元数据（语言/市场/品牌…）精确筛选，只把相关规则拼进 prompt。
反向规则（误报防护）：独立知识库，追加到 prompt 末尾说"这些场景不要报"。
学习闭环：审查→人工反馈→积累→阈值触发→LLM 生成建议→人工审批→落库→下次生效。
可复用点（这是让系统"越用越准"的机制）：

规则驱动，不靠模型自由发挥——业务规则是数据（yaml/md），改规则不改代码。你的新项目里"判断标准/校验规则/领域知识"都应这样外置。
双向规则：正向（要查什么）+ 反向（别误报什么）分离，生命周期不同。
反馈→建议→审批三段式，且 LLM 只出建议、落库必须人工。可自动化的（生成建议）自动化，有风险的（改规则）留人工关卡。
规则效果统计（trigger/accepted/rejected 次数、采纳率），让规则本身可被数据评价、可淘汰。
第 5 层：输出容错 + 后处理（工程质量的体现）
(a) LLM 输出解析容错——"先枚举畸形再定方案" _parse_issues_json 多层降级：直接 parse → 修复未转义引号 → 剥离 <think> → 截断 JSON 补全。失败原文落盘到 traces/。任何要 LLM 输出结构化 JSON 的项目都需要这层，直接抄这个多级 fallback 思路。

(b) 全链路 trace 每个 LLM/外部调用记录：类型+参数+状态+耗时+解析条数+原始返回。traced_call(tracer, label, call_fn, parse_fn) 统一包裹。可观测性拉满，出问题能回溯。

(c) 多层降级定位器（这个是 PDF 特有的，但思想通用） locate.py 6 层策略逐层放宽，保证 100% 有结果（最后兜底页面中心）。思想：当"把 LLM 的文字输出映射回原始数据位置"这类操作注定部分失败时，用多级降级 + 保底而不是"要么成功要么报错"。

第 6 层：Web 服务层（薄壳，但工程细节值得抄）
任务模型（异步作业系统骨架，通用性极强）：

JobRecord（Pydantic）：状态机 queued→running→done/failed + 所有产物路径 + 归属字段。
JobRegistry：进程内 dict + 每个 job 落盘 job.json + 启动时 recover（重启后 running/queued 判为 failed，历史可查）。
JobRunner：asyncio.Semaphore 限并发 + create_task 后台跑 + cancel 支持删除中断。
这套"上传→排队→后台异步跑→轮询进度→取结果"是任何长耗时任务 Web 化的标准骨架，几乎可原样复用。

其它可抄的工程细节：

统一错误信封：{"error":{code,message,detail}} + 一个 HTTPException handler 集中处理。
JWT 鉴权：users.yaml（PBKDF2 密码哈希）+ require_user/require_admin 依赖注入。轻量、无需数据库。
归属用稳定外键（owner_username）而非展示名软过滤；部门用创建时快照（人员调动不影响历史）。
规则写操作前自动全量备份 + 可回滚（备份前再备份，回滚也可逆）。
前后端一体：后端 serve 前端静态产物（SPA fallback），统一子路径。
单实例假设：进程内 dict 无锁（asyncio 单线程），文档里明确写了"要多副本就换 Redis/DB"——先简单，把扩展点标注清楚。
三、把它抽象成你新项目的通用模板
不管你新项目是"审合同 / 查代码 / 校对文案 / 审图片 / 质检数据"，这个框架的通用形态是：

输入物料 → 预处理成 LLM 可读的结构 → 多路/多模型并行分析（规则约束）→ 代码合并分层 → LLM 仲裁去噪 → 结构化输出 + 定位标注 → 人工反馈 → 规则进化

四、可直接沿用的设计原则清单
这些是 BLUEPRINT 里的原则，抽象后对任何 LLM 应用都成立：

准确第一，宁可漏报不误报——每条结果必须有依据（规则号或推理说明），可追溯。
LLM 输出不可信——每个解析 try/except + 类型检查 + 缺省值；先枚举畸形再定方案。
规则/知识外置——新能力优先加规则（低成本）→ 改 prompt → 最后才改代码。
可观测——每步 trace，问题可回溯。
并发有限——全局 Semaphore 防打爆配额。
依赖单向——核心零依赖外壳，可独立运行/移植。
有风险的操作留人工关卡——自动生成建议，人工审批落库；写操作前自动备份。
先单实例简单实现，扩展点标注清楚——不过早上分布式。
