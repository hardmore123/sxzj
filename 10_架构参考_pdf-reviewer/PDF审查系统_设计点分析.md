PDF 审查系统 —— 设计点分析
这是一个面向海信电视说明书质量审查的自动化流水线，用大模型审查多语言 PDF（中/英/日等），核心目标是"宁可漏报不误报"。整个系统的设计围绕一个矛盾展开：大模型输出不可信、容易误报，但审查又必须准确可追溯。它的每个设计点几乎都是为了化解这个矛盾。

下面按设计点逐个拆解——每个都说明实现了什么功能、构思是什么、具体做了哪些工作。

设计点 1：双模型交叉验证 + 独立仲裁（v4 架构）
实现的功能：同一批审查任务由两个不同的大模型（强模型 α=qwen3-397b、快模型 β=deepseek-flash）跑完全相同的 7 个规则分类、用同一套 prompt，再由代码合并、最后由独立仲裁模型去重删误报。

设计构思：

单模型审查要么漏报（保守）要么误报（激进），无法两全。用两个异构模型跑相同任务，通过结果的交并集天然地给出置信度分层，把"要不要相信这条问题"从模型的自评变成了系统的客观判断。
关键演进（2026-07-06）：早期 v3 版本是"按检查动作分工"（α查一致性/逻辑，β查拼写/数值），两个模型查的东西不同，只有部分重叠，无法真正交叉验证。v4 改成两模型跑相同分类，才实现了全面交叉验证。
具体做的工作（_merge_text_issues）：

α∩β（两模型都报）→ high 高置信
仅 α（强模型报）→ medium 中置信
仅 β（快模型报）→ low 低置信
匹配用模糊策略（_text_similar：同页 + 前 15 字符相同或包含关系），容忍两模型措辞差异
仲裁阶段不加载规则，纯做去重、删误报、纠正分类，避免规则再次干扰终审判断
强调"deepseek 可无缝替换成任意第二模型"，第二模型是可插拔的
这是整个系统最核心的设计——用架构（多模型冗余）而非单模型能力来保证准确性。

设计点 2：规则驱动 + 8 分类多维标签体系
实现的功能：审查行为由一个可追踪、可学习、可回滚的规则库约束（115 条正向规则 + 16 条反向规则），而不是让模型自由发挥。规则按元数据（语言/市场/品牌/文档类型）精确筛选后才注入 prompt。

设计构思：

核心理念是"category 管审查目标，其他标签管加载范围"。一份中文 CCC 认证说明书不该被喂进英文 FCC 规则，精确筛选既省 token 又减少误报。
规则用 .md（给人和 LLM 看的自然语言）+ index.yaml（给代码筛选的结构化多维数组标签）双层表示，人机各取所需。
具体做的工作：

预处理阶段先做 DocumentMeta 检测（语言按中英日字符比例+假名检测、市场按 CCC/FCC/CE 等关键词、品牌按文件名+文本），得出文档属性
RuleFilter 按 category + language + market(数组) + brand + needs_ref 精确筛选；通用规则(language=all)始终保留
条件加载：当用户上传了补充参考文档时，needs_ref=True 的规则也放行（+28% 规则量）
8 个分类中 7 个走文本路、visual_layout_assets 走视觉路
设计点 3：反向规则库（误报防护知识库）
实现的功能：一个独立于正向规则的"以下场景不要报为问题"知识库，追加到 prompt 末尾，专门压制已知的误报模式。

设计构思：这是"宁可漏报不误报"原则的直接落地。正向规则告诉模型"查什么"，反向规则告诉模型"别乱报什么"。二者分离，因为它们生命周期不同——反向规则大多来自反馈闭环中真实发生过的误报。

具体做的工作：文档里记录了几类典型误报及其根因和修复，很有说服力：

"断句错误暴增" → 根因是强模型 + 宽 prompt，修复是收窄 prompt 明确"PDF 提取的跨块换行不是断句错误"
"标准编号 IEC 62368-1 被误报为数值格式错误" → 加反向规则用正则 (FCC|UL|IEC|EN|GB/T|CB)\s*[A-Z0-9/-]+ 排除
反向规则带 pattern(正则) + instruction(自然语言) + examples，既能给 LLM 看又能精确匹配。

设计点 4：规则学习闭环（反馈→积累→建议→审批→落库）
实现的功能：审查完自动生成反馈模板，人工标注每条问题（✅正确/❌误报/⚠️部分正确），积累到阈值后由 LLM 分析生成规则建议，管理员审批后落库，下次审查自动生效。

设计构思：审查系统不能是静态的——真实误报和漏报模式只有在使用中才暴露。这个闭环把"人工复核的劳动"转化为"规则库的持续改进"，且每一步都有人工确认关卡（LLM 生成建议但绝不自动改规则），符合"审查准确第一"。

具体做的工作：

5 个阶段：反馈模板生成/解析 → 排除名单 → 经验积累统计 → LLM 辅助提炼 → 自动提醒
阈值触发：≥5 条新反馈，或 ≥3 条新反馈且误报≥3 条 → 提示运行 learn
LLM 建议分三类：新增排除模式、新增规则、修改建议
规则效果统计（rule_stats.yaml）记录每条规则的 trigger/accepted/rejected 次数，算出 acceptance_rate——让规则本身可被数据评价
设计点 5：统一定位器 + 6 层降级策略
实现的功能：把模型报出的问题（文字描述）精确定位到 PDF 上的坐标框，标注红框+序号。
locate.py
 统一算一次坐标，PNG 渲染和 PDF 批注共用同一结果。

设计构思：

早期 PNG 标注和 PDF 导出各有一套定位逻辑，割裂且不一致。重构成"定位只跑一次，以 PDF points 为标准坐标系写回 issue"（_bbox_pt），彻底消除割裂。
定位注定会失败（模型原文和 PDF 提取文本对不上、图片类问题没文字），所以设计成6 层降级，逐层放宽，保证 ~100% 可定位率（有兜底就永远有框）。
具体做的工作（6 层，全部归一到 PDF points）：

pymupdf 精确搜索原文（剥离项目符号，30→20→12→8 前缀降级，窄框防护）
block_id 匹配（PDF 块优先，OCR 块其次，像素→points 换算）
关键词宽松搜索
图号关键词（"图一/图二"）关联最近图片
该页最大图片
文本区域中点 / 页面中心兜底
还有个细节修复：早期"标注框只框前几个字"，因为前缀命中只覆盖前缀宽度——修复是命中后扩展到整个文本块的 bbox。定位后按阅读顺序（页→y→x）重排重新编号。

设计点 6：LLM 输出容错（畸形枚举 + JSON 修复）
实现的功能：把不可信的 LLM 输出安全地解析成结构化数据，各种畸形都不崩溃。

设计构思：项目原则明确写"LLM 输出不可信：每个输出解析都要 try/except + 类型检查 + 缺省值"，工程规则要求"修解析类问题先列举可能的输入畸形种类再定方案"。

具体做的工作：

_repair_unescaped_quotes：专门修复英寸符号 " 未转义破坏 json.loads 的问题（已知误报模式）
_try_fix_truncated_json：修复被 max_tokens 截断的 JSON
_parse_issues_json：多层容错解析
失败/空返回的原始输出落盘到 traces/ 供排查
全局重试：所有 LLM 调用最多重试 2 次，指数退避（3s, 6s）
设计点 7：可移植的独立包 + 可选 Web 层
实现的功能：pdf_review/ 是零依赖外部项目的独立包，一个 git clone + uv sync 就能跑 CLI；Web 服务是它之上的薄层可选依赖。

设计构思：核心原则"独立可移植"。关键设计是依赖单向——webapi/ 只引用核心模块，核心模块绝不引用 webapi。因此去掉 FastAPI 核心包仍能单独跑 CLI。整个 Web 层对核心的侵入被严格限制在唯一一个可选参数 on_event（进度回调），保证可移植性不被破坏。

具体做的工作：

CLI（__main__.py）：审查 / --v3 回退 / --checkpoint 重跑 / feedback / learn
Web（FastAPI 子包）：任务全流程、反馈裁决、规则浏览/编辑、建议审批、备份回滚
前端 Vite+React，后端 serve 前端静态文件，统一 /pdf-reviewer/ 子路径，前后端一体部署
设计点 8：Web 服务的工程化细节
几个体现"考虑周全"的设计：

JWT 用户账号体系（2026-07-15 从两级静态 Token 升级）：owner_username 作为任务归属的稳定外键（不再用 uploader 字符串软过滤），owner_department 是创建时的部门快照（用户调岗不影响历史任务归属）——这是对"权限边界"和"历史一致性"的深思
并发控制：全局信号量 MAX_CONCURRENT_JOBS（默认 2）防多任务打爆 LLM 配额，单流水线内部已并发 15 路
进程内注册表 + job.json 落盘：进程重启后仍可查历史/取结果
轮询而非 SSE/WebSocket：单实例简化，进度由 on_event 回调驱动（预处理 0.1→审查 0.5→仲裁 0.85→完成 1.0）
规则写操作前自动全量备份，可回滚，回滚前再备份（回滚本身也可逆）
统一错误信封 {"error":{code,message,detail}}，job_id 强制 UUID 校验防路径穿越
前端对接坑点也写进契约：带鉴权的图片不能直接用 <img src>（要 fetch→blob），非常务实
整体评价
这个项目最值得学习的地方，是它把"大模型不可信"这个前提贯彻到了每一层：

层次	应对"不可信"的手段
模型层	双模型交叉验证，用异构冗余分层置信度
规则层	正向规则约束"查什么" + 反向规则压制误报
解析层	畸形枚举 + JSON 修复 + 重试 + trace 落盘
定位层	6 层降级保证永不失败
流程层	独立仲裁去重 + 人工反馈闭环持续纠偏
落库层	LLM 只出建议，人工审批，自动备份可回滚
加上文档体系（BLUEPRINT 定原则、architecture 定架构、CHANGELOG 记演进），以及"新能力优先加规则（低成本），其次改 prompt，最后改代码"的决策偏好，这是一个把 AI 当成不可靠组件来做工程封装的成熟范例，而不是把 AI 当银弹。它的设计取舍几乎都能追溯到最高层的核心原则，一致性很强。
