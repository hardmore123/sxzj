# 多智能体设计经验精华（DSH + LangGraph）

> 来源：`桌面\日志笔记记录\一句话原则.md`（356行）
> 这是实习期间深入学习 DeepSeek Harness (DSH) 多智能体设计后整理的原则，对今后做多智能体系统极有价值。

---

## 一句话原则

> **多智能体里没有隐式共享。** 记忆必须**显式选择**，沟通必须**显式发送**，权威必须**显式持有**。
> 凡是"我以为它应该知道"的地方，都是 bug 的温床。

---

## 一、方向性判断

> **DSH 默认"什么都不共享"，LangGraph 默认"什么都共享"。**
> 所以两者要做的第一件事正好相反 —— DSH 要显式**打开**共享，LangGraph 要显式**切开**共享。

带着 DSH 思路用 LangGraph，会觉得"怎么什么都看得见"；带着 LangGraph 思路用 DSH，会觉得"怎么什么都得手动传"。**这是默认值的差异，不是能力差异。**

---

## 二、记忆侧：五个必须主动做的决定

### 决定 1：每个子代理的记忆来源，三选一（没有第四个）

| 选择 | 子代理看到 | 什么时候用 |
|---|---|---|
| **全新开始** | 什么都看不到 | 任务独立、要上下文干净 |
| **继承前缀** | 父的**已完成回合** | "接着我刚才的工作做" |
| **消息传递** | 事后一条条发 | 需要中途补充信息 |

**默认做法**：拿不准就用"全新开始" + 把必要背景写进任务描述里。继承会把父的历史塞进子的上下文预算，多半用不上。

**两个硬约束**：
- 继承只到父**最后一条回合结束**为止——当前正在进行的回合不会传过去
- **继承是快照，不是订阅**。分出去之后父继续干活，子不会看到新内容

### 决定 2：把子代理当"上下文防火墙"用（最容易忽略、收益最大）

> 让一个子代理去读 20 个文件、只把**结论**带回来，主会话的上下文**一点污染都没有**。

**反面做法**：让主会话自己去读 20 个文件——上下文直接被塞满，之后每一轮都在为这些内容付钱，而且很快触发压缩。

**做法**：读大文件、翻日志、多路检索这类"过程很长但结论很短"的工作，一律外包。

### 决定 3：回传的是结论，不是流水

父**不会自动看到**子的完整对话——它只拿到子的**最终输出**和一条**结束通知**。所以子的任务描述里就要写清楚"你要回传什么格式"。

### 决定 4：能活过重启的东西，才写进"身份卡"

可续跑子代理能冷恢复，但恢复时**只重建五样**：模型、推理档、角色设定、工具范围、提供方。

**刻意不恢复**的三样：结构化输出格式约定、每次任务的 token 预算、递归深度。

**实践含义**：子代理的"长期人设和配置"放身份卡里能活过重启；"这次任务的临时约定"必须写在任务描述里，重启后不会自动回来。

### 决定 5：权限在启动时固定，别指望会话内放宽

子代理权限在启动那一刻就固定了。**开会话时选对权限档**，而不是指望事后放宽；鼓励子代理**报告限制**而不是反复重试。

## 三、沟通侧：四条铁律

### 铁律 1：权威来自"活着的对象关系"，不来自消息内容

- 父→子：要求子会话记录里记明父是它的父
- 子→父：要求子的常驻实例记明目标
- **兄弟之间、隔代、自己发给自己、过期的对象、一次性的子——一律拒绝**
- 消息上的"发送者"字段**只用于追溯，不授予任何权限**

> **能说话 ≠ 有资格说话。** 把权限判断建立在消息字段上是常见的安全漏洞。

### 铁律 2：只有一条队列，不要发明第二条

收件箱是**唯一队列**。投递路由按目标状态自动决定（正在跑切进去/空闲唤醒/不在内存冷恢复）。

**反面教材**：在会话之上再糊一层"任务表/消息表/作业表"三件套——真相立刻分裂成两份，然后你就开始写同步代码，而那正是 bug 的产地。

### 铁律 3：投递语义是"至少一次 + 去重"

1. **先落盘"已排队"（先刷盘）** → 2. 再尝试投递 → 3. 目标**真正记下了**才回执"已送达"

- "已排队但未回执"就是恢复邮箱——崩溃后按同样顺序补投
- **不丢不重**：目标侧把来源跨收件箱与历史折叠做去重键

### 铁律 4：中断只停当前回合，不动队列

`interrupt` 语义：**停掉当前正在跑的回合，但保留未领取的队列**，也**不释放任务所有权**。中断之后不需要重新发一遍消息——队列还在。

---

## 四、协调状态：一点模型上下文都别占

> 名册、邮箱、任务板全是 Lead 会话日志里的事件，而且全是"只记录、不进模型历史"。

**你该照抄的原则**：
- 协调状态**从日志重放**，不另建数据库
- 共享状态用**版本号比较并交换**（用过期的版本更新会被拒，而不是覆盖）
- **写作用域只是建议**——重叠时只警告，不阻塞

> **让冲突被看见，比假装能消除冲突更现实。**

---

## 五、规模与边界：会失败，而且要失败得响

| 限制 | 默认 | 说明 |
|---|---|---|
| 递归深度 | **1** | 只允许直接子 |
| 同时活跃可续跑子 | **8** | 超限直接报错，不排队 |
| 团队人数 | **16** | 含创建失败的 |
| 活跃任务 | **256** | id 耗尽报错，**绝不重用** |

**两个刻意设计**：
- **超限不排队**——"一个正在等后代的父，不能去等自己被占满的槽位"，否则死锁
- **名字永久占用**——避免"名字指向了另一个 agent"这类幽灵 bug

## 六、反模式速查

| 反模式 | 后果 | 改法 |
|---|---|---|
| "新开会话它应该知道啊" | 默认就是不通 | 显式选记忆来源 |
| 让主会话自己读一堆大文件 | 上下文被污染、很快爆 | 外包给子代理，只回结论 |
| 在会话之上再造一层消息表 | 两份真相+同步代码 | 用同一条队列 |
| 用消息里的 sender 字段判权限 | 安全漏洞 | 查活对象关系 |
| 把"这次任务的约定"当成长久配置 | 重启后丢失 | 写进任务描述 |
| 建一堆 agent 指望更快 | 冲突、相互覆盖 | 上限是刻意的，先让冲突可见 |
| 用子代理的"我做完了"当验收 | 自我报告不是验证 | 必须有独立的验证路径 |
| 中断后重发一遍消息 | 重复执行 | 队列还留着 |

---

## 七、设计检查清单（八条）

1. 每个子代理的记忆来源，是**刻意选的**还是碰巧的？
2. 子代理回传的是**结论**还是**流水**？格式约定写进任务描述了吗？
3. 哪些东西必须活过重启？它们在"身份卡"里吗？
4. 谁能给谁发消息？这个判断是**查活对象**还是**信消息字段**？
5. 队列有几条？去重键是什么？怎么判定"已送达"？
6. 共享状态存在哪？两台机器同时改会怎样——**被拒绝、被覆盖，还是看不见**？
7. 所有上限都是**会失败**的吗（报错而不是静默丢弃）？
8. 子代理说"做完了"，**谁来独立验证**？

## 八、LangGraph 对照（换个框架该怎么做）

| 概念 | LangGraph | DSH |
|---|---|---|
| 状态载体 | graph state（节点间共享） | 每个 agent 独立的会话日志 |
| 短期记忆 | checkpointer + `thread_id` | 会话日志 + 投影 |
| 长期记忆 | store（跨 thread，namespace） | 外部记忆/跨会话引用/日志检索 |
| 消息 | `messages` + `add_messages` reducer | 单一收件箱队列 |
| 并发写 | **reducer 决定怎么合并** | 单写者所有权 |
| 权威判断 | **没有这个概念** | 活对象关系（父/子边） |
| 交付语义 | 状态快照重放 | 至少一次+去重 |
| 版本演进 | **没有内置** | 格式版本+相邻迁移链 |

> **权威、交付、版本，LangGraph 都不给**。这三样恰好是多智能体最容易出事的地方，所以都得自己补。

### LangGraph 必须自己补的四块

1. **handoff 目标白名单化**——不是"模型说切给谁就切给谁"，handoff 是提示注入面
2. **reducer 语义要刻意**——每个 state key 想清楚是追加/覆盖/合并，否则并行边会静默覆盖
3. **压缩不是自动的**——要自己在图里加"检查长度→生成摘要→替换消息"的节点
4. **checkpoint 保留策略**——官方把"checkpoint 无限增长"列为常见问题

> **一句话总结**：LangGraph 给你的是**一张可持久化的执行图 + 一套状态容器**——编排能力很强，但**记忆分层、边界、权威、交付语义全都要你自己设计**。DSH 那套"五条边界"在这里依然适用，只是每一条你都得亲手实现。
