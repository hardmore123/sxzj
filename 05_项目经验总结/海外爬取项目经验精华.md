## 一、核心方法论：探索→复用→回灌的闭环（全场核心）

这是本项目最值钱的东西，建议直接抄走：

```
    每个新站只做一次                每天/每周自动跑
┌──────────────────────┐     ┌──────────────────────┐
│  ① 探索              │     │  ② 复用              │
│  agent + skill       │     │  引擎读 schema       │
│  产出 schema/adapter │     │  固定代码抓全站      │
└──────────┬───────────┘     └──────────┬───────────┘
           ▼                            ▼
    schema/adapter ────────► 爬取结果 + 审计数据
           ▲                            │
           │                            │
┌──────────┴───────────┐                │
│  ③ 回灌              │◄───────────────┘
│  经验写回 skill       │
│  → 下次同型站几乎零成本│
└──────────────────────┘
```

**一句话**：把"每个站都要写代码"变成"每个站只探索一次，之后永远复用，而且每探索一次下次更快"。

| 环节 | 谁来做 | 频率 | 成本 |
|---|---|---|---|
| ① 探索生成 | agent + skill | 每个新站一次 | 一次性 LLM 成本 + 人审 |
| ② 复用爬取 | 固定引擎读 schema | 每天/每周 | **零 LLM、零人工** |
| ③ 经验回灌 | 强制沉淀（做成机制） | 每次接站后 | 几分钟 |

**最值钱的不是"AI 能生成配置"，而是第③步——经验会留在 skill 里**。有了③，成本才从线性变成递减。

## 二、四条工程红线（支撑闭环长期转下去）

| 原则 | 落地方式 | 防什么 |
|---|---|---|
| **只产配置，不产代码** | 需要执行的 JS 只能引用已登记片段库，禁止内联 | 失控逻辑 |
| **用真实数据当 reward** | 拿真实入库结果打分，不采信 LLM/脚本自述 | 闭环"自我感觉良好" |
| **红线要能自动否决** | 找全率 < 80% 直接判失败 | ★**抓一半当成功**（最危险） |
| **能力边界显式化** | 白名单常量；越界报错而非静默降级 | 假装支持导致的隐性缺失 |

> **第三条是红线，建议所有人都抄走。** 误判成功比抓不到更危险——抓不到会被发现，抓一半当成功会污染交付数据，而且很难被察觉。真实代价：某次登录墙被误判为反爬，621 个型号静默全跳过，日志看起来完全正常。

## 三、8 条可以直接拿走的经验

| # | 借鉴点 | 一句话 |
|---|---|---|
| **1** | ★ 把"每个站都做一遍"改成闭环 | ①探索一次 → ②引擎复用 → ③经验回灌；接站成本随数量递减 |

## 四、页面结构类：8 种翻页类型（先分类再解决）

翻页不是一个问题，是**八个问题**，每一类解法完全不同：

| 类型 | 表现 | 抓法 |
|---|---|---|
| 静态一次列全 | 首屏即全部 | 直接取 |
| 滚动懒加载 | 滚动才注入 | 滚动到**连续 N 轮不增长**再取 |
| 点"加载更多" | 点击追加 | 累积到不增长 |
| 编号页码 | 1/2/3 | 逐页点击累积 |
| **替换式渲染** | 翻页后内容被替换而非追加 | 每次翻页后**重扫页码**，累积到连续 2 轮不增长 |
| 服务端参数分页 | `?page=N` | 拼 URL 逐页取 |
| 需要 JS 渲染 | 页面有内容但程序抓到 0 | 上真实浏览器 |
| 一个系列多尺寸，DOM 只渲染一个代表 | 只解析 DOM 会严重漏 | 找**权威来源**（接口/swatch/详情页展开） |

**三条最值得抄的原理**：
1. **先分类，再解决**。用"点下一页"的通用方案去解决"替换式渲染"，只会拿到 12/25。
2. **等稳定 ≠ 等固定时间**。"滚 3 次"会漏，正确做法是等到集合不再增长。
3. **优先找权威来源，不要只解析 DOM**。靠这一条把某站从 6 系列/9 型号补到 64 系列/224 型号。

## 五、反爬类：三个反直觉的实测结论

### 1. 登录 ≠ 绕过反爬（最反直觉）

实测：真实浏览器、带 cookie、从首页进搜索，**仍然被拦**。IP 层被拦时，登录态、UA、Cookie 都不起作用，**唯一变量是出口线路**。

> 这是最容易被自我安慰的地方——很容易以为"只要我登录了就能抓"。把这条讲清楚，能省掉大量"再试试登录"的无效尝试。

### 2. 整页压缩喂模型会帮倒忙

实测对比：原始 HTML 直喂 → **94 分通过**；简单整页压缩后喂 → **0 分失败**。压缩破坏了 `id`/`class` 结构线索，LLM 只能生成 `h1` / `.price` 这种通用猜测。

**正确做法**：重复卡片去重 + 只保留对生成选择器有用的属性（id/class/href/data-*）。效果：112K → **418 字符，且页尾关键元素 4/4 全保留**。

### 3. 登录墙和反爬必须分开归因

曾把登录失效算作反爬，触发站级熔断，结果 **621 个型号静默全跳过**，日志看起来"很正常"。**分类错误比能力不足更危险**——能力不足你知道抓不到，分类错误会让你以为"这站抓不了"而永久放弃。

## 六、数据正确性类：底线原则

| 原则 | 说明 |
|---|---|
| **宁可缺，不可假** | 不写空价行、不用抓取时间冒充官网时间、不伪造历史。缺价就留空（缺价 > 错价） |
| **状态要语义化** | `empty`（请求成功但无数据）和 `failed`（请求失败）必须分开，不能用空表覆盖旧快照 |
| **"抓得少" ≠ "漏抓"** | 先实测核对（新机确实 0 评价、老系列接口确实 404），再判断是不是 bug |
| **退出码 0 ≠ 成功** | 必须同时核对审计表 + 状态表行数 + 产物文件行数 |
| **守恒校验** | 发现数必须等于落库数 |
| **匹配分级优先** | 前缀 > 独立词 > 子串 > 兜底，宁缺毋滥，绝不盲取第一个 |
| **尺寸一致性守卫** | 红线级，防止 55 吋的价记到 65 吋 |

## 七、长任务与运维类

### 三条最值得抄的原理

**① 长任务的第一原则不是"跑得快"，是"一定会停"。**
六条终止条件：条数上限 / 本页无新增 / 页数上限 / 拼不出下一页 / 被拦 / HTTP 连续失败。某站从"撞 148 个限流"变成"5 个即停"——**熔断比重试有用**。

**② 幂等是"敢跑 10 小时"的前提。**
时序表只增不改 + 唯一约束 + 只补空字段 → 中途被 kill 直接重跑即可，还能回填历史空值。

**③ 交接文档是交付物的一部分。**
目标是让接手人 30 分钟知道：现在在哪、能跑什么、下一步做什么、有哪些坑。最值钱的两节是「**必须知道的实测结论（别抱错希望）**」和「**风险提示**」。

### 实用技巧

| 问题 | 解法 |
|---|---|
| 跑几小时被超时 kill | 后台跑（前台通常 10 分钟被杀） |
| 轮询看不到日志以为卡死 | 日志是缓冲到进程结束才落盘的，用进程状态+产物文件判断进度 |
| 输出中文乱码 | 设 UTF-8 环境变量 + 直接重定向，不要用会按本地代码页转码的管道命令 |
| 并发反而更慢 | 用自己的实测数据决定并发度，我们实测并发反而更慢且更易触发风控 |

## 八、AI 协作类：怎么用 LLM 才划算

### 四条最值得抄的原理

**① 省 token 的终极答案不是压缩 prompt，是让 LLM 只跑一次。**
架构选择直接让日常全量抓取 token = 0。这跟"每页都调 LLM 抽取"的路线根本冲突——**选路线的时候就决定了成本**。

**② 让成本递减的答案不是"模型更聪明"，是让经验留下来。**
①探索只做一次、②复用零成本、③经验回灌让下一次的①几乎免费。最容易做漏的是第③步——因为它不影响本次成功率，只影响下一次，所以必须做成**强制流程**。

**③ 喂 LLM 有一个反直觉的坑：整页压缩会帮倒忙。**（见第五节）

**④ 两条最省钱的工作纪律：**
- **每轮只动一个变量**（否则分不清哪个改动起作用——为此花过 4 小时排查）
- **先证伪，再改代码**（三次印证：以为是抓取错误其实是归一化问题；以为是选择器其实是 JS 转义 bug；以为是代码 bug 其实是 IP 限流）

> 花半小时取证，比花半天改错地方划算。**你让 AI 去改一个不存在的问题，它会很认真地改坏别的东西。**

## 九、能力边界（不假装支持）

### 能全自动覆盖的 6 类页面结构（均真实站验证）

静态列表一次列全 ✅ / 懒加载注入 ✅ / 编号页码分页（含替换式）✅ 100% / JS 延迟注入 ✅ / 多级发现 ✅ / 接口发现+参数分页 ✅

### 仍需人写的

| 场景 | 为什么 |
|---|---|
| 型号 slug 完全无规律 | 无法用正则框住 |
| 需要带签名的接口 | 动态签名难自动复现 |
| 特殊分页的累积抓取 | 需站点专属片段 → 如实报告"需人工补一块" |
| 要点 tab 才出规格的 SPA | 交互链无法通用化 |
| 需登录/验证码/加购才显价 | 业务上必须人参与 |

### 三条止损信号（什么时候该放弃）

```
型号 slug 无规律、无法用正则框住
Load More 通用点击点不开
需要多级页面才拿到型号
需要调用带签名的接口
需要登录/验证码/加购后才显示
  → 停下来，记为「需人工适配」并说明缺口，不要在超边界站上耗时间
```

> **止损也是能力。** 让生成器本身给出这五个信号，命中就直接判"需人工"，而不是无限重试。

### 诚实的能力定位

> 系统的真实价值是：**标准站全自动；特殊分页站自动识别+复用已有片段，无匹配时精确告知人工补哪一块** —— 而不是号称"任意站零人工"。

## 十、借鉴开源项目的判断标准

借鉴了 Crawl4AI（5万 star）的架构模式，但**不引入该包**：

| 借鉴的 | 不借鉴的 |
|---|---|
| `generate_schema` 思路 → 配置生成器 | LLMExtractionStrategy（每页调 LLM，与 token=0 路线冲突） |
| `preprocess_html_for_schema` 重复卡片去重 → HTML 降噪 | PruningContentFilter（会误删规格表） |
| 插件自动发现、Strategy 分层、域名级调度 | 异步框架、stealth 插件、自有 schema 格式 |

> **判断标准不是"它好不好"，而是"它的设计中心和我的约束是否冲突"。** 它是 async+LLM 中心，我是同步+零依赖中心，那就只拿设计、不拿代码。**借鉴架构模式，不引入依赖。**

## 十一、Crawl4AI 三支柱与我们的 Skill 同源

Crawl4AI 作者提出 LLM Context Protocol 三支柱，我们的 skill 结构几乎是它的实例化：

| 支柱 | 内容 | 对应 skill 里的 |
|---|---|---|
| Memory（记忆） | API 签名、参数、类型——"事实" | `reference.md`：信号→解法规律 |
| Reasoning（推理） | 为什么这么设计——作者哲学 | `SKILL.md` 的铁律 + 判断口径 |
| Examples（示例） | 纯代码，无废话 | `cases.jsonl` + `playbook/` |

> 这三支柱就是"省 token 的正确姿势"——不是把所有东西塞进 prompt，而是**分层**：每次都进上下文的是"推理与铁律"（7.5 KB），事实与示例**按需检索**。这与我们"渐进式披露"的做法是同一个答案，被独立验证过。
