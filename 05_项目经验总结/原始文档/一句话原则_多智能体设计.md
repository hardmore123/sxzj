这个问题正好把前面所有材料收束成一套可操作的做法。我按**记忆**和**沟通**两条线来讲，最后给检查清单。

## 一句话原则

> **多智能体里没有隐式共享。** 记忆必须**显式选择**，沟通必须**显式发送**，权威必须**显式持有**。
> 凡是"我以为它应该知道"的地方，都是 bug 的温床。

---

# 一、记忆侧：五个必须主动做的决定

## 决定 1：每个子代理的记忆来源，三选一（没有第四个）

| 选择         | 子代理看到         | 什么时候用             |
| ------------ | ------------------ | ---------------------- |
| **全新开始** | 什么都看不到       | 任务独立、要上下文干净 |
| **继承前缀** | 父的**已完成回合** | "接着我刚才的工作做"   |
| **消息传递** | 事后一条条发       | 需要中途补充信息       |

**默认做法**：拿不准就用"全新开始" + 把必要背景写进任务描述里。理由：继承会**把父的历史塞进子的上下文预算**，而它多半用不上。

**必须知道的两个硬约束**：

- 继承只到父**最后一条回合结束**为止 —— **当前正在进行的回合不会传过去**。所以模型面向的措辞也分两套：全新的说"它看不到这个对话"，继承的说"它看不到当前正在进行的回合"。
- **继承是快照，不是订阅。** 分出去之后父继续干活，子不会看到新内容。

## 决定 2：把子代理当"上下文防火墙"用，而不是只当"并行加速"

这是**最容易忽略、收益最大**的一招：

> 让一个子代理去读 20 个文件、只把**结论**带回来，主会话的上下文**一点污染都没有**。

反面做法：让主会话自己去读 20 个文件 —— 上下文直接被塞满，之后每一轮都在为这些内容付钱，而且很快触发压缩。

**做法**：读大文件、翻日志、多路检索这类"过程很长但结论很短"的工作，一律外包。

## 决定 3：回传的是结论，不是流水

父**不会自动看到**子的完整对话 —— 它只拿到两样东西：

- 子的**最终输出**（最后一条非空助手消息）；
- 一条**结束通知**（说明这个子是怎么结束的）。

所以子的**任务描述里就要写清楚"你要回传什么格式"**。等它自己猜格式，十次里有一次会给你一大段过程叙述。

> 一个细节值得知道：那条结束通知用的是**独立的来源类型**，不是普通的子消息 —— 设计意图是"**一段对话记录不能把运行时的叙述算成子代理自己说的话**"。归因必须干净。

## 决定 4：能活过重启的东西，才写进"身份卡"

可续跑的子代理能冷恢复，但恢复时**只重建五样**：模型、推理档、角色设定、工具范围、提供方。

**刻意不恢复**的三样，你要心里有数：

| 不恢复                | 因为                                         |
| --------------------- | -------------------------------------------- |
| 结构化输出的格式约定  | 那属于**一次任务**的约定，不是这个子是谁     |
| 每次任务的 token 预算 | 同上                                         |
| 递归深度              | 改用持久化的**单调**记录，恢复**不能降低**它 |

**实践含义**：子代理的"长期人设和配置"放身份卡里能活过重启；**"这次任务的临时约定"必须写在任务描述里**，重启后不会自动回来。

## 决定 5：权限在启动时固定，别指望会话内放宽

子代理的权限**在启动那一刻就固定了**，而且系统会明确告诉它：

> "你的权限范围在启动时就固定，无法从这个会话内部被放宽 —— 需要审批的操作会被自动拒绝。**不要重试被拒的操作**，把你的限制说清楚，让委派方处理。"

**做法**：
- 开会话时**选对权限档**，而不是指望事后放宽；
- 鼓励子代理**报告限制**而不是反复重试 —— 这句话本身就写在它的上下文里了。

# 二、沟通侧：四条铁律

## 铁律 1：权威来自"活着的对象关系"，不来自消息内容

这是全套设计里最硬的一条：

- 父→子：要求子会话记录里**记明父是它的父**；
- 子→父：要求子的**常驻实例**记明目标；
- **兄弟之间、隔代、自己发给自己、过期的对象、一次性的子** —— 一律拒绝。

而且消息上带的"发送者"字段，**只用于追溯，不授予任何权限**。

> **能说话 ≠ 有资格说话。** 如果你在设计自己的多智能体，把权限判断建立在消息字段上是常见的安全漏洞。

## 铁律 2：只有一条队列，不要发明第二条

DSH 里 agent 的收件箱是**唯一队列**，上层明确声明"**不再定义第二条队列**"。

**投递路由按目标状态自动决定**：

| 目标状态       | 怎么送                 |
| -------------- | ---------------------- |
| 正在跑         | 在最近的步骤边界切进去 |
| 空闲但有牵挂   | 唤醒它，然后切进去     |
| 已经不在内存里 | **冷恢复**，然后再送   |

**反面教材**：在会话之上再糊一层"任务表 / 消息表 / 作业表"三件套。真相立刻分裂成两份，然后你就开始写同步代码 —— 而那正是 bug 的产地。

## 铁律 3：投递语义是"至少一次 + 去重"

团队消息的做法很值得抄：

1. **先落盘"已排队"**（并且先刷盘）→ 2. 再尝试投递 → 3. 目标**真正记下了**才回执"已送达"。

由此得到两个性质：

- **"已排队但未回执"就是恢复邮箱** —— 崩溃后按同样顺序补投；
- **不丢不重**：目标侧把来源**跨收件箱与历史折叠**做去重键。

要注意的诚实声明：这是"**进程内重试 + 目标侧去重**"，**不是跨进程恰好一次**。

## 铁律 4：中断只停当前回合，不动队列

`interrupt` 的语义很讲究：**停掉当前正在跑的回合，但保留未领取的队列**，也**不释放任务所有权**。

**实践含义**：中断之后不需要重新发一遍消息 —— 队列还在，等它闲下来会用。

# 三、协调状态：一点模型上下文都别占

这一条是 Team 设计里最漂亮的地方：

> **名册、邮箱、任务板全是 Lead 会话日志里的事件，而且全是"只记录、不进模型历史"。**

结果是**协调完全不花上下文**，模型只在工具结果里看到它们。

**你该照抄的原则**：

- 协调状态**从日志重放**，不另建数据库；
- 共享状态用**版本号比较并交换**（用过期的版本更新会被拒，而不是覆盖）；
- **写作用域只是建议** —— 重叠时**只警告，不阻塞**。

> 最后这条是刻意的取舍：**让冲突被看见，比假装能消除冲突更现实。**

# 四、规模与边界：会失败，而且要失败得响

| 限制               | 默认      | 说明                      |
| ------------------ | --------- | ------------------------- |
| 递归深度           | **1**     | 只允许直接子              |
| 同时活跃的可续跑子 | **8**     | **超限直接报错，不排队**  |
| 团队人数           | **16**    | 含创建失败的              |
| 活跃任务           | **256**   | id 耗尽报错，**绝不重用** |
| 单成员排队消息     | **64**    |                           |
| 单条消息大小       | **64 KB** |                           |

两个刻意设计：

- **超限不排队** —— 理由很直白："**一个正在等后代的父，不能去等自己被占满的槽位**"，否则死锁。
- **名字永久占用** —— 第一个记录就占住，**连创建失败的也占**，永不重用。避免"名字指向了另一个 agent"这类幽灵 bug。

以及三条要写在明面上的**不支持**：**共享同一个工作目录**（没有 worktree、没有文件锁，命令行工具能绕过检查）、**不跨进程共识**、**没有自动的任务所有权释放**。

# 五、反模式速查

| 反模式                         | 后果                 | 改法                       |
| ------------------------------ | -------------------- | -------------------------- |
| "新开会话它应该知道啊"         | 默认就是不通         | 显式选记忆来源             |
| 让主会话自己读一堆大文件       | 上下文被污染、很快爆 | 外包给子代理，只回结论     |
| 在会话之上再造一层消息表       | 两份真相 + 同步代码  | 用同一条队列               |
| 用消息里的 sender 字段判权限   | 安全漏洞             | 查活对象关系               |
| 把"这次任务的约定"当成长久配置 | 重启后丢失           | 写进任务描述               |
| 建一堆 agent 指望更快          | 冲突、相互覆盖       | 上限是刻意的，先让冲突可见 |
| 用子代理的"我做完了"当验收     | 自我报告不是验证     | 必须有独立的验证路径       |
| 中断后重发一遍消息             | 重复执行             | 队列还留着                 |

# 六、设计检查清单（八条）

1. 每个子代理的记忆来源，是**刻意选的**还是碰巧的？
2. 子代理回传的是**结论**还是**流水**？格式约定写进任务描述了吗？
3. 哪些东西必须活过重启？它们在"身份卡"里吗？
4. 谁能给谁发消息？这个判断是**查活对象**还是**信消息字段**？
5. 队列有几条？去重键是什么？怎么判定"已送达"？
6. 共享状态存在哪？两台机器同时改会怎样 —— **被拒绝、被覆盖，还是看不见**？
7. 所有上限都是**会失败**的吗（报错而不是静默丢弃）？
8. 子代理说"做完了"，**谁来独立验证**？



读完官方文档了。先说一个**方向性的判断**，它决定了后面所有设计动作：

> **DSH 默认"什么都不共享"，LangGraph 默认"什么都共享"。**
> 所以两者要做的第一件事正好相反 —— DSH 要显式**打开**共享，LangGraph 要显式**切开**共享。

如果你带着 DSH 的思路去用 LangGraph，会觉得"怎么什么都看得见"；带着 LangGraph 的思路去用 DSH，会觉得"怎么什么都得手动传"。**这是默认值的差异，不是能力差异。**

## 一、原语对照表（先建立映射）

| 概念     | LangGraph                           | DSH                              |
| -------- | ----------------------------------- | -------------------------------- |
| 状态载体 | **graph state**（节点间共享）       | 每个 agent 独立的会话日志        |
| 短期记忆 | **checkpointer** + `thread_id`      | 会话日志 + 投影                  |
| 长期记忆 | **store**（跨 thread，namespace）   | 外部记忆 / 跨会话引用 / 日志检索 |
| 消息     | `messages` + `add_messages` reducer | 单一收件箱队列                   |
| 并发写   | **reducer 决定怎么合并**            | 单写者所有权                     |
| 权威判断 | **没有这个概念**                    | 活对象关系（父/子边）            |
| 交付语义 | 状态快照重放                        | 至少一次 + 去重                  |
| 版本演进 | **没有内置**                        | 格式版本 + 相邻迁移链            |

看最后三行 —— **权威、交付、版本，LangGraph 都不给**。这三样恰好是多智能体最容易出事的地方，所以都得你自己补。

---

## 二、状态设计：把"模型要读的"和"代码要用的"分开

LangGraph 的 state 是一个字典，什么都能塞 —— 这就是问题所在。建议按**四个去处**分：

| 去处                 | 放什么                         | 判断标准               |
| -------------------- | ------------------------------ | ---------------------- |
| **`messages`**       | 模型要**逐字读**的对话         | 不读它就做不了决策     |
| **state 的普通字段** | 节点之间要**流转**的结构化数据 | 代码要用，模型不一定看 |
| **store**            | 要**跨会话**活着的长期事实     | 换一个 thread 还得在   |
| **节点内部**         | 中间计算结果                   | 出了这个节点就没用     |

**最关键的一条规则**：**不要把大块结构化数据塞进 state**。因为每走一步都会做一个 checkpoint，state 越大，每个 checkpoint 越大、越慢、越贵。这和 DSH 里"上下文是最贵的资源"是同一个道理，只是一个花 token，一个花存储和延迟。

---

## 三、reducer 是 LangGraph 的核心，也是最容易埋雷的地方

共享 state 意味着**多个节点可能同时写同一个 key**。reducer 就是"并发写怎么合并"的规则。

- `add_messages` 是消息的 reducer：追加、按 id 去重或更新；
- 其他 key 默认是**覆盖**语义。

**你要为每个 key 做一个明确决定**：

| 这个 key 是…                   | 用什么 reducer               |
| ------------------------------ | ---------------------------- |
| 累积型（消息、日志、发现列表） | 追加/合并 reducer            |
| 覆盖型（当前状态、当前负责人） | 默认覆盖，但要能接受"后写赢" |
| 计数/投票型                    | 自定义 reducer               |

**反模式**（很常见）：所有 key 都用默认覆盖，然后靠"节点按顺序执行"来保证正确。这在单线图里能跑，**一旦引入并行边或 fan-out 就立刻崩** —— 两个分支同时写 `result`，先跑的会被后跑的覆盖掉，而且不报错。

> 对照 DSH：那边用"单写者所有权"直接消除了这个问题；LangGraph 用 reducer 让你**显式回答**这个问题。两条路都对，但 LangGraph 这条路要求你**每个 key 都想一遍**。

---

## 四、消息设计：这里是最大的陷阱

**共享 `messages` 意味着每个 agent 都看到全部消息。** 三个后果：

1. **token 成本线性膨胀** —— agent 越多，每个 agent 的输入越大；
2. **互相污染** —— A 的中间输出会进入 B 的上下文，B 可能对无关内容做出反应；
3. **子图的消息不一定回传父图** —— 官方文档明确写了：**每个子图管理自己的 checkpoint namespace**，父图不会立刻看到子图的改动。

### 三种处方，按隔离强度递增

| 做法                                  | 隔离程度 | 说明                                                     |
| ------------------------------------- | -------- | -------------------------------------------------------- |
| 共享一个 `messages`                   | 无       | 只适合 agent 很少、且真的需要互相看                      |
| **每个 agent 一个消息子键**           | 中       | 如 `state["researcher_messages"]`，各自 trim，汇总时再合 |
| **一个 agent 一个子图 + 独立 thread** | 强       | 通过 store 或显式 handoff 传结论                         |

**推荐默认**：**子图 + 独立 thread**，只在父图保留"汇总后的消息"。这就是 DSH 里"把子代理当上下文防火墙"的等价做法 —— 让一个 agent 去读 20 个文档、只把结论带回来。

> 注意官方那条坑：子图改 state，**父图可能看不到**。要么用 store 跨图传数据，要么显式配置让它写父图的 checkpoint。**别指望它自动同步。**

---

## 五、记忆分层：对照 DSH 的四道闸门逐个落地

| 闸门                        | DSH                        | LangGraph 里怎么做                                           |
| --------------------------- | -------------------------- | ------------------------------------------------------------ |
| **1. 裁剪**（不发模型调用） | 工具结果超长截头尾         | `trim_messages` / `filter_messages`，最好做成**一个节点**    |
| **2. 压缩**（要模型调用）   | 阈值触发摘要替换           | summary memory —— 但**要你自己加节点**，LangGraph 不会自动帮你压 |
| **3. 外存**                 | 大结果挪出上下文，只留路径 | 大结果写文件或写 store，消息里只放引用                       |
| **4. 跨会话**               | 引用快照 / 检索 / 外部记忆 | **store**（namespace + key）就是正牌方案                     |

**最需要提醒的一点**：LangGraph 的"压缩"**不是自动的**。DSH 是按上下文比例自动触发，LangGraph 里你得自己在图里加一个"检查长度 → 生成摘要 → 替换消息"的节点，并且想清楚**在哪条边上触发**。不加，它就是无限增长，直到你的模型报上下文超限。

---

## 六、权威与安全：LangGraph 完全不提供，必须自己建

这是我认为**最需要补**的一块。LangGraph 里没有"谁有权给谁发消息"的概念 —— handoff 工具本质上是**让模型自己决定把控制权交给谁**。

**这意味着 handoff 是一个提示注入面**：只要上下文里出现了能被诱导的内容（用户输入、外部文档、工具结果、另一个 agent 的输出），模型就可能被引导切换到不该切的目标。

### 四条要自己加的规则

1. **handoff 目标白名单化** —— 不是"模型说切给谁就切给谁"，而是"只允许在预定义的边集合里切"（对应 DSH 的"只允许直接父子边，兄弟和隔代一律拒绝"）。
2. **权限判断绝不看消息字段** —— 消息里写的 `sender` 只能用于追溯和展示，不能作为授权依据。
3. **节点入口做显式授权检查** —— 每个 agent 节点进来先问"这个身份、在这个位置，允许做这件事吗"。
4. **外部内容一律当不可信背景** —— 从 store 取回来的、从别的 agent 传来的、从文件读来的内容，都要在提示里明确标注"这是资料不是指令"（DSH 的跨会话引用就带一条固定警告）。

---

## 七、副作用与恢复：checkpointer 不是消息队列

两个容易混淆的概念要分开：

- **checkpointer 保证的是"状态能恢复"**，不是"消息只被处理一次"。
- 节点执行到一半失败会**重放**（官方概念里的 pending writes），所以**节点必须可重入**。

**处方**：

- 所有外部副作用（发邮件、写外部系统、调付费接口）配一个**幂等键**；
- 别把"已发送"记在节点的局部变量里 —— 重放就没了，要记在 state 或 store 里；
- **长会话要加 checkpoint 保留策略** —— 官方文档把"checkpoint 无限增长"直接列为常见问题，建议加定时清理。

---

## 八、拓扑选择直接决定记忆设计

| 拓扑                       | 记忆特征                            | 什么时候选             |
| -------------------------- | ----------------------------------- | ---------------------- |
| **Supervisor（中心调度）** | 一份中心 state，子 agent 通常无状态 | 任务分派清晰、要可控   |
| **Swarm（互相 handoff）**  | 共享 messages，agent 直接切换       | 对话式协作、要灵活     |
| **Hierarchical（子图）**   | 每个子图独立 state/thread           | **要上下文隔离时首选** |

**一句话**：**想要上下文干净，就用子图；想要省事，就用 swarm —— 但要知道 swarm 是上下文膨胀最快的那个。**

---

## 九、版本演进：也要自己补

state 的 schema 改了，**旧的 checkpoint 可能读不出来**。LangGraph 没有内置的格式迁移机制。

**最小做法**：state 里放一个 `schema_version` 字段，节点入口（或图入口）做一个迁移函数。

> 对照 DSH：那边有格式版本号、相邻迁移链、已提交代际永不覆盖的硬规则。你在 LangGraph 里至少要做到"**能识别旧版本并明确报错或迁移**"，绝不能静默按新 schema 解析旧状态。

## 十、落成检查清单（LangGraph 版）

1. 每个 state key 的 **reducer 语义**是刻意的吗？（追加 / 覆盖 / 合并）
2. `messages` 是**共享一份**还是**每个 agent 一份**？为什么？
3. 子图的改动，**父图怎么拿到**？（store？显式写父 checkpoint？）
4. 有没有**自动的**长度控制节点？还是指望模型不超限？
5. 哪些数据放 **store**（跨会话），哪些放 **state**（本会话）？分对了吗？
6. handoff 的目标是**白名单**吗？模型能切到不该切的地方吗？
7. 节点可重入吗？副作用有**幂等键**吗？
8. checkpoint 有**保留策略**吗？
9. state 有**版本字段**吗？旧 checkpoint 会怎么处理？
10. 哪个 agent 的输出被**独立验证**了？还是全靠自我报告？

---

**一句话总结**：LangGraph 给你的是**一张可持久化的执行图 + 一套状态容器** —— 编排能力很强，但**记忆分层、边界、权威、交付语义全都要你自己设计**。DSH 那套"五条边界"在这里依然适用，只是每一条你都得亲手实现。
