## 1. 数据库设计误区

### 1.1 ❌ UNIQUE 约束含 captured_at 导致重复入库

**问题**：
```sql
UNIQUE (source, source_id, captured_at)  -- 同一记录每次抓取一行快照
```

**设计意图**：时序快照——同一 source_id 每次抓取 INSERT 新行，保留字段变化历史（如能效等级从 E 升到 A）。

**实际误区**：`captured_at` 精度到秒，每次抓取时间不同，所以 UNIQUE 约束**永远不会触发**。同一 source_id 可以无限重复 INSERT，导致数据库膨胀。实际运行中 ANATEL 出现了 2454 条重复。

**修复**：`compintel_db.py` 的 `add_record()` 在 INSERT 前先查重：
```python
if not fields.get("_force_update"):
    existing = self.conn.execute(
        "SELECT id FROM compintel_record WHERE source=? AND source_id=? "
        "ORDER BY captured_at DESC LIMIT 1",
        (source, source_id)).fetchone()
    if existing:
        return int(existing["id"])  # 已存在，跳过 INSERT
```

**下一位开发者注意**：
- 如果需要追踪字段变化（如能效等级升级），需设 `_force_update=True` 强制 INSERT 新快照
- 普通抓取（记录未变化）不需要强制更新，`add_record` 会自动跳过
- 定期运行 `dedup_records.py` 清理历史残留重复

### 1.2 ❌ source CHECK 约束需手动迁移

**问题**：`schema.sql` v8 只有 `('fcc','eprel')`，v9 扩展到 7 个源。但 `CREATE TABLE IF NOT EXISTS` 不会修改已有表的 CHECK 约束。

**修复**：`db.py` 第222行的 `_migrate_compintel_source_check()` 方法重建表扩展 CHECK：
```python
def _migrate_compintel_source_check(self):
    """v8→v9: 扩展 compintel_record / compintel_alert 的 source CHECK 约束。"""
    for table in ("compintel_record", "compintel_alert"):
        # 检查当前 CHECK 是否含新 source
        # 如果不含，重建表（CREATE NEW → INSERT SELECT → DROP OLD → RENAME）
```

**下一位开发者注意**：新增数据源时，必须同时更新 `schema.sql` 的 CHECK 约束，且确保 `_migrate_compintel_source_check()` 能处理旧库迁移。

### 1.3 ❌ product 表跨模块耦合

**问题**：`detect_launch_warning` 中的 `_is_on_market()` 查 `product` 表判断竞品是否在售。但 `product` 表属于海外采集框架（电商爬虫），不是竞品情报系统的表。

**影响**：如果部署环境没有海外采集框架的数据，`product` 表为空，`_is_on_market` 恒返回 False，所有新认证都会被判定为"尚未在售"，生成大量 launch_warning。

**设计决策**：这是有意为之——在售判断只是辅助过滤，宁可多预警不漏预警。FCC 认证 ≠ 在售，不能靠"品牌在 product 表有记录"判定（那会把所有竞品品牌的新认证都误判为已售）。

**下一位开发者注意**：
- `_is_on_market` 只在 `source_id` 本身出现在 product 表的 model 字段时才算在售（极少见）
- 不要改成"品牌在 product 表有记录就算在售"——这会误杀所有预警
- 如果不需要在售过滤，可跳过步骤2（但会增多噪声信号）

## 2. 爬虫开发误区

### 2.1 ❌ ENERGY STAR brand_name 大小写不一致

**问题**：Socrata API 的 `brand_name` 字段大小写不统一——有 "Samsung"、"SAMSUNG"、"SONY" 等。

**错误写法**：
```python
where_parts = [f"brand_name='{brand}'"]  # 精确匹配，大小写敏感
```
这导致搜索 "Samsung" 时漏掉 "SAMSUNG" 的记录，只抓到 22/38 条。

**修复**：
```python
where_parts = [f"upper(brand_name)='{brand.upper()}'"]  # 大小写不敏感
```

**下一位开发者注意**：所有按品牌名查询的 API 都要做大小写不敏感处理。

### 2.2 ❌ IC/ISED 的 licenceDateFrom 参数导致 HTTP 500

**问题**：IC/ISED 的 Spring WebFlow API 有一个 `licenceDateFrom` 参数用于按日期过滤，但实际使用时会导致 HTTP 500（Spring WebFlow 内部错误）。

**错误写法**：
```python
params["licenceDateFrom"] = since  # 触发 500
```

**修复**：删除该 API 参数，改为本地过滤：
```python
# API 不传日期参数，拿到全量后本地过滤
if since:
    recs = [r for r in recs if r.get("auth_date", "") >= since]
```

**下一位开发者注意**：不要尝试给 ISED API 加日期过滤参数，已验证会 500。本地过滤是唯一可行方案。

### 2.3 ❌ EPREL offset 翻页不工作

**问题**：EPREL API 的 `offset` 参数被忽略，不同 offset 返回相同的 25 条记录。大 offset 还会触发 403。

**错误写法**：
```python
for offset in range(0, total, 25):
    recs = api.list(offset=offset)  # 每次返回相同的 25 条！
```

**修复**：用 `supplierOrTrademark` 过滤器按品牌搜索，每个品牌取最新 25 条：
```python
recs, total = crawler.search_by_supplier(supplier, group)
# supplierOrTrademark 改变返回的 25 条，近1年新品出现在 offset=0
```

**下一位开发者注意**：
- EPREL 每个供应商只能拿到最新 25 条，无法翻页获取更多
- 多个子品牌需要多关键词搜索（LG → HELGI/elgato/LG Electronics）
- 如果需要更多历史数据，只能用 `scan_range` 按注册号区间遍历（慢）

### 2.4 ❌ ISED 品牌间需 15 秒延迟

**问题**：ISED API 对快速连续请求返回 500。品牌间切换需等待 15 秒+。

**代码**（`ic_ised_crawler.py` 第388行）：
```python
time.sleep(15)   # ISED 对快速连续请求返回 500,需等 15s+
sub = IcedCrawler(proxy=self.proxy)
```

**下一位开发者注意**：
- ISED 抓取很慢（6 品牌 × 2 公司号 × 15s = 3 分钟+）
- 每个公司号需新建独立 Crawler 实例（execution token 不能复用）
- 近1年电视类仅 2 条，投入产出比最低

### 2.5 ❌ TÜV/VDE 字段缺失是数据源限制

**问题**：TÜV Certipedia 搜索页只返回证书号，没有结构化的 model/auth_date。VDE Solr API 不返回认证日期。

**影响**：
- TÜV 89 条记录的 model 和 auth_date 全空
- VDE 136 条记录的 auth_date 全空
- launch_warning 中 VDE 的 lead_days 显示"提前量未知"

**下一位开发者注意**：这不是 bug，是数据源 API 的限制。如果要补全字段，需逐条抓详情页（TÜV 15s/条，89 条需 22 分钟）。

## 3. 信号检测设计误区

### 3.1 ❌ is_new 标志必须在入库前设置

**问题**：`detect_new_records` 和 `detect_launch_warning` 依赖 `is_new` 标志判断"本次新出现的记录"。如果入库后再查 `seen_source_id`，恒为 True（因为刚插入），所有记录都会被判定为"非新"。

**正确写法**（orchestrator.py）：
```python
is_new = not cidb.seen_source_id("energystar", r["source_id"])  # 入库前查
r["is_new"] = is_new      # 标记到记录 dict
sid = r.pop("source_id")
cidb.add_record(run_id, "energystar", sid, **r)  # 然后才入库
```

**错误写法**：
```python
cidb.add_record(run_id, "energystar", sid, **r)  # 先入库
is_new = not cidb.seen_source_id("energystar", sid)  # 恒为 False！
```

**下一位开发者注意**：新增爬虫编排时，必须遵循"先查 is_new → 标记到 dict → 入库 → 信号检测"的顺序。

### 3.2 ❌ EPREL 近1年新品即使已上市也要预警

**设计决策**：EPREL 的 `market_start` 字段表示上市日期。近1年注册的新品即使 `market_start` 已过（已上市），仍然生成 launch_warning。

**原因**：EPREL 注册到上市通常只差 1-6 个月，近1年注册的都是"新品信号"。如果按其他源的逻辑跳过已上市的，会漏掉大量 EPREL 预警。

**代码**（`alert.py` 第431行）：
```python
if on_market and source != "eprel":
    continue   # 已在售，不是"即将上市"预警
# EPREL 例外：近1年新品即使已上市也生成预警
```

**下一位开发者注意**：不要把这个 EPREL 例外去掉，否则 EPREL 的 launch_warning 会从 53 降到 0。

### 3.3 ❌ 产品类型关键词先排除再匹配

**问题**：FCC description 里有 "TV Remote"（遥控器），含 "tv" 关键词但不是电视。

**设计**：先排除非电视产品（含 remote/charger/phone 等排除词 → return None），再匹配电视关键词。

```python
# 先排除
for ex in EXCLUDE_KEYWORDS:
    if ex in text:
        return None
# 再匹配
for kw in TV_DISPLAY_KEYWORDS:
    if kw in text:
        return kw
```

**下一位开发者注意**：
- `EXCLUDE_KEYWORDS` 的优先级高于 `TV_DISPLAY_KEYWORDS`
- "baby monitor" 含 "monitor" 但被 "baby monitor" 排除词过滤
- 新增关键词时注意排除词的覆盖范围

### 3.4 ❌ 5 个信号检测函数已实现但未启用

**现状**：`alert.py` 有 9 个信号类型，但 `orchestrator.py` 只调用了 `detect_new_records` 和 `detect_launch_warning`。其余 5 个函数（`detect_confidential_expired` / `detect_supplier_change` / `detect_field_changes` / `detect_energy_class_jump` / `detect_delisted`）代码完整但未调用。

**原因**：这些函数需要历史快照对比（需要多次抓取同一 source_id 才能检测变化），当前每次抓取都是全量近1年，没有保留多次快照的机制。

**下一位开发者注意**：启用这些函数前，需确保同一 source_id 会被多次抓取（当前 `add_record` 的防重逻辑会跳过已存在的记录）。设 `_force_update=True` 可强制插入新快照。

## 4. 品牌匹配设计误区

### 4.1 ❌ 子品牌名不匹配导致漏数据

**问题**：各数据源的供应商名不一致，竞品有多个子品牌/收购品牌：

| 标准品牌 | 子品牌/变体 | 数据源 |
|----------|------------|--------|
| LG | HELGI, elgato, LG Electronics | EPREL |
| TCL | THOMSON | EPREL |
| Sony | SONY（全大写） | EPREL / ENERGY STAR |
| TCL | TCL Electronics / TCL Technology / TCL Overseas | FCC |

**修复**：
- EPREL：`EPREL_SUPPLIER_SEARCH` 字典映射品牌到多个搜索关键词
- FCC：`_BRAND_NORMALIZE` 字典把公司名变体归一化为标准品牌名
- ENERGY STAR：`upper(brand_name)` 大小写不敏感

**下一位开发者注意**：
- 新增品牌时，需同时更新 `EPREL_SUPPLIER_SEARCH`（orchestrator.py 第485行）和 `_BRAND_NORMALIZE`（orchestrator.py 第828行）
- `_BRAND_NORMALIZE` 用 `startswith` 匹配，关键词必须从长到短排列（先匹配 "tcl electronics" 再 "tcl"）

### 4.2 ❌ EPREL 两级品牌匹配

**问题**：EPREL 的 `supplier_name` 可能是子品牌（如 THOMSON），`organisation_name` 含集团名（如 TCL Operations）。只用 `supplier_name` 匹配会漏掉 THOMSON → TCL 的关联。

**设计**（`orchestrator.py` `_eprel_to_db_dict` 第885行）：两级匹配：
1. 先用 `supplier_name` 匹配 → 如果匹配到标准品牌，直接用
2. 如果 `supplier_name` 未匹配，再用 `organisation_name` 匹配

```python
brand = _normalize_brand(rec.supplier_name or "")
if brand == (rec.supplier_name or "") and rec.organisation_name:
    # supplier_name 未匹配到标准品牌，尝试 organisation_name
    org_brand = _normalize_brand(rec.organisation_name)
    if org_brand != rec.organisation_name:
        brand = org_brand
```

**下一位开发者注意**：新增 EPREL 子品牌时，可能需要在 `_BRAND_NORMALIZE` 中加入子品牌名（如 "thomson" → "TCL"）。

## 5. 时间处理误区

### 5.1 ❌ --since 默认空字符串 = 抓全量历史

**问题**：CLI 的 `--since` 参数默认空字符串，如果直接传给爬虫，空字符串不做时间过滤，导致抓取全量历史数据（可能几万条）。

**修复**：`compintel_cli.py` 的 `_parse_since` 函数默认近 365 天：
```python
def _parse_since(args, default_days=365):
    if getattr(args, "since", ""):
        return args.since
    from datetime import datetime, timedelta
    return (datetime.utcnow() - timedelta(days=default_days)).strftime("%Y-%m-%d")
```

**下一位开发者注意**：
- 不传 `--since` → 自动用近 365 天
- 传 `--since 2026-01-01` → 从 2026-01-01 开始
- 传 `--since 1900-01-01` → 抓全量历史
- **不要**把空字符串直接传给爬虫

### 5.2 ❌ EPREL 时区 vs UTC naive 比较

**问题**：EPREL 的 `market_start` 是 ISO 格式带时区（如 `2026-03-04T00:00:00+01:00`），而 `datetime.utcnow()` 是 offset-naive。直接相减会报 `TypeError: can't compare offset-naive and offset-aware datetimes`。

**修复**（`alert.py` `_is_on_market` 第380行）：
```python
d_naive = d.replace(tzinfo=None) if d.tzinfo else d
return d_naive <= datetime.utcnow()
```

**下一位开发者注意**：所有日期比较前，必须统一为 offset-naive UTC。`_parse_date` 用 `datetime.fromisoformat` 解析，带 Z 的转为 +00:00。

### 5.3 ❌ crawl_all_extended 的 sources 参数用 "certs" 不是 "tuv_ul"

**问题**：`crawl_all_extended` 的 `sources` 参数中，TÜV+VDE 对应的键是 `"certs"` 而非 `"tuv_ul"`。

```python
sources = sources or ["energystar", "anatel", "ic_ised", "certs", "eprel"]
#                                                          ↑ 是 "certs"
```

**下一位开发者注意**：CLI 传 `--sources` 时要用 `certs`，不是 `tuv_ul` 或 `tuv`。

## 6. 代理与网络误区

### 6.1 ❌ 抓取海外 API 必须走 OVERSEAS_PROXY

**问题**：FCC/EPREL/ENERGY STAR/ANATEL/IC-ISED 等海外 API 在中国直连不可达，必须走出口代理。

**设置**：
```bash
$env:OVERSEAS_PROXY = "http://127.0.0.1:7877"
```

**下一位开发者注意**：
- 代理端口需替换为实际代理端口
- 看板浏览（Web API）不需要代理，只有抓取需要
- 如果代理不可用，抓取会失败但看板仍可正常浏览已有数据

### 6.2 ❌ ISED 需新建独立 Crawler 实例

**问题**：ISED 的 Spring WebFlow 表单搜索依赖 `execution` token + Cookie。每个公司号的搜索需新建独立 Crawler 实例，不能复用。

**代码**（`ic_ised_crawler.py` 第389行）：
```python
for num in company_nums:
    time.sleep(15)
    sub = IcedCrawler(proxy=self.proxy)  # 每次新建！
    recs = sub.search_rel(company_number=num, ...)
```

**下一位开发者注意**：不要尝试复用 IcedCrawler 实例，execution token 会过期导致 500。

## 7. LLM 调用误区

### 7.1 ❌ openai 库会缓存代理配置

**问题**：`openai` 库底层用 `httpx`，在构造 client 时就缓存代理配置。事后改环境变量无效。

**修复**（`llm_analyze.py` 第62-78行）：
```python
# ① 先改环境（必须在建 client 前）
for k in proxy_keys:
    os.environ[k] = ""
os.environ["NO_PROXY"] = "inner-apisix.hisense.com,..."

# ② 再建 client（此时读到的是无代理配置）
client, cfg = _get_client(model)

# ③ 调用完后恢复环境变量
```

**下一位开发者注意**：
- LLM 调用走海信内网（`inner-apisix.hisense.com`），不走 `OVERSEAS_PROXY`
- 必须在创建 client 前清空 `HTTP_PROXY/HTTPS_PROXY` 并设 `NO_PROXY`
- 调用完后必须恢复环境变量（finally 块）

### 7.2 ❌ LLM 不通时必须优雅降级

**设计**：LLM 调用失败（网络错误/内网不可达）时返回空字符串，调用方降级为规则式摘要，不抛异常不阻塞。

```python
except Exception:
    return ""  # 静默失败，返回空字符串让调用方降级
```

**下一位开发者注意**：
- 不要在 LLM 调用处抛异常，会导致整个 API 请求 500
- 外部部署时，LLM 不可用是常态，系统必须在无 LLM 时正常工作
- 如需替换模型，修改 `MODEL_CONFIGS` 字典的 `base_url` 和 `api_key`

## 8. 核心设计思路

### 8.1 时序快照设计

**决策**：每次抓取 INSERT 新行，而非 UPDATE 已有行。

**理由**：
- 保留字段变化历史（如能效等级从 E → A 的升级轨迹）
- 支持变化检测信号（`detect_field_changes` / `detect_energy_class_jump`）
- `last_record()` 取最新快照，`history()` 取全部历史

**代价**：数据量增长快（需定期去重），`add_record` 需查重防止重复。

### 8.2 上市预警四步过滤

**决策**：在基础 `new_*` 信号之上叠加业务过滤，只留真正"新产品即将上市"的信号。

```
new_fcc_id/new_cert/eprel_new_reg  →  大量噪声（含手机/家电/路由器等）
    ↓ 步骤1: 产品类型过滤（TV/display 关键词匹配）
    ↓ 步骤2: 在售状态比对（已上市不预警，EPREL 例外）
    ↓ 步骤3: 提前量计算（认证日期距今天数）
    ↓ 步骤4: 产出 launch_warning
launch_warning  →  真正可用的上市预警（仅电视/显示器类新品）
```

**理由**：直接用 `new_fcc_id` 信号会包含大量噪声（手机/遥控器/可穿戴等），无法直接用于上市预警。四步过滤把 980 条信号精炼为 129 条上市预警。

### 8.3 零第三方依赖

**决策**：核心模块仅用 Python 标准库（`urllib`/`http.server`/`sqlite3`/`argparse`），不引入 requests/Flask/SQLAlchemy 等。

**理由**：
- 部署简单（无需 `pip install`，只需 Python 3.10+）
- 内网环境可能无法 pip install
- 减少依赖冲突风险

**代价**：代码量略多（urllib 比 requests 啰嗦），功能受限（无 async/中间件）。

### 8.4 品牌标准化两级匹配

**决策**：所有数据源的供应商名/公司名都归一化为 6 个标准品牌名（Samsung/LG/Hisense/TCL/Sony/Panasonic）。

**理由**：
- 按竞品聚合统计（如"Samsung 有多少预警"而非"Samsung Electronics + Samsung"）
- 子品牌/收购品牌关联（THOMSON → TCL，HELGI → LG）
- 跨数据源品牌名统一

**实现**：
- `_BRAND_NORMALIZE` 字典：公司名变体 → 标准品牌名（startswith 匹配，从长到短）
- EPREL 两级匹配：先 supplier_name，未匹配再 organisation_name

### 8.5 编排器统一模式

**决策**：所有 7 个 `crawl_*` 函数遵循统一模式（创建爬虫 → start_run → 抓取 → 落库 → 信号检测 → finish_run）。

**理由**：
- 代码结构一致，易于维护和扩展
- 信号检测逻辑集中（都调 `detect_new_records` + `detect_launch_warning`）
- 批次审计统一（都记到 `crawl_run` 表）

### 8.6 防"缺价 > 错价"原则

**决策**：宁可留空不造假。认证日期缺失就显示"?"，提前量无法计算就显示"提前量未知"。

**理由**：预警系统的核心价值是准确性。错误的提前量/在售状态比没有更危险。
