## 附录 A：Playwright + 本机 Edge 与登录（工程细节）

> 核心一句话：**我们不是在"用 Playwright 抓网页"，我们是在"让程序扮演一个可信的真实浏览器用户"。**

### A.1 为什么是 Playwright + 本机已装 Edge

| 决策                                      | 理由                                                         |
| ----------------------------------------- | ------------------------------------------------------------ |
| 用 **Playwright** 而不是 Selenium         | 同步 API 干净；`add_init_script` / `storage_state` / `launch_persistent_context` 刚好是我们要的 |
| 用 **本机已装 Edge** 而不是下载 Chromium  | ① 免下载（服务器还访问不了 Playwright CDN）② **真实浏览器指纹** ③ 企业环境本来就有 |
| 用 **`channel`** 而不是 `executable_path` | `channel="msedge"` 按官方通道启动，UA / 特性标志与真实 Edge 对齐 |

**配置是一个"通道兜底链"**：

```python
BROWSER_EXECUTABLE = (os.environ.get("OVERSEAS_BROWSER_EXECUTABLE") or "").strip()
# 未指定离线路径时按顺序尝试系统通道（Windows 本机通常有 msedge）
BROWSER_CHANNELS = [
    c.strip() for c in
    (os.environ.get("OVERSEAS_BROWSER_CHANNELS") or "msedge,chrome,chromium").split(",")
    if c.strip()
]
```

- **本机（Windows）**：不设 `BROWSER_EXECUTABLE` → 依次试 `msedge` → `chrome` → `chromium`
- **服务器（Linux）**：`OVERSEAS_BROWSER_EXECUTABLE=/opt/chrome-linux64/chrome`
  （服务器**访问不了 Playwright CDN**，只能用仓库里的离线 Chrome）

> 这个兜底链是**换机器不用改代码**的关键：同一份代码，本机用 Edge、服务器用离线 Chrome。

### A.2 启动参数：每一行都在解决一个具体问题

```python
BROWSER_ARGS = [
    "--disable-blink-features=AutomationControlled",   # ★ 去掉最强的自动化特征
    "--no-sandbox",                                     # ★ Linux 无头必须，否则静默卡死
    "--disable-dev-shm-usage",                          # 容器 /dev/shm 太小导致崩溃
    "--disable-gpu",                                    # 服务器没有 GPU
]
```

外加一层 **JS 补丁**（每次新建 context 时注入）：

```python
self._ctx.add_init_script(
    "Object.defineProperty(navigator,'webdriver',{get:()=>undefined})")
```

| 手段                                            | 挡掉什么检测                                           |
| ----------------------------------------------- | ------------------------------------------------------ |
| `--disable-blink-features=AutomationControlled` | Chrome 启动时就带上的自动化标志位                      |
| `navigator.webdriver = undefined`               | 页面 JS 里最常见的 `navigator.webdriver === true` 判断 |
| `channel=msedge`                                | UA / 客户端提示与真实 Edge 一致                        |
| `locale=en-CA`、`viewport 1440x900`             | 与目标站点地区、常见桌面分辨率一致                     |

> **注意诚实态度**：这些只能过**"轻中度"**检测。
> Cloudflare、PerimeterX 这类强挑战不是靠参数能过的。

### A.3 两条上下文路径：`storage_state` vs **持久化 profile**（最重要）

|            | `storage_state`（早期）                     | **持久化 profile（现用）**                              |
| ---------- | ------------------------------------------- | ------------------------------------------------------- |
| API        | `browser.new_context(storage_state=...)`    | `chromium.launch_persistent_context(user_data_dir=...)` |
| 本质       | 一份 cookie + localStorage 的 **JSON 快照** | **真实 Chromium 用户目录**                              |
| 反爬信任度 | 一般（仍是新建 context，自动化指纹明显）    | **高**（真实目录、真实 profile）                        |
| 登录稳定性 | 一般                                        | **登录一次，长期复用**                                  |
| 隔离粒度   | 按站点一份 `.json`                          | 按站点一个**目录**                                      |

源码注释原话：

> 与 storage_state 的区别：profile 是真实 Chromium 用户目录，反爬系统更信任，
> 登录态也更稳。用 `launch_persistent_context` 打开后，登录一次即可长期复用。

配置里留下的实测结论：

> **为何必须用 `--profile`**：临时 context 的自动化指纹拿不到登录凭证；
> 持久化真实用户目录（`launch_persistent_context` + msedge 通道）才能登录成功。

> **同样是"存 cookie"，`storage_state` 和持久化 profile 在反爬眼里是两个人。**
> 前者是"一个带着 cookie 的机器人"，后者是"一台用过的电脑"。

### A.4 三级降级链

```
① profile_dir 存在？
     → launch_persistent_context(user_data_dir + channel + args + proxy)
     成功 → 完成（profile 自带登录态）

     失败（最典型：profile 被其它进程占用）
     → [WARN] 持久化 profile 打开失败，回退临时上下文：<异常类型>
     → 继续走 ②

② 有 BROWSER_EXECUTABLE？
     → chromium.launch(executable_path=...)           # 服务器离线 Chrome
   否则按 BROWSER_CHANNELS 依次 try：msedge → chrome → chromium
     任一成功 → 完成

③ 全部失败
     → raise RuntimeError("无法启动浏览器（试过 <列表>）：<最后一个异常>")
```

**两条"不让小事炸掉整条链"的设计**：

1. **坏 `state.json` 不阻断抓取**：缺失/损坏 → **静默降级为无状态抓取**
2. **登录态回写保护**：本次会话**命中过登录墙就拒绝回写 state**
   （匿名抓取同样有一堆 cookie，存下来会污染登录态并使状态检查误报）

### A.5 浏览器复用与统一 Dom 接口

**（1）一个 Fetcher 复用一个浏览器**：`_ensure()` 懒加载，不是每个 URL 开一个浏览器。
理由：浏览器启动是**秒级**成本；而且**真实用户不会翻一页就重启一次浏览器**。

**（2）上层不关心"页面怎么拿到"**：`HttpFetcher` 和 `BrowserFetcher` 实现同一个 `Dom` 接口
（`content()` / `eval_js()` / `wait_selector()` / 滚动与等待）。

**收益**：同一个抽取器对两种取数方式都能用 → **站点可以按防护等级"升级"取数方式，
而不是重写一遍解析逻辑**。

### A.6 什么时候必须上浏览器

| 等级 | 含义   | Fetcher                    | 本次实测                       |
| ---- | ------ | -------------------------- | ------------------------------ |
| L1   | 温和   | HTTP 即可                  | Samsung / TCL / Philips（200） |
| L2   | 中等   | **需真实浏览器**           | LG / Sony（403 Access Denied） |
| L3   | 强防护 | 浏览器 + 低频 + 可能需代理 | Amazon / Walmart / BestBuy     |

**必须上浏览器的四类情形**：① L2/L3 站点；② 需要 JS 渲染；
③ 需要登录态；④ **需要在页面上下文里 fetch 接口**。

第 ④ 条是被踩出来的：**同一页面在上下文内调用可得 30 个候选，站点解析器 0 候选**。
**生产抓取本来就是在上下文内解析，工具必须对齐。**

### A.7 登录：能解决的 9 条

| #    | 问题                                   | 解法                                                         |
| ---- | -------------------------------------- | ------------------------------------------------------------ |
| 1    | 临时 context 拿不到登录凭证            | 持久化 profile + `channel=msedge`                            |
| 2    | 每次采集都要重新登录                   | profile 一次登录、长期复用                                   |
| 3    | 国别 cookie 名不同导致误判未登录       | 前缀匹配 `at-` / `sess-at-` / `x-`（只认某一国会**实测连错 3 次**） |
| 4    | 没勾"保持登录"就漏判                   | **分级判据**：凭证 cookie 直接判成功；否则要求"离开登录页 + 静置 5 秒 + 只读 DOM 出现 Sign Out" |
| 5    | 拿订单历史页当判据（登出态也有该链接） | 改用 **Sign Out**，并**排除** `Hello, sign in` 文案          |
| 6    | 登录墙被误判为反爬 → 熔断静默全跳过    | `not_logged_in` 单独归因，**豁免熔断**，打印修复命令         |
| 7    | 匿名 cookie 污染登录态                 | 命中过登录墙就**不回写** state                               |
| 8    | 一个坏 `state.json` 阻断整条链         | 缺失/损坏 → **静默降级为无状态抓取**                         |
| 9    | 登录校验**刷掉用户正在填的表单**       | 改**全被动**：不 reload、不新开页、不跳深层页                |

**被动登录的三条硬规则**（来自三次踩坑）：

```
1) 登录全过程只打开一次页面：不新开标签页
   （新标签会抢前台，让用户正在登录的页面"消失"＝闪退）
2) 绝不导航到需要登录的深层页：未登录时它必然 302 到登录页，
   用户会直接看到登录墙
3) 判定顺序：先看 cookie，再用页眉的 Sign Out 做二次确认
   （reload 同一页，不换页）
```

**登录命令**：

```powershell
# 查看登录态
& $py -m overseas.cli login-status
# 登录（必须加 --profile）
& $py -u -m overseas.cli login --site amazon_us --profile --url 'https://www.amazon.com/'
# --keep-open 默认保留窗口 120 秒，避免"刚登录完窗口就消失"
```

**权威判据**（不是看用户名）：账号订单历史页**不跳登录页** ⇒ 真登录。

### A.8 登录：不能解决的 8 条

| #    | 做不到的事                          | 为什么                            | 处置                                                   |
| ---- | ----------------------------------- | --------------------------------- | ------------------------------------------------------ |
| 1    | 需登录才显示的价格（会员价/选仓价） | 业务规则 + 账号权限，不是技术问题 | 明确列为**不自动处理**；缺价留空，**不用别的字段硬凑** |
| 2    | 加购后才显示的价格                  | 需要交互式决策                    | `needs_human` 止损，交人工                             |
| 3    | 验证码                              | 设计上就是给人做的                | 命中即标记需人工，不硬解                               |
| 4    | Cloudflare / PerimeterX 强挑战      | IP + 指纹 + 行为的综合判定        | 明确挑战标记命中即判拦，**换线路是唯一出路**           |
| 5    | **IP 层封锁（403）**                | ★ **登录态对它完全无效**          | 换线路                                                 |
| 6    | 平台服务端硬上限                    | 站点策略                          | 如实标注"该平台仅开放首屏"                             |
| 7    | profile 被并发占用                  | 用户目录是独占资源                | 只能**串行**：同站一个进程                             |
| 8    | 会话过期自动续期                    | 我们不存账号密码（也不该存）      | 被动检测 + 提示重登                                    |

**第 5 条的实测证据**（最值得强调）：

| 场景                                              | 结果                                                   |
| ------------------------------------------------- | ------------------------------------------------------ |
| 真实浏览器：首页 → 搜索（同一 context 带 cookie） | `blocked=True reason=marker:robot or human` / 16,963 B |
| 真实浏览器：首页 → 商品页（同一 context）         | `blocked=True` / 同样 16,963 B                         |
| curl 直连首页                                     | 同样被拦                                               |

### A.9 浏览器相关的实战坑清单

| 现象                                     | 根因                                      | 处置                                                         |
| ---------------------------------------- | ----------------------------------------- | ------------------------------------------------------------ |
| Playwright 安装失败                      | 上次中断留下 `__dirlock` **孤儿锁**       | 清掉 `__dirlock` 再装                                        |
| `持久化 profile 打开失败…回退临时上下文` | profile 是**独占锁**，同站拆 2 进程会撞锁 | **同站只跑一个进程**；杀掉残留浏览器进程                     |
| 浏览器静默卡死                           | Linux 无头缺 `--no-sandbox`               | 已在启动参数预置                                             |
| 服务器起服务参数被裁剪                   | CLI 参数不全                              | 用 `--config` JSON 起服务                                    |
| 服务器装不了浏览器                       | 访问不了 Playwright CDN                   | 仓库内离线 Chrome + 环境变量指定路径                         |
| 想在服务器上调试浏览器                   | 服务器无显示器/难直连                     | **SSH 隧道**：`ssh -N -L 9333:127.0.0.1:9333`，"本地驱动、服务器执行" |

## 附录 B：Crawl4AI 架构与能力

> 只讲最值得讲的。重点不是"它有什么功能"，
> 而是**它把哪些我们踩过的坑做成了通用能力**，以及**我们为什么不直接用、却拿了什么**。

### B.1 它是什么

> Crawl4AI turns the web into clean, LLM ready Markdown for RAG, agents, and data pipelines.

- 定位：**面向 LLM 的网页爬取框架**（GitHub 5 万+ star，Python，async 优先）
- 理念："零 Key、可自部署"——CLI + Docker
- 风格：**配置驱动**（浏览器级配置 / 单次运行级配置分层）

### B.2 架构一眼看懂

```
AsyncWebCrawler          ← 唯一入口
      │
      ├── BrowserConfig       浏览器级：headless / channel / proxy / user_data_dir / CDP
      ├── CrawlerRunConfig    单次运行级：缓存 / JS / 等待 / 抽取 / 滚动 / 截图
      │
      ├── BrowserManager      浏览器池、页面复用、CDP 连接缓存
      ├── CrawlerStrategy     页面级策略：导航、JS 执行、等待、hooks、截图/PDF
      │
      ├── Dispatcher          并发调度：RateLimiter + MemoryAdaptiveDispatcher
      │
      ├── 处理链（可插拔）
      │     content_filter_strategy     剪枝 / BM25 内容过滤
      │     markdown_generation_strategy raw / fit markdown 生成
      │     extraction_strategy         LLM / CSS / JSON-CSS 抽取
      │
      └── CrawlResult         统一结果对象
```

**模块地图（相关的部分）**：

| 模块                                          | 作用                                                         |
| --------------------------------------------- | ------------------------------------------------------------ |
| `hub.py`                                      | **外部插件自动发现** ← 我们借鉴的就是这个模式                |
| `async_dispatcher.py`                         | `RateLimiter`（按域名 + 状态码退避）、`MemoryAdaptiveDispatcher` |
| `deep_crawling/`                              | BFS / DFS / BestFirst + filters + scorers，含 `resume_state` 崩溃恢复 |
| `adaptive_crawler.py`                         | 自适应爬取（覆盖率 / 一致性 / 饱和度打分）                   |
| `antibot_detector.py` / `browser_profiler.py` | 反爬检测 / 浏览器指纹画像                                    |
| `cache_context.py`                            | 缓存三档：`read_write` / `read_only` / `bypass`              |
| `script/c4a_script.py`                        | **c4a-script**：一套可编译的脚本语言（不是裸 JS）            |

### B.3 最值得讲的 5 个能力（按对我们的价值排序）

#### ① `generate_schema` —— LLM 产 schema，抽取走高速引擎 ★★★

给一个**真实样本页 HTML** + 自然语言查询 → **一次性**生成稳定的抽取 schema；
之后抽取全部走高速引擎，**不再调 LLM**。

**这就是我们整个项目的路线**：LLM 只产配置、不产代码。

**我们改进的一点**：让生成器**直接吃真实型号页 HTML 样本**，而不是只吃人工摘要的探测报告，
选择器更贴合实际 DOM；同时保留我们的优势——生成的配置要过**守恒校验与字段校验**才能入库。

> 这条是"英雄所见略同"。我们把整个架构押在"LLM 只产配置"上，
> 后来读它源码发现它最高价值的也是这一条——**这条路是被验证过的。**

#### ② `preprocess_html_for_schema`：重复卡片去重 ★★★（我们直接拿来用了）

- **列表页 N 个同构产品卡 → 只留 1 个样例** 再喂 LLM
- 效果（我们的实测回归）：1200 个重复导航卡被压成 1 个，
  **112K → 418 字符，且页尾关键元素 4/4 保留**（旧版截断 30K，关键元素 0/4）

**但必须讲清楚它的边界（我们踩过的负面结果）**：

| 喂法                        | 结果                                                         |
| --------------------------- | ------------------------------------------------------------ |
| A 原始 HTML（内部截断 30K） | **94 分 PASS，2 轮收敛**                                     |
| B 简单整页压缩后再喂        | **0 分 FAIL**——压缩破坏了 `id`/`class` 线索，LLM 只能生成 `h1` / `.price` 这类通用猜测 |

**结论**：它给的是**"地图"**，不是**"施工面"**。
适合**定位阶段**，不能替代"用原始 DOM 片段生成精确选择器"。

> **好工具用错阶段，效果是负的。**

#### ③ `VirtualScroll` —— 把"滚动"分成三种语义 ★★★（和我们撞在同一个问题上）

| 场景                 | 含义                                        | 是否需要特殊处理   |
| -------------------- | ------------------------------------------- | ------------------ |
| **No Change**        | 滚动后内容不变（静态页或已到底）            | 否                 |
| **Content Appended** | 新内容**追加**（传统无限滚动）              | 否（DOM 自然增长） |
| **Content Replaced** | 内容被**替换**（真·虚拟滚动，DOM 大小恒定） | **是**             |

原文：

> Traditional infinite scroll **appends** new content to existing content.
> Virtual scroll **replaces** content to maintain performance.
> Without proper handling, crawlers only capture the currently visible items, **missing the rest**.

**★ 关键对照**：我们项目里那个"**替换式分页**"，就是同一类问题。

|          | Crawl4AI              | 本项目                                         |
| -------- | --------------------- | ---------------------------------------------- |
| 触发方式 | 滚动                  | 点击编号页码                                   |
| 行为     | 替换 DOM 内容         | 替换当前页产品卡（**不是追加**）               |
| 后果     | 只抓到当前可见项      | 只抓到首屏 **12/25**                           |
| 解法     | `VirtualScrollConfig` | 每次翻页后**重扫页码** + 累积到连续 2 轮不增长 |

> 这条我特别想讲，因为它说明**我们遇到的问题不是"我们运气差"**。
> 一个 5 万星的框架专门为它做了一个功能模块，
> 说明"**渲染式替换**"是一类**普遍存在的页面形态**。我们的坑是有名字的。

#### ④ `MemoryAdaptiveDispatcher` + `RateLimiter` —— 并发与限速的正确抽象 ★★

**它做了什么**：

- `RateLimiter`：按**域名**维护延迟；`rate_limit_codes = [429, 503]` 命中即自适应加大延迟
- `MemoryAdaptiveDispatcher`：后台持续监控**真实内存占用**，超过阈值（默认 90%）
  进入 **`memory_pressure_mode`**，**自动降低并发而不是 OOM**

**我们的对照实现**：我们也做了域名级限速 + 自适应退避——思路一致；
但我们**主动选择串行**，理由是**自己的实测数据**：

| 方案          | 耗时              | 结论                           |
| ------------- | ----------------- | ------------------------------ |
| 串行          | ~7.3 min / 9 型号 | 基准                           |
| 三站并发      | 11.2 min          | **反而更慢**（CPU / 代理争抢） |
| 同站拆 2 进程 | 失败              | **profile 被锁**               |

而且限速器是**进程内**的——并发 = 同一出口 IP 速率 ×3 → 封禁风险显著上升。

> **好的抽象值得学，但"该不该并发"必须用自己的实测数据决定。**

#### ⑤ `Adaptive Crawling` —— 把"爬够了没有"变成可计算的分数 ★★

| 分数            | 衡量什么                     | 直觉           |
| --------------- | ---------------------------- | -------------- |
| **Coverage**    | 对查询词及关联概念的覆盖程度 | "该说的说了吗" |
| **Consistency** | 跨页信息是否自洽、有无矛盾   | "说的对不对"   |
| **Saturation**  | 新页面是否还在提供**新信息** | "还有新东西吗" |

**停止判据**：新增信息 < 10% 就停。
**链接排序**：`ExpectedGain = Relevance × Novelty × Authority`。

**我们的对照**：我们的终止条件是**穷举式**的六条
（条数上限 / 本页无新增 / 页数上限 / 拼不出下一页 / 被拦 / HTTP 连续失败）。

> 两者思路一致——**把"什么时候停"从模糊感觉变成显式判据**。
> 差别在于它更**通用**（打分驱动、可调阈值），我们更**贴业务**。

### B.4 其他值得知道的

| 能力                  | 一句话                                                       |
| --------------------- | ------------------------------------------------------------ |
| **Deep Crawling**     | BFS / DFS / BestFirst + filters + scorers；含 `resume_state` **崩溃恢复**（长任务友好） |
| **Hooks**             | 导航前后、执行开始等钩子，用于认证、埋点、取证               |
| **Sessions**          | `session_id` 复用浏览器上下文，保持 cookie / localStorage    |
| **Cache 三档**        | `read_write` / `read_only` / `bypass`（我们的做法一致：正式快照**不依赖缓存**，命中要如实标记） |
| **`crwl` CLI**        | `crwl <url> -o markdown` / `--deep-crawl bfs --max-pages 10` / `-q "Extract all prices"` |
| **Docker API Server** | FastAPI + JWT + 浏览器池 + Dashboard + Playground + **MCP 集成** |
| **`c4a-script`**      | 可编译的脚本语言（不是裸 JS）——比"内联任意 JS"更安全，和我们"只产配置不产代码"的安全观同源 |
| **prefetch 模式**     | 新版 URL 发现提速 5-10×                                      |

### B.5 ★ 一个额外发现：它的「LLM Context Protocol」和我们的 Skill 同源

Crawl4AI 作者有一篇文章，核心论点：

> 光喂 API 文档给 AI，它写出的代码"语法正确但没用"——像拿着短语手册说话的游客。
> 应该提供的是**智慧**，不只是**信息**。

他提出**三支柱**：

| 支柱                  | 内容                           | 对应我们 skill 里的什么       |
| --------------------- | ------------------------------ | ----------------------------- |
| **Memory**（记忆）    | API 签名、参数、类型——"事实"   | `reference.md`：信号→解法规律 |
| **Reasoning**（推理） | **为什么这么设计**——作者的哲学 | `SKILL.md` 的铁律 + 判断口径  |
| **Examples**（示例）  | 纯代码，无废话                 | `cases.jsonl` + `playbook/`   |

**我们的 skill 结构几乎就是这个协议的实例化**：

```
.kiro/skills/spec-schema-gen/
    SKILL.md        ← Reasoning（主流程 + 铁律 + 工具边界，7.5 KB）
    reference.md    ← Memory（判断经验库，8.7 KB）
    cases.jsonl     ← Examples（案例库，可 grep，5.1 KB）
    playbook/       ← Examples（8 类结构型套路，≈28 KB，按需读）
```

> **这三支柱其实就是"省 token 的正确姿势"**——不是把所有东西塞进 prompt，而是**分层**：
> 每次都进上下文的是"推理与铁律"（7.5 KB），事实与示例**按需检索**。
> 这与我们"渐进式披露"的做法是同一个答案，被独立验证过。

### B.6 我们为什么不直接用它

**不用的理由**（写在项目 README 里的原话）：

> 架构模式借鉴 Crawl4AI（插件自动发现、Strategy 分层、域名级调度、大字段外置），
> 但**不引入该包**：它有 30+ 重依赖且是 async + LLM 中心设计，
> 与本项目「标准库优先、可离线部署」的取向冲突。

**借鉴的（2 项，都落地了）**：

1. `generate_schema` 思路 → 我们的配置生成器
2. `preprocess_html_for_schema` 的**重复卡片去重** → 我们的 HTML 降噪升级

**明确不借鉴的**：

| 不借鉴                        | 理由                                                         |
| ----------------------------- | ------------------------------------------------------------ |
| `LLMExtractionStrategy`       | **每页调 LLM 抽取**——成本与本路线冲突（我们日常重跑要做到 token = 0） |
| `PruningContentFilter` / BM25 | 面向**正文提取**，会**误删规格表**                           |
| 异步框架 / stealth 插件       | 与我们的同步架构冲突（已有等价能力）                         |
| 其自有 schema 格式            | 我们已有更贴业务的契约格式                                   |

> 这条决策本身就是个可复用的方法——**借鉴架构模式，不引入依赖。**
> 判断标准不是"它好不好"，而是"它的**设计中心**和我的**约束**是否冲突"。
> 它是 async + LLM 中心，我是同步 + 零依赖中心，那就只拿设计、不拿代码。

## 附录 C：多页与滚动（完整技术细节）

### C.1 八种翻页类型与对应抓法

| 类型                      | 表现                                   | 抓法            |
| ------------------------- | -------------------------------------- | --------------- |
| `none` 静态一次列全       | 首屏即全部                             | 直接取          |
| `scroll` 滚动懒加载       | 滚动才注入新卡片                       | 滚动到稳定      |
| `click_more` 点加载更多   | 点按钮追加                             | JS 点击累积     |
| `numbered_pages` 编号页码 | `Show page N of results`               | 逐页点击 + 累积 |
| `query_param` 服务端分页  | `?firstResult=N`                       | 拼 URL 逐页取   |
| `filter_sweep` 过滤扫描   | 靠星级/排序过滤穷举                    | 按条件扫描      |
| `url_page` 独立评价页     | `/product-reviews/<ASIN>?pageNumber=N` | 拼 URL          |
| `bv_api` 第三方接口       | BazaarVoice JSON 接口                  | 纯 HTTP 直连    |

### C.2 分页识别的信号优先级

判定规则被专门收紧过一次，因为**误判比漏判更贵**：

- **只有"编号页码"是可靠的分页信号**
- **孤立的 next 按钮多半是轮播** → 判为"无分页"

**真实事故**：某静态站，LLM 自作主张加了分页、点错了轮播的 next 按钮，
导致实抓 **0~1 个型号**。修法两条：
① 探测器只在"编号页码"时判分页；
② prompt 在"静态列全"时明确告知 LLM「首屏即全部、忽略 next 按钮、不要加分页」。

### C.3 滚动：等到稳定

**契约**：等到目标集合**连续 N 轮不增长**再取。

真实事故记录：

| 现象                        | 根因                                            |
| --------------------------- | ----------------------------------------------- |
| 曾因时序**只发现 1 个系列** | 入口首个链接出现 ≠ 全部注入 DOM                 |
| 稳定拿到 33 个，**漏 4 个** | 滚动停止时那 4 个还未稳定注入                   |
| 总量在 **29~36 之间波动**   | 首页只有 2 个产品，其余全靠懒加载，稳定判定不足 |

**默认参数与代价**：成功页等 `networkidle`（默认 **4 秒**上限），再执行滚动 **3 次 × 0.8 秒 ≈ 2.4 秒**。

**耗时成本结构（实测拆解）**：

```
限速等待        ≈ 55%~60%
成功页固定等待  ≈ 25%~35%   ← settle(≤4s) + 滚动(≈2.4s)，即每成功页额外 4~7 秒
真实页面加载与解析  占比最小
```

> 反直觉的结论：**我们大部分时间不是在下载网页，是在等自己。**

### C.4 把"是否滚动"变成按页面类型的参数

**动机**：`settle + 滚动` 是逐页固定支出，但**评价页与讨论页根本不是懒加载列表**，滚动收益极低。

**做法**：把「是否滚动 / 是否等 networkidle」从全局常量改成**调用级参数**：

- 搜索页、系列页：保留滚动（确实有懒加载）
- 评价页 / 讨论页：`scroll_passes=0`，`settle` 缩短到 1~1.5 秒，保留锚点等待作为渲染判据

**落点**：`page()` 增加 `settle_ms / scroll_passes / scroll_wait_ms / nav_timeout_ms` 入参
（默认 `None` = 沿用全局配置，不传时行为完全不变）。

**风险与对策（很重要）**：必须逐站抽样比对「关闭滚动前后解析出的条数一致」，
任一数量下降就回退该页面类型的配置。

> 性能优化最怕"一刀切调参"。**先按页面类型分类，再分别调，
> 且每类都要有"改完数据不变"的回归证据。**

### C.5 替换式分页：48% → 100% 的完整排障故事 ★

**背景**：某站官网显示 `TV (25)`、`1 - 12 of 25 results`，底部有 1/2/3 页码。
适配器只能发现 **12 个型号**。

| 轮次 | 判断                                               | 结果                                                         |
| ---- | -------------------------------------------------- | ------------------------------------------------------------ |
| 1    | 以为选择器写错                                     | 看首屏 HTML 其实有 **122 个产品链接**，去重后只 **12 个型号** → 第二三页根本没进 DOM |
| 2    | 确认是前端分页，点击**替换**当前页卡片（不是追加） | 写专用片段：探测最大页码 → 逐页点击 → 每页轮询等新链接渲染（≤8 秒）；**走两轮全部页码 + 每轮回采第 1 页**消除时序抖动 → **12 → 25 全找到** |
| 3    | 换通用片段后**又掉回 12/25（48%）**                | 初诊断怀疑选择器，**实测定位真实根因是 JS 片段三层转义 bug**：正则里是 `\\d`（匹配字面反斜杠）→ 页码按钮永远匹配不到 → 翻页全失败 |
| 4    | 修好转义 + 把通用片段做鲁棒                        | **48% → 100%**                                               |

**让通用片段鲁棒的三个设计（含金量最高）**：

1. **最大页码不能只在首屏探测一次** —— 替换式分页首屏只渲染前几个页码按钮，
   更大的页码要翻页后才出现 → 必须**每次翻页后重扫 DOM**
2. **每次翻页后重扫页码** —— 返回页码集合，翻页后补入新页码，
   直到**无未访问页码且连续 2 轮已收集规模不增长**（对替换式和追加式都稳）
3. **安全阀** —— 总翻页上限 80、页码 ≤ 200；无编号页码时回退"点下一页直到不增长"（上限 60）

**一条关键口径修正**：

> 分页站的找全率**不能用首屏 HTML 卡分**，
> 要用**引擎执行分页片段后的实际发现数**判定。

否则你会判一个"其实能翻全"的站为失败，或者反过来把 48% 当成功。

### C.6 终止条件：六条统一的安全阀

**任一命中即停且不重试**：

1. 条数达上限
2. 本页无新增（**增量停止**）
3. 页数达上限
4. 拼不出下一页 URL
5. 被拦（带原因）
6. HTTP 连续失败

**增量停止的实现**：读取已入库的唯一键集合 → 逐页抓 →
**本页全为已知记录即停止翻页**。效果：第二次跑请求数 ≤ 首次 30%、新增 0 条。

**站级熔断**：连续 5 个被拦（blocked / 410 / 403 / 429）即跳过该站剩余型号。
效果：某站 204 型号全量从"撞 **148 个 410**"变为"**5 个即停**"。

### C.7 评价翻页的真实能力边界

| 站点         | 实测                                                         | 结论                                     |
| ------------ | ------------------------------------------------------------ | ---------------------------------------- |
| 某强防护站   | 独立评价页 3 页全是空壳；商品页滚动 5/14/30 次也只有 8 条    | **评价区是组件动态加载，非整页滚动触发** |
| 同上         | 总评分 2,742 的产品也只给 **8 条**                           | **服务端硬顶**，已穷尽 9 种途径          |
| Shopify 类站 | 评价内嵌在商品页，无独立翻页，首屏即全部                     | 当前抓法已覆盖                           |
| 某会员制站   | DOM 里没有评价明细，但第三方评价**客户端 JSON 接口可纯 HTTP 直连** | 零成本接入，不需要登录/passkey           |

**修过的真实 bug**：评价翻页 URL 的拼接分支只替换了商品号与页码，
**漏替换了基址占位符** → 翻页 URL 一直是无效的。

> **"实现了翻页"和"能抓到全量评价"是两件事。**
> 站点硬上限、风控、懒加载机制都可能让你的翻页代码一行都跑不到。

### C.8 多尺寸：比翻页更容易漏的一类

一个系列常有多个尺寸型号，**DOM 默认只渲染一个代表尺寸**。

| 站点类型      | 权威来源                                 |
| ------------- | ---------------------------------------- |
| 品牌官网（A） | swatch 的 `data-product`                 |
| 品牌官网（B） | 官方 finder 接口（一次取全，按品类过滤） |
| 品牌官网（C） | 详情接口的 `baseOptions`                 |
| 品牌官网（D） | 前端分页逐页点击                         |
| 品牌官网（E） | 详情页同系列同类别尺寸展开               |

**真实收益**：

- 某站从 **6 系列 / 9 型号** → **64 系列 / 224 型号**（旧适配器只读 DOM）
- 某站一次真实运行得到 **34 系列 / 118 尺寸型号**（展开补入 82 个变体）
- 某站从 **12 型号** → **11 系列 / 25 型号**

**一个细节坑**：尺寸 swatch 可能是无 `href` 的按钮；
展开时必须**限制同类别路径**，否则会抽到推荐区跨类别历史链接（那些常 404）。

### C.9 别把业务锚点当"等待选择器"

**现象**：翻页到尽头时本就没有内容，如果传了业务锚点当等待条件，
会被反爬检测误判为"锚点缺失"，**中断整个型号**。

**正确做法**：抓翻页时不传业务锚点，靠自身数量判断是否还有内容；
**真正的拦截由三路捕获**：状态码（403/429/503）/ 验证码关键字 / 正文过短。

**相关**：搜索页的等待选择器不要填候选容器——容器是**滚动后才懒加载出来**的，
等待会先白等 8 秒超时。用 `a` 或 `body`，靠滚动次数决定。

**滚动次数不够 = 0 候选**：某站需 `scroll≥12`（配 10 秒等待）才出 24 个候选，
默认 `scroll=3` 时是 **0**。

## 附录 D：省 token 与经验回灌的完整做法

> 这两件事在闭环里是同一件事的两面：
> **省 token = 让 LLM 只跑一次（① 探索）**；
> **经验回灌 = 让"下一次的探索"更便宜（③ 回灌）**。

### D.1 最大的省法：把 LLM 移出运行期

| 做法                            | 效果                                     |
| ------------------------------- | ---------------------------------------- |
| **LLM 只产配置，不产代码**      | 配置一次生成、长期复用                   |
| **日常重跑只读配置**            | 每次全量抓取 **token = 0（已达成指标）** |
| **明确不采用"每页调 LLM 抽取"** | 那是根本性的成本冲突                     |

> 省 token 的终极答案不是压缩 prompt，是**让 LLM 只跑一次**。

### D.2 让那"唯一一次"尽量少轮次

| 手段                       | 说明                                                     |
| -------------------------- | -------------------------------------------------------- |
| **小样先行**               | 每轮只跑 1~2 个系列判分，达标才全量 → 省 token、快速失败 |
| **双层校验替代反复重生成** | 静态校验 + 真实页面实测打分；不达标**只回喂失败清单**    |
| **硬性轮次上限**           | + diff 检测**反复横跳** → 转人工                         |
| **按站点缓存**             | 同站重复探测不重复调 LLM                                 |
| **失败现场留档**           | 不用靠"再跑一次看看"来复现问题                           |

### D.3 喂给 LLM 的内容要"少而准"

**反直觉的实测结论**：

| 喂法                      | 结果                                      |
| ------------------------- | ----------------------------------------- |
| 原始 HTML（内部截断 30K） | **94 分 PASS，2 轮收敛**                  |
| 简单整页压缩后再喂        | **0 分 FAIL**（压缩破坏了 id/class 线索） |

**升级后的降噪做法**：

- 去 `<head>` 整段 + script/style/svg 等非内容标签
- **只保留 `id/class/name/type/value/href/data-*`**（生成选择器有用的属性）
- 长属性值 / 长正文截断
- **重复卡片去重**：同 `(tag, class, 文本hash)` 的元素只留第一个
- 解析库不可用时回退正则版（保底不崩）

**效果对比**（112K 字符，1200 个重复导航卡 + 页尾关键元素）：

| 版本                        | 输出大小     | 页尾关键元素保留 |
| --------------------------- | ------------ | ---------------- |
| 旧做法（截断 30K）          | 30,021 字符  | **0/4**          |
| 新做法（去重 + 白名单属性） | **418 字符** | **4/4**          |

> **压缩版当地图定位目标，原始 DOM 片段当施工面生成选择器。**

### D.4 ★ ③ 经验回灌：闭环里最值钱的一步（这里讲全）

> 正文 1.5 讲了它"为什么值钱"，这里讲"**怎么落地成机制**"。

**机制：Step 0 先查经验 → Step 6 强制回写。成功或失败都必须写。**

```
Step 0 — 先查经验（省时间的关键，别跳）
   检索案例库（按域名/建站特征/URL 路径匹配相似站）
   读经验库（信号→解法规律 + 已知坑）与结构型索引
   ★ 命中相似站 → 直接以那份配置为起点改，通常 1 轮就过

Step 6 — 强制回写（漏了等于白干一次）
   追加案例一条 + 新规律进经验库 + 新结构型加一份套路
```

**三类产出的具体形态**：

| 产出             | 内容                                            | 大小   | 何时读             |
| ---------------- | ----------------------------------------------- | ------ | ------------------ |
| 主流程（含铁律） | 标准动作 + 判断口径 + 工具边界                  | 7.5 KB | **每次都进上下文** |
| 经验库           | 信号 → 解法规律、已知坑                         | 8.7 KB | 探索前             |
| 案例库           | 每站一条：特征 / 参数 / 结果与找全率            | 5.1 KB | **Step 0 检索**    |
| 结构型套路       | 静态 / 懒加载 / 编号分页 / 替换式 / 多级 / 接口 | ≈28 KB | 命中结构型时       |
| 自检脚本         | 校验经验与代码是否脱节                          | —      | 改动后必跑         |

**为什么"强制"两个字很重要**：
经验回写如果只是"建议"，任务一忙就会被跳过，
**skill 就会永远停在第一天的水平**。所以它被写成了流程的第 6 步，且成功失败都要写。

**回写之后要校验（否则会沉淀错误）**：

| 校验项                       | 拦什么                                         |
| ---------------------------- | ---------------------------------------------- |
| 结论标记与找全率是否自相矛盾 | 标"成功"但实际只有 80% 找全率                  |
| 引擎白名单与规范文档是否一致 | 代码改了文档没改 → AI 照旧文档写出跑不通的配置 |
| 已定稿配置是否仍合法         | 引擎升级后老配置失效                           |
| 文档有无死链                 | 经验资产腐化                                   |

> 上线第一次跑自检就抓出一处过度声明。
> **沉淀不校验，等于把错误固化下来。**

### D.5 渐进式披露（结构本身就在省 token）

**只有主流程文件是"每次都进上下文"的**（7.5 KB），
经验库 / 案例库 / 套路文档全部**按需加载**（≈42 KB）。

对照另一条线（经验库 21.8 KB、案例库 16.3 KB），这种拆分的价值更明显。

### D.6 防脱节机制：省的是"无效重试"的 token

文档与代码脱节是 AI 协作最贵的隐性成本——
**智能体照旧文档写出跑不通的配置，然后反复试错**。

所以加了一个自检脚本，核对：

- 引擎白名单常量是否都在规范文档里有记录
- 规范文档里的示例是否真能过校验
- 已定稿配置是否仍合法
- 案例里的结论标记与找全率是否**自相矛盾**（标成功但 < 95% 会被拦）
- 文档有无死链

> 上线第一次就抓出了一处过度声明（某站标成功但找全率只有 80%）。
> **改动引擎或规范后必须跑一次。**

### D.7 上下文卫生：两条最省钱的工作纪律

**（1）每轮只动一个变量** —— 否则分不清哪个改动起作用（为此花过 4 小时排查）

**（2）先证伪，再改代码** —— 三次印证：

1. 以为"翻译错了" → 其实是词典归一化问题，**不是抓取错误**
2. 以为分页 48% 是选择器问题 → **实测根因是 JS 三层转义**
3. 以为限流是代码 bug → **定位后是 IP 频率限流**

> **花半小时取证，比花半天改错地方划算。**
> **你让 AI 去改一个不存在的问题，它会很认真地改坏别的东西。**

## 附录 E：长任务 IDE 工作流细节

### E.1 量级参考

| 任务                                     | 耗时             |
| ---------------------------------------- | ---------------- |
| 三站电商全量（621 + 405 + 204 型号）     | **约 10.5 小时** |
| 单品牌规格（重页面）                     | ~80 分钟         |
| 单品牌价格+网评（44 型号 × 多页 × 限速） | 15~25 分钟       |
| 规格全量                                 | 数十分钟         |
| 证书核对全量（238 行，15s + 抖动）       | 约 1 小时        |

**而单次前台调用约 10 分钟就会被 kill。**

### E.2 标准做法

**（1）后台任务 + 定期看输出**

> 交接文档原话：「**务必用后台任务**（单次前台调用会超时约 10 分钟被 kill）：
> `run_in_background: true`，然后用 `job_output` 定期查看。」

**（2）输出重定向到文件，且避开会转码的管道**

```powershell
# 正确
$env:PYTHONUTF8='1'
& $py -X utf8 script.py *> run.log 2>&1

# 错误 —— 某些管道命令会按本地代码页转码，中文乱码
```

> 教训原话：「输出统一 `> file 2>&1` + UTF-8 模式；
> **不要用会按本地页转码的管道命令**。」

**（3）理解"日志缓冲"——不要把正常现象当卡死**

> 「管道/文件重定向会**缓冲到进程结束才落盘**，轮询期间读不到中间日志属正常；
> **判断进度用进程状态 + 产物文件**，不要误以为卡死。」

**（4）终端与进程卫生**

工作日志里专门有"终端和进程"章节：跑完的终端要关闭空跑终端，
但**要保留 API 进程和 IDE 语言服务进程，别误关**。

### E.3 幂等 / 续跑 / 分段核对

**（1）幂等性设计**

| 表       | 机制                              | 效果                                             |
| -------- | --------------------------------- | ------------------------------------------------ |
| 价格快照 | **只增不快照改**，不 UPDATE       | 重跑不产生脏数据，天然形成价格曲线               |
| 评价     | `(商品, 评价唯一键)` **唯一约束** | 重跑不重复入库                                   |
| 运行审计 | 每次新增审计记录                  | 可追溯                                           |
| 已有记录 | **只补空字段**                    | 修好选择器后重跑可**回填历史空值**，不用清库重采 |

> 所以「中途若被 kill：**直接重跑即可**」。
> `新增 0 条` 表示"已抓过"，**不是失败**。

**（2）断点续跑（不要"部分成功当全量成功"）**

**问题**：批处理 **1800 秒超时会截断大品牌**。

**解法**：用数据库审计（**入口发现集 vs 成功集**）算出 pending，定向续跑；
多轮不收敛即停并提示人工。

**核心纪律**：**不把部分成功当全量成功**——
产物标"有条件通过"而非无条件验收，并写明差异条款，**部署前不得静默忽略**。

**（3）分段执行 + 每段立即核对**

> 「每站跑完**立即**做核对，**再**开始下一站。」

核对内容：行数增量 + 完整性检查 + **型号级成功率（按状态分组）** + 抽查导出文件。
并且给出**期望区间**，让接手人能判断"这算正常还是算异常"：

| 指标                | 期望                                |
| ------------------- | ----------------------------------- |
| 价格成功 / 型号数   | 各站 10%~80% 不等（视站点）         |
| 评价成功 / 价格成功 | 接近 100%                           |
| 无价格              | 页面无主价 → **正确留空，不是失败** |
| 被拦                | 应接近 0；若 >5/站 → 出口 IP 被限流 |

### E.4 交接文档模板（10.5 小时任务的交付物）

```
0. 一句话任务（做什么、多久）
1. 环境准备（每次开新会话必做）+ 自检命令（必须全过再开始）
2. 已完成并验证的工作（接手方无需重做）
3. 必须知道的实测结论（决定预期，别抱错希望）
4. 执行全量（核心步骤，含备份、顺序、运行方式建议）
5. 结果核对（每站跑完必做，含期望区间）
6. 已知限制（如实交付，不要美化）
7. 故障排查（症状 → 原因 → 处理）
8. 技术改动索引（改了哪些文件）
9. ⚠️ 重要风险提示
10. 交接验收标准（可勾选清单）
```

**最值得学的两条**：

- **§3「必须知道的实测结论（别抱错希望）」** —— 先告诉接手人"哪些做不到"，
  避免他在不可能的事情上浪费时间
- **§9「重要风险提示」** —— 如实写出"**有另一个会话在并发修改同一工作区**"，
  证据是文件时间戳，并建议"全量运行期间避免同时改共享代码"

### E.5 为什么用 IDE 终端而不是纯对话

| 需求                                 | IDE 终端        | 纯对话       |
| ------------------------------------ | --------------- | ------------ |
| 10 小时不中断                        | ✅ 后台进程      | ❌ 有超时上限 |
| 多任务并行（抓取 / 自检 / API 服务） | ✅ 多终端        | ❌ 串行       |
| 看真实日志文件                       | ✅               | 受上下文限制 |
| 长输出的上下文成本                   | ✅ 只读尾部/产物 | ❌ 全进上下文 |

> **对话用来判断和编排，IDE 终端用来跑和留痕。**
