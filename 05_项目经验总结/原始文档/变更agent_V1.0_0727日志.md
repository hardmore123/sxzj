表1、表2分开解析；

2. Parser：文档解析模块
代码位置：

compare_core/parser/doc_parser.py
职责：

.doc/.docx
    ↓
表格、行、列、分组、合并单元格解析
    ↓
Row结构化对象
统一输出为 Row：

Row(
    table=1,
    group="53772-A型机内电源单元上元器件",
    关键件名称="X电容",
    型号="MKP62",
    位号="CX802",
    规格材料="0.47μF X2 305VAC",
    制造商="...",
    生产企业="...",
    认证标准="...",
    证书号="...",
)
设计思路
Word 文件不能直接可靠地进行字符串比较，必须先变成结构化数据。

Parser 重点解决：

表格列结构不固定；
合并单元格导致列号变化；
关键件名称跨多行；
分组标题不是普通数据行；
证书号列位置和表头名称不完全一致；
Word 中存在非法控制字符。
当前方案
Word COM + pywin32
优点：

可以读取老式 .doc；
能处理复杂合并表格；
已在真实样例上验证关键字段。
不足：

解析速度较慢；
Word COM 容易受进程状态影响；
Word 被占用或异常退出时可能挂起；
生产环境需要增加超时和进程恢复机制。
后续建议：

.doc → 预转换为 .docx → python-docx 批量解析
3. Normalize：数据归一化模块
代码位置：

compare_core/differ/normalize.py
归一化不是修改原始展示文本，而是为了让比较更稳定。

当前处理：

繁体 → 简体
全角 → 半角
～ → ~
连续空白 → 空
顿号、中文逗号统一
大小写统一
例如：

250V～
250V~
归一化后视为相同。

電線組件
电线组件
归一化后也视为相同。

设计原则：

格式差异不要误判为业务差异。

但输出层仍可根据配置决定是否统一转简体。目前默认输出简体字，并统一使用宋体。

4. Differ：行级差异比对引擎
代码位置：

compare_core/differ/diff_engine.py
这是当前 MVP 的核心模块。

输出四类差异：

类型	含义
same	两侧是同一条资料，合并保留一条
changed	两侧属于同一分组、同一关键件，但内容有变化
only_plm	只有 PLM 清单存在，属于新增或变更后项
only_orig	只有原报告存在，必须保留
当前匹配键：

rich key：
表号 + group + 关键件名称 + 型号 + 位号 + 规格材料 + 证书号

loose key：
表号 + group + 关键件名称 + 型号
匹配逻辑：

先尝试 rich key
    ↓
命中：same
    ↓
未命中时尝试 loose key
    ↓
命中：changed
    ↓
仍未命中：only_plm
    ↓
最后追加所有未消费的原报告行：only_orig
为什么使用多重集而不是普通字典
错误方式：

orig_index[key] = row
如果多个物理行拥有相同名称和型号，后面的行会覆盖前面的行。

当前方式：

orig_rich[key] = [row1, row2, row3]
配合：

used = set()
每次只消费一行，因此可以保留：

同名同型号不同证书号；
同名同型号不同位号；
同名同型号不同规格；
同一分组下的多个物理记录；
不同分组下的相同型号。
当前确认的业务原则
group 是身份上下文
证书号不同不能折叠
位号不同不能折叠
原报告独有项全部保留

四、LangGraph 在项目中的位置
LangGraph 不是业务逻辑核心，而是流程编排器。

flowchart LR
    START --> parse
    parse --> judge
    judge --> suggest
    suggest --> human_review
    human_review --> apply
    apply --> memory
    memory --> END
各节点职责：

节点	职责
parse	Word转结构化Row

设计原则：

LangGraph 可以替换
compare_core 尽量不替换
因此当前支持：

--engine core
直接运行核心顺序流程，也支持：

--engine graph
运行 LangGraph 人工确认流程。

十、当前项目最核心的设计原则
原则一：代码负责确定性判断
解析、归一化、匹配、差异分类、文件生成
尽量由代码完成。

原则二：LLM 只负责语义归纳
把多条行级差异归纳成业务人员能读懂的变更事项
不让 LLM 直接决定是否丢弃关键件。

原则三：所有关键决策都有人确认
AI建议 → 人工确认 → 生成最终资料
原则四：结果必须可追溯
每条输出应能追溯到：

原报告哪一行
PLM 哪一行
匹配键是什么
发生了哪些字段变化
用户是否接受
原则五：业务补充和自动差异分开
自动清单差异
≠
