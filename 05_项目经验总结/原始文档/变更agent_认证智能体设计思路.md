### 变更agent

**功能：**新机型变更认证时，把 PLM 新导出清单 + 派生原报告清单两份 Word 整合成一份"变更后关键件清单"，并生成"变更前后对照表"，用于 KOA 3C 认证变更流程。

**输入输出：**

输入：PLM导出清单.doc（变更后来源）+ 原报告清单.doc（变更前基准）
输出：安全&EMC关键件清单.doc（整合版）+ 变更前后对照表.doc
**整合规则**

（PRD "重复合并、非重复标红加粗、备注来源" 的细化）：

以"行级报备项"为比对单位，表1/表2 各自比对
重复→合并保留一份；仅一方有→保留并标来源；仅 PLM 有的新增项→标红加粗+备注来源；内容不同→标红加粗差异字段
比对前做归一化（空格/全半角/单位符号）
对照表规则：不是逐行 diff，而是把行级差异归纳成业务变更项（增加型号规格/增加备选件/补充供应商/增加照片…），"变更前"填见原报告、"变更后"填"见原报告 增加：…"。

**目前实现思路**:

**流程（判断→建议→修改 + 人确认 + 记忆）映射成 6 个节点的状态图：**

1. `parse` 解析两份 .doc → 结构化行（代码）
2. `judge` 归一化+匹配键对齐 → diff 分类：重复/仅原报告/仅PLM/内容差异（**纯代码，保证确定性**）
3. `suggest` 规则库+LLM → 每项给"建议动作+理由+命中规则+置信度"，并把行级 diff 归纳成对照表变更项（**LLM 只在这里**）
4. `human_review` → 用 LangGraph 的 `interrupt()` 中断，用户逐项点 是/否/改
5. `apply` → 生成整合清单.docx + 对照表.docx（代码后处理）
6. `memorize` → 用户决策落盘

**你关心的三件事对应的设计：**

- **人有决策权 + 中间细节可见**：`interrupt()` 挂起后前端展示一张"差异确认表"，每行带 AI 理由/命中规则/置信度，以及 parse/judge 的中间产物。这既满足透明性，也是反馈数据来源。
- **提示词+编排+后处理**：提示词只在 suggest；编排是 StateGraph；后处理是 LLM 输出的 try/except 校验 + Word 富文本写回。
- **用户操作正向促进（长期记忆）**：做**两层**——短期用 Checkpointer（会话内中断恢复），长期用 Store/反馈库。促进方式三档递进：① suggest 前检索相似历史决策直接复用/做 few-shot，**减少需人工的项**；② 被反复否掉的建议沉淀成"反向规则"防误报；③ 积累到阈值后 LLM 提炼规则建议、**人工审批**才落库。关键红线：自动只到"出建议"，改规则必须人工确认，保证可控可回滚。

**规则库**先做最小 YAML（匹配键+归一化+标注+变更项分类几条），它同时就是人工反馈的落地载体。

**最小实现顺序**：M1 解析 → M2 diff → M3 编排跑通出整合清单 → M4 加人确认 → M5 接 LLM 出对照表 → M6 记忆闭环。每步能独立验证。

好问题。答案是：当前会丢弃 A 侧的内容。我用代码确认给你看。

CHANGED 行在 writer 里的取值逻辑（_emit_table）：

if d.type == DiffType.SAME:
    row = d.orig or d.plm       # SAME 取 A
else:
    row = d.plm or d.orig       # CHANGED 取 B ！！
所以 CHANGED 行只输出 B（PLM）侧的内容，A 侧被丢弃。

具体到你的电线组件例子：

diff 阶段：
  A "电线组件" HL-006L (证书 2025010101761675)
     ↕ fuzzy 配对
  B "电线组件(0.5平方毫米...)" SP-505C (证书 2013010101590637)
  → 判 CHANGED

writer 输出：
  只写 B 的这行：电线组件(0.5平方毫米...) SP-505C  ← A 的 HL-006L 那行没了！
A 的"电线组件 HL-006L"确实被丢掉了。 这跟你之前确认的策略矛盾——你说过 CHANGED 时"保留 A 侧内容，B 的内容也保留（加删除线）"，且"不丢行"。

问题根源
fuzzy 匹配把 A 的一行和 B 的一行配成了 CHANGED，但 writer 对 CHANGED 只输出一行（B 侧），于是配对消耗掉的 A 行内容消失了。

这在普通 CHANGED（同名同型号仅规格变化）时问题不大——A 和 B 大部分字段一样，丢 A 保留 B 可接受。但在 fuzzy 名称变更这种情况下，A 和 B 是两个不同的物料（HL-006L vs SP-505C，不同型号不同证书号），把 A 丢掉就是真的丢了一个物料。

两种修复方向
方向 1：CHANGED 输出两行（A + B 都保留）

A 侧行：正常显示（或加删除线表示"变更前"）
B 侧行：标红显示（"变更后"）
符合你之前说的"A保留，B也保留标红"
方向 2：fuzzy 命中的不算 CHANGED，拆成 ONLY_ORIG + ONLY_PLM

fuzzy 只用来"归组排序"（让它们聚在一起），不合并成一行
A 的 HL-006L → ONLY_ORIG（保留，来源"派生报告"）
B 的 SP-505C → ONLY_PLM（保留，标红，来源"PLM"）
两行都在，都不丢
方向 2 更干净：fuzzy 本来就是"名称不同的两个物料，只是同属一个关键件组"，它们确实不该被合并成一行。fuzzy 的价值只在排序归组（让它们排在一起），不该消除任何一方。

我倾向方向 2——fuzzy 不再产生 CHANGED（不合并），而是让 A 保留为 ONLY_ORIG、B 保留为 ONLY_PLM，但通过之前的关键件组排序让它们聚在一起。这样：

不丢任何行
电线组件组仍然聚拢
A 的 HL-006L（派生报告，不标红）+ B 的 11 个选型（PLM，标红）全在
