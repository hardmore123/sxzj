**overseas（9.4–9.18）：把"接站"从写代码改成审配置**

本期的方法论内核是"**契约驱动 + 能力档位显式化 + 红线可执行**"。下面每一条都配了可核对的数字，避免"感觉做了很多"：

| 创新点 | 具体做法 | 可核对的收益 |
|---|---|---|
| **契约即适配器** | 站点能力写成 `AdapterSpec` / `RetailSpec`（纯 JSON），执行走同一套引擎 | 接站代码量 **224~502 行 → 0 行**；多站复用同一引擎 |
| **重跑与 LLM 解耦** | 配置一次生成、长期复用；日常抓取只读配置 | 每次全量抓取 **token = 0（已达成）** |
| **能力档位显式化** | 三个白名单常量，越界直接抛错而非静默降级 | 结构型覆盖 **4 类 → 6 类**，SPEC 线 P0 缺口清零 |
| **审计表即 reward** | 用真实入库数据给配置打分，不采信 LLM/脚本自述 | 找全率 **<80% 直接判失败**，堵住"假装成功" |
| **红线写进校验** | 零售线 `on_no_match` 必须 `skip`、声明 capabilities 必给 match 段 | 匹配准确率 **= 100%** 成为可执行约束，而非口号 |
| **经验闭环** | 案例库 + 7 类结构型 playbook，"Step0 查经验 / Step6 强制回写" | 上线当天即纠正一处**过度声明**（80% 找全率被标 success） |

配套的数据产出：**17 份品牌 SPEC 宽表**（日 6 / 加 6 / 美 5，中文覆盖率 100%）、日本 kakaku **价格 304/368 命中**、六品牌网评汇总（含离线 NLLB + 在线接口双通道中文翻译版）、北美零售实测 **54 条价格 + 258 条网评**。

### 1.2 改进与创新

**（1）架构级改进：从"写代码接站"到"审配置接站"**

| 维度 | 改前（手写适配器） | 改后（双契约配置驱动） | 量化收益 |
|---|---|---|---|
| 接一个新站 | 写 224~502 行 Python，1~3 天 | 给一个 URL + 审一份 JSON，目标 ≤2 小时 | **接站代码量 0 行** |
| 日常重跑 | 无统一入口 | 读已存配置跑全量，**完全不调 LLM** | **token 成本 = 0（已达成）** |
| 能力边界 | 静默降级、假装支持 | 白名单常量显式化，越界直接抛错 | 杜绝隐性数据缺失 |
| 站点扩展 | 品牌硬编码散落在多脚本 | `regions_config.py` 集中声明 + 适配器自动发现 | 消除结构性技术债 |
| 跨国家复用 | 每个国家重写一套 | 契约 + 引擎复用，仅换配置 | 日本线经验直接复用到加/美/墨 |

**（2）方法论创新：把"经验"和"红线"变成可执行机制**

- **双入口分工**：skill 入口（人机协同、判断力优先，用于接新站与疑难诊断）vs 程序化 CLI（无人值守，用于改版自愈与定时健康探测）——共用同一份 schema、同一套校验、同一个引擎，差别只在 Generate 由谁做。
- **审计表即 reward 函数**：用真实入库数据给配置打分，而不是采信 LLM 或脚本的"自我感觉良好"；`score_spec_on_html` 带**找全率硬否决**（<80% 直接判失败，≥95% 才可交付）。
- **经验闭环**：`cases.jsonl` 案例库 + 7 类结构型 playbook + "Step0 先查经验、Step6 强制回写"——新站十有八九与做过的同型，skill 越用越强。上线当天即抓出一处**过度声明**（把找全率仅 80% 的站点标成 success，改为 partial）。
- **红线工程化**：SPEC 线红线"找全率 ≥95%"、零售线红线"匹配准确率 = 100%"，都不是口头约定——后者写进 `validate_retail_spec` 强制校验（`on_no_match` 必须 `skip`、声明了 capabilities 就必须给 match 段），堵住"不写 match 段即可绕过张冠李戴红线"的漏洞。

**（3）反爬与稳定性创新：把"撞墙"变成"可控停止"**

- **结构化反爬识别 + 白名单豁免**：既识别 IP 层拦截（403/captcha），也避免把 Shopify 站正常内嵌的 `captcha-bootstrap` 脚本误判——`block_marker_allowlist` 使 leons_ca/thebrick_ca 两站从"被抓不到"变为实测通过。
- **站级熔断**：连续 5 个型号被拦（blocked/410/403/429）即跳过该站剩余型号。liverpool 204 型号全量由"撞 148 个 410"变为"5 个即停"；配合间隔 5→12 秒与分批策略，410 限流可有效规避。
- **统一终止条件（6 条）**：评价达上限 / 本页无新评价 / 页数达上限 / 拼不出下页 URL / 被拦（带原因）/ HTTP 连续失败——任一命中即停且不重试，长任务不会失控。

**（4）数据质量创新：宁可"缺"，不可"假"**

- **状态语义化**：系列级 `success / empty / failed` 明确区分"官方确实没有"与"我们没抓到"，不把二者混为一谈。
- **同名覆盖修复**：Samsung 同名 family 因 `family_id` 丢失互相 upsert 覆盖（入口 64 family / 224 型号，落库仅 60 / 205）；用内部键 `<系列名> [family_id=...]` + 对外展示名还原，迁移补抓后 64/224 全齐——这是典型的"看着齐了其实少了"的隐蔽缺陷。
- **不伪造数据**：不写空价行、不用抓取时间冒充官网上市时间、不伪造历史周、部分成功不标全量成功（美国包标 CONDITIONAL 并写明差异）。
- **如实更正**：把 `sams_mx` 从"有问题"更正为"未验证"；把"加拿大站不通"更正为"实测 3 站可抓"——不确定性如实写进交接文档。

**（5）工程与交付创新**

- **零依赖优先、可离线**：核心只用标准库，Playwright 可选；借鉴 Crawl4AI 架构模式但不引入其 30+ 重依赖。服务器无浏览器时用离线 Chrome + `--no-sandbox` + `--config` + SSH 隧道实现"本地驱动、服务器执行"。
- **周度刷新 + 断点续跑**：批处理 1800s 超时会截断大品牌 → 用数据库审计（入口发现集 vs 成功集）算 pending，`refresh_spec_resume.py` 定向续跑，**不把部分结果当全量成功**。
- **交付包可校验**：SHA256 + manifest + 部署说明 + 回滚说明，接收方可独立验证完整性。
- **四层指标看板**：L1 数据正确性（红线）/ L2 覆盖面 / L3 效率收益 / L4 系统健康度，让"完成度"可被讨论而不是靠感觉。
- **本地化能力**：SPEC 离线术语词典（78 → 450 条）+ 归一化兜底 + 未命中待补表，**词典更新后重导出即可、无需重采**；网评翻译走离线 NLLB + 在线接口双通道。

**（6）流程改进：排期与协作方式**

- 从"先写适配器再验证"改为"**先探结构、再判能力边界、能配置就不写代码**"，把不可行站点在前 30 分钟就止损（`needs_handwritten.md` 给出 5 个止损信号）。
- 从"口头交接"改为"**交接文档 + 坑清单 + 验证清单**"，目标是接手人 30 分钟知道"现在在哪、能跑什么、下一步做什么、有哪些坑"。

### 1.3 SPEC 线与零售线的差异（关键分界）

**分叉位置**：见 1.1 总览图——两条线在**契约层就分开了**（SPEC 线用 `AdapterSpec` 走通用引擎 `generic_spec`，零售线用 `RetailSpec` 走执行层 `mx_retail`/`crawl_ca_retail`），此后只在**存储层（SQLite 快照）与导出/出口层**共用同一套基础设施。也就是说：**"共用"的是地基（限速/反爬/缓存/抽取/入库/导出），"不同"的是契约、目标与红线。**

| 维度 | SPEC 线（规格） | 零售线（价格 + 网评） |
|---|---|---|
| 数据源 | 品牌官网规格页 | 零售电商站商品页（含第三方店铺报价） |
| 契约 | `AdapterSpec`（discover / paginate / extract） | `RetailSpec`（search / match / price / reviews / paginate / shops） |
| 接站探索方式 | **入口驱动**：给 lineup 入口 → 探分页/规格表 → **发现**官网型号 | **型号驱动**：给 1 个真实型号 → 探搜索候选纯度 / 商品页价格区 / 评价翻页 / 是否多店铺 |
| 接站产物与入口 | `sites/<code>/schema.json`；skill `spec-schema-gen` / CLI 程序化入口 | `docs/retail_specs/<code>.retail.json`；skill `retail-schema-gen` / 从已有 schema 反抽象 / agent 探索 |
| 核心目标 | **抓得全**（覆盖官网标称型号） | **抓得准**（型号绝不能张冠李戴） |
| ★红线指标 | 找全率 **≥ 95%**（< 80% 直接判失败） | 匹配准确率 **= 100%**（抽检 20 个零误匹配） |
| 主要风险 | 抓不全 | **抓错**（把 55 寸价格记到 65 寸、把配件评价当电视评价） |
| 期望值来源 | 官网标称型号数 | 已给定的型号清单 |
| 失败处理 | 系列级 `success / empty / failed` 如实登记 | 未匹配一律 `skip`，**禁止取第一个凑覆盖率** |
| 增量语义 | 无增量（每周全量快照 + 版本对比） | 评价增量停止（第二次跑请求 ≤ 首次 30%、新增 0 条） |
| 导出形态 | SPEC 宽表（区分 / 项目 / 项目(中文) / 机型…） | 网评 **20 列**统一模板 + 价格**多店铺动态列** + 最低价溯源 |
| 反爬强度 | 低（品牌官网，低频访问即可） | 高（IP 层 403、captcha、410 限流、SPA 懒加载） |
| 主要硬约束 | 站点结构多样 → 靠扩**引擎能力档位** | **网络线路**（需美/加/墨线路或住宅代理） |
| 规模化瓶颈 | 引擎档位（P0 缺口已清零，剩 P1 生产化） | 线路未到位，只有墨西哥 2 站可全量 |
| 当前完成度 | 约 55%（生产化视角）；6 类结构型全自动、接站 0 代码 | 约 55%（基础设施）；14 份 spec，实测跑通 5 站 |
| 验收方式 | 找全率 + 守恒 + 规格质量 + 回归基线 | 匹配准确率抽检 + 价格填充率 + 币种 + 去重 + 增量 |

> **一句话记住区别**：SPEC 线怕"抓不全"，零售线怕"抓错"；SPEC 线的敌人是**站点结构**，零售线的敌人是**网络线路和反爬**。所以两条线的红线、验收口径、优先级都不能互相套用——把零售线的 `on_no_match` 改成 `first` 去冲覆盖率，是唯一一条"一次就能毁掉整条线可信度"的禁令。

## 四、个人思考

1. **"配置化"比"多写一个适配器"值钱，但覆盖面只能靠扩引擎档位。** 本期把接站从 224~502 行 Python 降到 0 行配置，效率收益是确定的；但 skill 化本身不会自动提升覆盖面——全自动站点数从 4 往 10 走，靠的是 P0-1/2/3 这类**引擎能力档位**的补齐。这条判断已写进方案对比文档，避免后续把希望寄托在"让 LLM 更聪明"上。

2. **红线指标要写在最前面，并且要能自动否决。** SPEC 线红线是找全率 ≥ 95%（<80% 直接判失败），零售线红线是匹配准确率 = 100%（宁 `skip` 不错配）。工程上做了两件关键事：一是用**真实入库数据**当 reward，而不是采信 LLM/脚本自述；二是把红线做成**校验层强制**（`on_no_match` 必须 skip，capabilities 声明了就要给 match 段）。误判成功比抓不到更糟——它污染交付数据且很难被发现。

3. **先证伪，再改代码。** 本期至少三次印证：①"翻译错了"最后证明是词典归一化问题而非抓取错误；②分页找全率 48% 的初诊断是选择器问题，实测根因是 JS 三层转义；③liverpool 410 一开始像代码 bug，定位后是 IP 频率限流。**花半小时取证，比花半天改错地方划算。**

4. **数据宁可"缺"，不可"假"。** 全程坚持：不写空价行、不用抓取时间冒充官网上市时间、不伪造历史周、不把部分成功当全量（美国包标 CONDITIONAL、加拿大 LG 8 个失败系列如实入审计）。把 `sams_mx` 从"有问题"更正为"未验证"、把加拿大站从"不通"更正为"可抓"，短期看是"数据不好看"，长期是把不确定性如实交接给下一个人。

5. **网络与反爬是硬边界，要早测早汇报。** 第一周就把服务器出海能力测清（8+ 站不通），直接决定了后续"美加规模化前必须拿线路"的排期判断，避免在能测的地方反复重试浪费时间。现在有了站级熔断兜底，但仍明确"拿到线路前不做无谓连通性重试"。

6. **长任务必须有上限与熔断。** 评价条数上限、翻页页数上限、连续无增长即停、HTTP 连续失败即停、站级连续被拦熔断——这六条终止条件让"204 型号 × 18 站"这种量级不会变成失控的撞墙循环。

7. **工程细节的坑值得沉淀成清单。** 本期踩到并记录：`int(cfg.get("start") or 1)` 把合法的 0 吞掉；类体不是闭包作用域导致 `NameError` 被 `try` 之外抛出；`.gitignore` 的 `_*.py` 误伤 `__init__.py` 导致换机拉代码包直接不可用；`.kiro/` 整段忽略使经验资产无法入库；JS 片段三层转义；PowerShell 吞 stderr 表现为"进程静默退出"。这些已写进交接文档的"必须知道的坑（血泪）"。

8. **交接文档是交付物的一部分。** 目标是让接手人 30 分钟知道"现在在哪、能跑什么、下一步做什么、有哪些坑"，所以除了方案与指标，还专门写了分支/提交状态、可复制命令、18 站分层、红线禁令与验证清单。代码是好的，但如果接手人不知道"别动 `on_no_match=skip`"，一次"为了提高覆盖率"的改动就能毁掉整条线的可信度。

## 六、未来目标与实现路径（下一个半月）

> 排期分三档：**不依赖外部条件的，马上做扎实；依赖外部条件的，边推边等；能常态化的，就让它自己转。**
> 每条都写清"**目标 → 怎么实现 → 拿什么验收**"，不让目标停在口号层。

### 6.1 不依赖外部条件的，马上做扎实

#### 目标 1：把墨西哥打成完整样板（零售线的"标准答案"）

- **目标**：墨西哥 4 站（liverpool / coppel / palacio / sams）全部有 spec、全部产出可交付的价格 + 网评宽表，成为零售线的跨国样板与回归基线。
- **怎么实现**：① liverpool、coppel 跑全量，**分批 ≤35 型号 + 12 秒间隔 + 批间冷却**（规避 410 限流），完成后汇总价格命中数 / 评价条数 / 匹配率；② palacio、sams 补 spec 并通过 `validate_retail_spec`；③ 产物按 `data/墨西哥/` 归国，网评 20 列 + 价格骨架对齐日本线；④ 每站跑 `retail-health` 小样并更新 `data/北美零售抓取任务表.csv`。
- **验收**：4 站 spec 校验全过；每站抽 20 个已匹配商品**零误匹配**；价格填充率 ≥95%；币种 100%；评价按 `(product_id, review_key)` 零重复。

#### 目标 2：零售线工程收尾（R1-6 ~ R1-11）

- **目标**：把"能跑"变成"能交付、能维护"。
- **怎么实现**：① 输出统一到 `data/<国家>/`；② 价格表统一走 `price_export`，废掉 `price_export_ca` 独立布局；③ CA 线接入 RetailSpec（现仍走 SiteRegistry 适配器）；④ `retail_probe` 增加反爬分类汇报（status / blocked / block_reason 四类）；⑤ probe 分页识别加强（补 `rel=next` / `aria-label` / 图标识别，修死分支）。
- **验收**：命令级可验证——14 份 RetailSpec 仍全部合法；回归基线不变（kakaku 8 个店铺列与网评条数、Philips CA 仍 11 系列 25 型号）；改动后 `py_compile` 通过。

#### 目标 3：加拿大暂无线路的 5 站，先用离线样本往前推

- **目标**：不等线路，先把 spec 做出来——bestbuy_ca / walmart_ca / costco_ca / visions_ca / canadiantire_ca。
- **怎么实现**：用**离线 HTML 样本**（页面另存 / 历史留档）走 `retail-schema-gen` 的 Step1~Step3，产出并校验 RetailSpec；`regions_config.py` 中保持 `enabled=False` 不抓取，线路到位即可直接开跑。
- **验收**：5 份 spec 过静态校验 + 在离线样本上选择器命中；数据入库前明确标注"待联网验证"（不把离线验证当联网通过）。

#### 目标 4：SPEC 线补齐生产化能力（P1 四件套）

- **目标**：从"能抓"到"能无人值守"。
- **怎么实现**：① 落地 `adapter_spec` / `onboard_run` 库表——schema 入库可回滚、失败现场可复现；② 实现 `spec-health` 定期探测，让改版从"不可测"变 ≤7 天检出；③ Verify 补规格质量实测（规格非空率、每型号规格行数）；④ 合规白名单 + robots 准入落到抓取前置。
- **验收**：schema 持久化率 100%；人为改坏选择器后 `spec-health` 能检出并告警、exit code 区分健康/告警；未登记域名被抓取前明确拒绝。

#### 目标 5：用真实难站验证"新引擎能否替代手写适配器"

- **目标**：证明配置驱动在难站（多级发现 / 接口发现 / 参数分页）上找全率不输手写适配器，或明确哪些站仍需手写。
- **怎么实现**：松下、夏普（多级发现）与 TCL / Samsung / LG（`xhr_api` / `query_param`）用新引擎跑真实站；对照基线取现有手写适配器的落库量（如 Samsung CA 64 系列 / 224 型号、LG US 90 系列 / 91 型号）。
- **验收**：**找全率 ≥95%**、守恒率 100%（发现数 = 落库数）、抽 3 个型号每个 ≥8 行规格且键值非空；不达标则记入引擎缺口清单并写明"该站暂需手写"。

#### 目标 6：分支合并与协作规范定死

- **目标**：让"同名资产丢失/覆盖"这类事故不再发生（已出现三次：`__init__.py` 从未入库、`.kiro/` 整段被忽略、Samsung 同名 family 互相覆盖）。
- **怎么实现**：① 人工解 `feature/auto-adapter-p0` 与 `origin/main` 的冲突（两条线都改过 `spec_generator.py` / `generic_spec.py`），**不强推 main**；② 把 `.gitignore` 白名单（`!__init__.py`、`!.kiro/skills/`）与 `__init__.py`、skill 入库写进提交前检查清单；③ 合并后完整跑一遍回归基线。
- **验收**：`git status` 干净、各 `sites/*/__init__.py` 齐全、`git check-ignore` 不再误伤；回归基线（Philips CA / REGZA / Sony / kakaku 条数）数字不变。

### 6.2 依赖外部条件的，边推边等

#### 目标 7：拿到线路后，北美零售从 5 站铺到 18 站

- **前置（唯一前置）**：美国 4 站需美国住宅代理；加拿大 8 站需加拿大线路；墨西哥被拦 2 站需当地线路。**线路是北美零售规模化的唯一前置条件。**
- **怎么实现**：申请到位后按"**先小样、再全量**"——① 每站低频小样（3~5 型号）验证连通性与价格/评价可抽性；② 过红线抽检（零误匹配）；③ 再按 ≤35 型号分批 + 12 秒间隔 + 批间冷却铺开；④ 站级熔断作为兜底（连续 5 个被拦即停）。
- **验收**：单站小样通过（零误匹配 + 价格填充率 ≥95%）才允许开全量；开站前先改 `regions_config.py` 的 `enabled` 开关。
- **现在的动作**：先把 6.1 中不依赖网络的部分做完，**拿到线路前不做无谓的连通性重试**（有熔断兜底，但仍浪费时间）。

#### 目标 8：CQC 与平台上报落地

- **前置**：管理员注册 `cert_verify` agent、下发专用 API Key、审批 `cmsent` 资源；拿到 `cmsent` 接口定义。
- **怎么实现**：① 同步推动"注册 + 密钥 + 资源审批"三件事；② 拿到接口定义后实现按证书号取数的 provider，接入核对流程作为权威数据源；③ 服务器 `.env` 配置 `PAP_*` 后重启，完成真实上报验证。
- **验收**：真实授权跑通一次并取到 cmsent 数据；平台侧能查到 `cert_verify` 的 register / usage 记录，且 `benefit_minutes` 与"完成行数 × 3"一致。

### 6.3 能常态化的，就让它自己转

#### 机制 1：日本线按周刷新 + 规格改版自动对比

- **实现**：systemd timer 每周日 03:20 执行 `spec-crawl` + `spec-export`（超时 3 小时），失败走 `refresh_spec_resume.py` 断点续跑；周快照之间 diff 出"新增 / 删除 / 改值"。
- **判据**：刷新后中文覆盖率仍 100%、表头与型号数校验通过；改版差异有清单可查。

#### 机制 2：上线前红线抽检，零误匹配才放行

- **实现**：零售站上线前必抽 20 个已匹配商品做匹配准确率抽检（`on_no_match` 必须 `skip`，**禁止改成 `first` 冲覆盖率**）；SPEC 站按"找全率 ≥95% + 守恒 + 规格质量 + 回归基线 + 经验沉淀"清单验收。
- **判据**：抽检零误匹配；任一项不达标不进交付。

#### 机制 3：每接一个站，强制回写经验

- **实现**：`cases.jsonl` 追加一条 + 必要时更新 `reference.md` / playbook，并由 `selfcheck.py` 校验骨架与规范同步。
- **判据**：`selfcheck.py` 全过；每接一个站至少新增 1 条案例——**让"越用越强"不是口号，而是机制。**
