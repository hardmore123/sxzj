## 1. 项目定位与业务背景

- **业务**：银行对公业务，为中小企业客户提供 AI 行业咨询（市场机遇、竞争分析、政策研判、数据洞察），充当 7x24 "首席战略官"。
- **技术定位**：Multi-Agent 深度研究系统。输入行业问题 → 6 个专家 Agent 协作 → 自动完成「规划→检索→分析→绘图→写作→审核」闭环 → 输出结构化研报。
- **核心价值**：将传统 3-5 天的行业研究压缩至 20-40 分钟；碎片信息 → 可追溯、带信源评级、含可视化的专业研报。
- **性能指标（文档记录）**：单次 20-40 分钟、3 层递归搜索、50-100 数据点、2-5 图表、20-40 去重信源、3000-8000 字、单次成本约 ¥0.05。

## 2. 系统架构（四层）

```
前端展示层  React18 + TS + AntD + ECharts（dist/ 预构建，SPA）
        │ HTTP / SSE
API 网关层  FastAPI（52 个接口）：路由 / JWT鉴权 / SSE流式 / CORS
        │
业务逻辑层  多智能体引擎 deep_research_v2/（graph.py + state.py + 6 Agent）
           辅助服务：Text2SQL / 记忆 / 新闻采集 / 知识库
        │
数据存储层  PostgreSQL + Milvus + Redis
```

**后端目录分层**：`config → core → models → schemas → service → router → app_main.py`（标准 Controller-Service 分层）。

## 3. 已实现的功能与设计

### 3.1 六个 Agent（多智能体核心）

| Agent | 职责 | 模型 | temperature |
|---|---|---|---|
| ChiefArchitect 总架构师 | 问题分析、大纲、假设 | deepseek-v3.2 | 0.7 |
| DeepScout 深度侦探 | 搜索、信源评级、递归追溯 | qwen-plus | 0.5 |
| DataAnalyst 数据分析师 | 数据提取、知识图谱、ECharts | deepseek-v3.2 | 0.3 |
| CodeWizard 代码极客 | 代码沙箱、绘图、自愈 | deepseek-v3.2 | 0.3 |
| LeadWriter 首席笔杆 | 逐章撰写、整合、引用 | deepseek-v3.2 | 0.7 |
| CriticMaster 审核大师 | 对抗审核、评分、路由 | deepseek-v3.2 | 0.5 |

### 3.2 协作机制（已实现）

- **黑板模式（Blackboard）**：6 Agent 不直接通信，全靠读写共享的 `ResearchState`（TypedDict），由 `graph.py` 按 `phase` 字段驱动接力。
- **状态机流转**：`INIT→PLANNING→RESEARCHING→ANALYZING→WRITING→REVIEWING→(RE_RESEARCHING/REVISING)→COMPLETED`。
- **消息双写**：`add_message` 既写 `state["messages"]`（可回溯）又塞 `asyncio.Queue`（实时 SSE 推送）。
- **自研执行器**：定义了 LangGraph 但**注释不用**，实际走手写 `_run_simplified`——因为 LangGraph 的 `astream` 只能节点级批量输出，做不到逐条实时流式 + 检查点 + 取消。
- **三路智能路由**：Critic 审核后写 `unresolved_issues`/`critic_feedback`，调度器据此决定 complete / re_research（补搜） / revise（改文字）。

### 3.3 其他已实现能力

- **假设驱动研究**：Architect 先生成 H1/H2/H3，Scout 检索时标注支持/反驳。
- **信源评级**：0-1 分级（官方 0.9-1.0 / 学术 0.8-0.95 / 媒体 / 自媒体 0.2-0.5），仅采纳 >0.6。
- **信源追溯**：遇"据 XX 统计"自动生成追溯查询。
- **双模检索**：Bocha 全网搜索 + Milvus 本地知识库。
- **数据可视化**：ECharts 配置（DataAnalyst）+ Python 沙箱绘图（CodeWizard）。
- **代码沙箱**：正则黑名单（FORBIDDEN_PATTERNS）+ 模块白名单（ALLOWED_MODULES）+ exec；失败 LLM 自愈最多 3 次。
- **四级降级 JSON 解析**（base.py:parse_json_response）：直接解析 → markdown 代码块提取 → 抓最外层 `{}` → ast.literal_eval；修转义/尾逗号/缺引号 key；对 `code` 字段跳过转义修复。
- **扁平化 JSON schema**：Architect 规划 prompt 用 `sec_1_title/sec_1_desc/...` 扁平键值，Python 侧 `_convert_flat_to_outline` 重组——规避 LLM 嵌套输出不稳。
- **SSE 流式**：FastAPI StreamingResponse + asyncio.Queue，多类型事件（phase/thought/action/observation/search_results/chart/section_content 等 10+ 类）。
- **检查点续跑**：Redis（24h TTL）+ PostgreSQL 双写，存后端 state + 前端 ui_state；ui_state 用"只增不减"策略防冲刷。
- **长期记忆**（memory_service，服务普通聊天非研究流程）：超 10K token → LLM 压缩成 {summary, key_insights, user_preferences, topics} → 多粒度向量化存 Milvus → 语义召回；压缩率约 96%（文档数字）。
- **Text2SQL**（v1，text2sql_service.py，真实现）：NL→SQL + 安全校验（禁 DELETE/DROP）。
- **定时采集**：APScheduler 采新闻/招投标。
- **认证**：JWT + bcrypt（部署时实测跑通 register/login/鉴权）。

## 4. 本地部署记录（Docker-free）

> 环境约束：Windows 11、7.9GB RAM、**BIOS 虚拟化(VT-x)关闭** → Docker Desktop 不可用。故改为原生部署。

### 4.1 部署结果

| 组件 | 状态 | 说明 |
|---|---|---|
| PostgreSQL 15.18 | ✅ 运行 :5432 | Windows 服务，14 张表自动建好 |
| Redis 7.4.2 | ✅ 运行 :6379 | 便携版 |
| Backend FastAPI | ✅ 运行 :8000 | 52 接口注册成功 |
| Frontend | ✅ 运行 :5183 | 静态托管 dist/，SPA 回退 |
| Milvus | ❌ 未运行 | 需 Linux/Docker；知识库+长期记忆不可用，深度研究(web)不受影响 |

- 已验证：注册 → 登录 → JWT 鉴权 → 数据落库全链路（FastAPI + SQLAlchemy + PostgreSQL + bcrypt + JWT + Redis 打通）。

### 4.2 部署踩坑与解决

1. **Python 版本**：本机 3.14 无 cp314 wheel（pymilvus/numpy/psycopg2）→ 装 Python 3.12.10 建独立 venv。
2. **llama-index 装不上**：清华镜像 403 + pip 先解析后安装 → 分 13 组阶梯安装 + 阿里/清华/官方三级降级；llama-index 换成 llama-index-core。
3. **GitHub 被墙**：Redis 下载改用 ghfast.top 镜像。
4. **Redis 协议不兼容**：redis-py 8.1.0 用 RESP3 HELLO 握手，Redis 5 不认（unknown command HELLO）→ 升级 Redis 7.4.2（也对齐 compose 的 redis:7）。
5. **前端源码缺失**：`frontend/src/` 不存在，`npm run dev` 必败；改为静态服务器托管预构建 `dist/`（bundle 内烧死 localhost:8000，后端 CORS=*，可用）。

### 4.3 硬阻塞：两个 API key 失效

- `DASHSCOPE_API_KEY`：401 Incorrect API key（两个端点都验过，是 key 本身问题）。
- `BOCHA_API_KEY`：403 无余额（key 有效但没配额）。
- 后果：6 个 Agent 调不了 LLM，Scout 搜不到。**基础设施就绪，换 key 即可用。**

### 4.4 配置修正建议

- `DASHSCOPE_BASE_URL` 被改成了 `coding.dashscope.aliyuncs.com`（无 embeddings 接口，返 404），应改回 `https://dashscope.aliyuncs.com/compatible-mode/v1`。
- 三个 base_url 变量名不一致（`LLM_BASE_URL` / `DASHSCOPE_BASE_URL` / `OPENAI_BASE_URL`），建议在 .env 显式统一。
- `dr_g.py` 硬编码了真实格式的 API key 作为兜底默认值 → 应改空串（凭据泄漏）。

## 5. 关键设计思考与工程权衡

| 决策 | 权衡 / 理由 |
|---|---|
| 多 Agent vs 单 Agent | 单 Agent prompt 过长、职责混乱、无法针对性选模型；多 Agent 可分工 + 混合模型 + 出错只重试单 Agent |
| 自研执行器 vs LangGraph 原生 | astream 只能节点级批量输出，做不到实时流式 + 检查点 + 取消 → 自研 asyncio.Queue |
| 黑板模式 vs 点对点通信 | Agent 解耦；新增 Agent 只需约定读写字段；代价是耦合到 state schema |
| 混合模型 | 搜索用快模型(qwen-plus)、推理用强模型(deepseek)，省 ~90% 成本 |
| SSE vs WebSocket | 单向推送够用、浏览器原生自动重连、HTTP 友好 |
| 检查点双写 | Redis 快(24h TTL) + PG 持久化；断点续跑省重复 LLM 调用 |
| 异步 vs 多线程 | IO 密集 + GIL；异步无 GIL 瓶颈、资源省 |
| Milvus + PG 分离 | Milvus 专注向量检索、PG 专注复杂查询；检索时 Milvus 返 doc_id → PG JOIN 详情 |
| 扁平化 JSON schema | LLM 产扁平 KV 远比嵌套对象稳 |

### 关于"是不是 Multi-Agent"的澄清
- "不直接通信" ≠ "不通信"——黑板模式属于**间接通信**，是 MAS 标准范式。
- 判定 Multi-Agent 看：自治性（每个 Agent 独立调 LLM 决策）+ 角色分化 + 协作机制，而非通信方式。
- LangGraph 是**编排工具**，Multi-Agent 是**架构范式**，两者正交。
- 本项目属于**中心化编排型（Supervisor 模式）** Multi-Agent，非去中心化自主协商型。

### 工具层现状（重要）
- **v1**（react_controller.py + tool_executor.py）：有标准 Tool 注册表 + ReAct，封装 8 工具。
- **v2**（多智能体主打版）：**无独立工具层**，能力硬编码在各 Agent 内。
- **未用 MCP，也未用 OpenAI function calling**（尽管课程大纲承诺了 MCP）。

## 6. 已发现的问题与技术债

1. **代码沙箱可逃逸**：正则黑名单可被 `().__class__.__base__.__subclasses__()` 绕过；代码注释自己承认应用 Docker 隔离。
2. **凭据泄漏**：dr_g.py 硬编码真实格式 key。
3. **启动被阻塞**：app_main lifespan 在 yield 前同步跑整轮新闻采集，拖慢启动约 2 分钟。
4. **base_url 变量名不一致**：导致 embedding/记忆走了错误端点。
5. **LLM 调用层无统一重试/熔断/降级**：课程文档讲了 Retry/CircuitBreaker/Fallback/DLQ，但**代码未实现**（仅"实现建议"）。
6. **SFT 微调**：仅示例代码，无真实数据/训练/评估。
7. **无评测 harness**：只有手动 test 脚本，无基准/打分/回归框架。
8. **compose 文件重复**：根目录一份、backend 一份。
9. **Docker 化只做一半**：中间件有 compose，但后端 Dockerfile 悬空未被引用、前端无 Dockerfile。

## 7. 规划中的改造：统一工具层 + MCP Server

> 完整 spec 位于 `.kiro/specs/mcp-tool-layer/`（requirements.md + design.md + tasks.md）。

### 7.1 改造目的

解决 v2 "能力硬编码、无法复用、无法对外" 的架构缺陷：
1. **解耦与复用**：能力从 Agent 私有 → 独立 Tool，任何 Agent/外部系统可调用。
2. **横切集中治理**：重试/超时/缓存/日志/指标收敛到 ToolInvoker 一处（DRY）。
3. **开闭原则**：新增工具零侵入，不改调用方。
4. **平台化对外**：封装 MCP Server，任意 MCP 客户端可发现调用，补齐课程承诺的 MCP。

### 7.2 规划的 6 个工具

| 工具 | 包装能力 | 缓存 |
|---|---|---|
| WebSearchTool | Bocha 搜索 | ✅ 默认开 |
| WebExtractTool | trafilatura | ✗ |
| VectorSearchTool | Milvus + embedding | ✅ 默认开 |
| SandboxTool | 代码沙箱 + 子进程隔离 | ✗ |
| ChartTool | matplotlib/ECharts | ✗ |
| StockQueryTool | 股票 API | ✗ |

### 7.3 规划的组件

- **BaseTool**（抽象）→ **ToolRegistry**（注册/发现）→ **ToolInvoker**（横切：校验/重试/超时/缓存/日志/指标/错误归一）→ 具体 Tool。
- **ToolClient**：Agent 侧灰度适配（Feature_Flag 决定走工具层还是旧实现）。
- **MCP Server**：官方 mcp SDK，Registry→MCP 自动映射，stdio(默认)+SSE/HTTP 双传输，Bearer Token 鉴权。
- **沙箱子进程隔离**：跨平台（POSIX setrlimit / Windows Job Objects / psutil 轮询降级）+ 内存/CPU 上限 + 禁网。

### 7.4 关键决策（已确认）

| 决策点 | 结论 |
|---|---|
| 能力清单 | 5 核心 + stock_query；text2sql/招投标不纳入本次 |
| 缓存范围 | 搜索类默认开，其余默认关 |
| 沙箱隔离 | MCP 暴露时必须子进程隔离 + 内存/CPU/禁网 |
| MCP 传输 | stdio 默认 + SSE/HTTP |
| 鉴权 | 网络传输 Bearer Token |
| 性能上限 | Tool_Invoker 附加开销 ≤50ms |

### 7.5 设计原则

- 行为等价（重构非重写，SSE/流程不变）
- 开闭原则（新增工具零侵入）
- Feature_Flag 灰度（可回退、单工具失败不中断）
- 两级安全（进程内轻校验 / MCP 暴露重隔离）
- 26 条正确性属性 + Hypothesis 属性测试（每条 ≥100 迭代）

### 7.6 现状 vs 规划

```
现状 v2:  Agent ──直接硬编码调用──> Bocha/Milvus/exec/matplotlib（能力私有、无复用、无 MCP）

规划:     Agent ──ToolClient(灰度)──> ToolInvoker ──> ToolRegistry ──> 6个Tool ──> 底层能力
          外部MCP客户端 ──> MCP Server ──┘（stdio/SSE + Bearer鉴权）
```

- ❌ 单列设计模式（工厂/单例/策略）→ 显初级，留作面试谈资

### 9.4 差异化资产（最该突出、别人写不出）

1. 非标环境部署排障（虚拟化受限、Redis 协议、依赖 wheel、配置 bug）
2. "为什么弃用 LangGraph 原生流"的技术选型权衡
3. 识别 v2 能力硬编码的架构缺陷并主导工具层/MCP 重构
4. 26 条正确性属性的可验证质量意识

### 9.5 核心原则

> 简历的杀伤力不在于堆了多少亮点，而在于**说的每一句都能被追问到底**。
> "只讲设计不讲实现"的边界：**架构类**决策可以纯讲设计（价值在结构和权衡）；**需要数据/训练/调优验证**的（SFT、百分比、熔断阈值）不能只写设计，否则一问实测就穿。
