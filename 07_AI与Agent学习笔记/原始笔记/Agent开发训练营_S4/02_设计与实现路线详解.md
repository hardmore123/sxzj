## 1. 统一工具层（Tool Layer）

### 目标
把散落在各 Agent 里的能力（搜索/解析/检索/代码执行/绘图/股票）抽象为统一 Tool，集中治理横切能力，支持零侵入扩展。

### 当前效果
能力硬编码在 Agent 方法内（scout._execute_search、wizard._execute_in_sandbox…），无复用、无统一治理、加能力要改 Agent 源码。

### 实现工具与方式
- 语言：Python 3.12；`abc.ABC` 抽象基类、`dataclass` 数据结构、`asyncio` 异步执行。
- 组件：`BaseTool`（抽象）+ `ToolRegistry`（注册表）+ `ToolInvoker`（横切）+ 具体 Tool。
- Schema 校验：JSON Schema（`jsonschema` 库）或 Pydantic。

### 备选路线

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. 自研 Tool 抽象（推荐）** | 自定义 BaseTool + Registry + Invoker | 完全可控、贴合黑板架构、无额外重依赖、易加横切 | 需自己写注册/校验/横切逻辑 |
| B. 复用 v1 的 Tool 框架 | 沿用 react_controller 的 Tool dataclass | 项目已有、改动小 | v1 是 ReAct 范式，与 v2 黑板不契合；无异步/横切治理 |
| C. LangChain Tool | `langchain.tools.BaseTool` | 生态成熟、与 function calling 打通 | 引入重依赖、与自研编排冲突、过度封装 |
| D. OpenAI function calling schema | 直接用 LLM 的 tools 参数 | 标准、LLM 原生支持选工具 | 需模型支持；把"选工具"交给 LLM，弱化了确定性编排 |

**Schema 校验子选型**：
- Pydantic：类型安全、报错友好、与 FastAPI 一致 → **推荐**。
- jsonschema：轻、纯 JSON Schema，但报错不如 Pydantic 友好。

**推荐**：路线 A + Pydantic。理由：贴合现有黑板架构、无重依赖、横切能力可完全定制、满足开闭原则。

## 2. MCP Server 封装

### 目标
把工具层暴露为标准 MCP 服务，任意 MCP 客户端可发现调用。

### 当前效果
无 MCP，能力仅本进程可用。

### 实现工具与方式
- 官方 `mcp` Python SDK（`mcp.server.Server`）。
- Registry → MCP 工具自动映射（`@server.list_tools` / `@server.call_tool`）。

### 备选路线（传输方式）

| 路线 | 传输 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. stdio（默认，推荐先做）** | 标准输入输出 | 最简单、本地进程接入、无网络/鉴权负担 | 仅本机、单客户端 | 本地集成、Claude Desktop |
| B. SSE | Server-Sent Events | 支持远程、浏览器友好、与现有 SSE 技术栈一致 | 单向、需鉴权 | 远程只读式工具调用 |
| C. Streamable HTTP | HTTP 流 | 远程、双向、可负载均衡 | 实现最复杂、需完整鉴权 | 生产多客户端 |

### 备选路线（鉴权）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. Bearer Token（推荐）** | 请求头 Authorization: Bearer | 简单、无状态、够用 | 需安全下发 token |
| B. mTLS | 双向证书 | 最强、适合服务间 | 证书管理复杂 |
| C. OAuth2 | 授权服务器 | 标准、可细粒度授权 | 重、需额外基础设施 |

### 备选路线（部署形态）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. 独立进程 MCP Server（推荐）** | 单独启动 `python -m ...mcp.server` | 与主应用解耦、可独立扩缩 | 需进程管理 |
| B. 挂载到现有 FastAPI | ASGI 子应用 | 复用现有端口/中间件 | 与主应用耦合、共享故障域 |

**推荐**：stdio 先做（验证 + Claude Desktop 演示），再加 SSE/HTTP + Bearer Token；MCP 独立进程部署。

## 3. 代码执行沙箱隔离

### 目标
安全执行 LLM 生成的 Python 代码（绘图/计算），防逃逸、限资源。

### 当前效果
正则黑名单（FORBIDDEN_PATTERNS）+ 模块白名单 + `exec`。**可被 `().__class__.__base__.__subclasses__()` 逃逸**，无资源限制，代码注释自认应上 Docker。

### 备选路线（隔离强度递增）

| 路线 | 方式 | 优点 | 缺点 | 安全等级 |
|---|---|---|---|---|
| A. 正则黑名单（现状） | 正则匹配危险模式 | 零依赖、快 | 可绕过、无资源限制 | ★ |
| B. RestrictedPython | AST 级限制内建/属性访问 | 纯 Python、比正则强 | 仍非真隔离、配置复杂 | ★★ |
| **C. 子进程 + 资源限制（推荐，本机可行）** | multiprocessing spawn + setrlimit/Job Objects/psutil | 真进程隔离、可限内存/CPU/禁网、跨平台 | Windows 硬限制打折、有启动开销 | ★★★ |
| D. Docker 容器 | 每次执行起容器 | 强隔离、成熟 | 需 Docker（本机 VT-x 关，不可用）、开销大 | ★★★★ |
| E. gVisor / Firecracker | 沙箱内核/微 VM | 最强隔离 | 需 Linux + 运维、重 | ★★★★★ |
| F. 云端代码执行服务 | E2B / Judge0 等 | 免运维、强隔离 | 依赖外部、成本、延迟 | ★★★★ |

### 子进程路线（C）的跨平台细节

| 限制项 | POSIX | Windows（无 Docker）|
|---|---|---|
| 内存 | `resource.setrlimit(RLIMIT_AS)` | Job Object（pywin32）或 psutil 轮询 kill |
| CPU 时间 | `resource.setrlimit(RLIMIT_CPU)` | Job Object 或 wall-clock 超时兜底 |
| 禁网 | socket 桩 + 黑名单 | socket 桩 + 黑名单（无 namespace）|
| 墙钟超时 | `proc.join(timeout)` + kill | 同左 |

**降级链**：Job Object/setrlimit 不可用 → psutil 轮询内存 + wall 超时 → 仅 wall 超时 + 静态黑名单（日志标注"硬限制未生效"）。

**推荐**：进程内保留 A（低开销默认）+ 对外经 MCP 时用 C（子进程隔离）。生产环境若有 Linux/Docker 再上 D。本机因 VT-x 关闭无法用 D，C 是当前最优。

## 4. 外部依赖容错体系

### 目标
LLM/搜索 API 不稳时，系统不雪崩、能降级、单点失败不中断主流程。

### 当前效果
课程文档讲了 Retry/CircuitBreaker/Fallback/DLQ，但**代码仅"实现建议"**，实际只有 Wizard 的代码自愈重试。

### 备选路线（按需组合）

**4.1 重试**

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. 指数退避重试（推荐）** | `tenacity` 库或自研 | 成熟、可配退避/抖动 | 需防重试放大故障 |
| B. 固定次数重试 | 简单循环 | 最简单 | 无退避易加剧拥塞 |

**4.2 熔断**

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. pybreaker（推荐若要做）** | 三态熔断器库 | 现成、标准三态 | 需调阈值、增加复杂度 |
| B. 自研计数窗口 | 滑动窗口失败率 | 可控、无依赖 | 要自己写状态机 |
| C. 不做熔断 | 仅重试+降级 | 简单、够用 | 持续故障时浪费重试 |

**4.3 降级（Fallback）**

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. 模型降级（推荐）** | deepseek 失败切 qwen | 保可用、贴合混合模型策略 | 降级模型质量略降 |
| B. 缓存降级 | 返回上次缓存结果 | 快 | 数据可能过时 |
| C. 跳过降级 | 该工具失败则跳过、流程继续 | 保主流程 | 结果不完整 |

**4.4 死信队列（DLQ）**

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. Redis List/Stream | 失败任务入队 | 复用现有 Redis、轻 | 功能弱于专业 MQ |
| B. RabbitMQ/Kafka | 专业消息队列 | 功能全、可靠 | 重、需运维 |
| C. 不做 DLQ | 失败即记录日志 | 简单 | 无自动重放 |

**推荐（务实组合）**：tenacity 指数退避重试 + 模型降级（A）+ 工具级跳过降级（C）。**熔断和 DLQ 除非有真实高并发场景，否则不做**——避免过度设计。简历只写"重试+降级"这类真做了的，别吹熔断/DLQ。

## 5. 缓存

### 目标
降低重复 LLM/搜索调用成本，加速重复查询。

### 当前效果
Scout 有进程内内存字典 `search_cache`（MD5 键），非分布式、进程重启即失。

### 备选路线

| 路线 | 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 进程内字典（现状） | dict + MD5 键 | 零依赖、最快 | 不共享、重启丢失、无 TTL | 单机单进程 |
| B. 进程内 + TTL | `cachetools.TTLCache` | 有过期、仍快 | 不共享 | 单机 |
| **C. Redis 缓存（推荐）** | Redis setex | 跨进程共享、有 TTL、持久 | 需 Redis（已有）、有网络开销 | 多 worker/生产 |
| D. 两级缓存 | 进程内 L1 + Redis L2 | 快 + 共享 | 实现复杂、一致性问题 | 高并发 |

**缓存键设计**：`f"{tool_name}:{sha256(canonical_json(params))}"`（纳入工具名防碰撞，规范化 JSON 防顺序差异）。

**推荐**：升级到 C（Redis）——项目已有 Redis，能真实写"分布式缓存"，且解决进程重启失效问题。高并发再考虑 D。

## 6. 多智能体流式执行引擎

### 目标
6 Agent 编排 + 实时流式输出 + 检查点 + 取消。

### 当前效果
定义了 LangGraph 但注释不用，实际走自研 `_run_simplified`（asyncio.Queue）。

### 备选路线

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. 自研 asyncio.Queue（现状/推荐）** | 手写阶段机 + 队列 | 真逐条实时流式、支持检查点/取消、完全可控 | 代码量大（~360行）、逻辑集中 |
| B. LangGraph 原生 astream | 官方状态机 | 声明式、少代码、社区支持 | 只能节点级批量输出、做不到实时逐条 + 检查点 + 取消 |
| C. LangGraph + 自定义 streaming | astream_events + 回调 | 兼顾框架 + 部分实时 | 仍受框架事件粒度限制、复杂 |
| D. Temporal/Prefect 工作流引擎 | 专业工作流编排 | 持久化/重试/可视化强 | 极重、学习曲线陡、杀鸡用牛刀 |

**推荐**：维持 A（自研）。这正是本项目最有含金量的技术选型——"评估 LangGraph 后因 astream 局限自研"。可优化点：把 360 行的 `_run_simplified` 拆分（阶段/路由/检查点/流式分离），提升可维护性。

## 7. 长期记忆与向量化

### 目标
长对话压缩沉淀 + 跨会话语义召回。

### 当前效果
超 10K token → LLM 压缩 {summary/insights/preferences/topics} → 多粒度向量化存 Milvus → 召回。压缩率约 96%（文档数字）。

### 备选路线（向量化粒度）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. 整体摘要向量化 | 一条摘要一个向量 | 简单、省存储 | 召回粒度粗、丢细节 |
| **B. 多粒度（摘要/洞察/主题，现状/推荐）** | 每类独立向量 | 精细召回、多角度匹配 | 存储/embedding 调用多 |
| C. 原始分块向量化 | 不压缩直接切块存 | 不丢信息 | token 爆炸、成本高 |

### 备选路线（embedding 效率）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. 逐条 embedding（现状） | N 次 API | 简单 | 慢、API 调用多 |
| **B. 批量 embedding（推荐优化）** | 一次批量请求 | 快、省调用 | 需接口支持 batch |

### 备选路线（召回策略）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. 固定 Top-K | 取前 K | 简单 | 可能召回低质 |
| B. Top-K + 相似度阈值 | 过滤 score<阈值 | 质量高 | 阈值需调 |
| **C. + 时间衰减（推荐）** | score × exp(-Δt/半衰期) | 新记忆优先、符合直觉 | 需调半衰期 |

**推荐**：粒度维持 B；embedding 改批量（B）；召回用 B+C。

## 8. RAG 分块与检索策略

### 目标
提升垂直领域内部资料的检索精度与召回率。

### 当前效果
文档称 500-1000 字/块带重叠；Milvus IVF_FLAT + COSINE。

### 备选路线（分块）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. 固定长度分块 | 按字符/token 切 | 简单、快 | 可能切断语义 |
| **B. 带重叠固定分块（现状/推荐起点）** | 滑窗重叠 | 保上下文连续 | 冗余存储 |
| C. 语义分块 | 按句/段/语义边界 | 语义完整 | 需额外模型、慢 |
| D. 父子分块 | 小块检索、大块喂 LLM | 精准检索 + 完整上下文 | 实现复杂 |

### 备选路线（索引）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. IVF_FLAT（现状） | 倒排 + 精确 | 精度高、易用 | 大规模慢 |
| B. HNSW | 图索引 | 快、高召回 | 内存占用大 |
| C. IVF_PQ | 量化压缩 | 省内存 | 精度略降 |

### 备选路线（检索增强）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. 纯向量检索 | 语义相似 | 简单 | 关键词精确匹配弱 |
| **B. 混合检索（推荐）** | 向量 + BM25/标量过滤 | 语义+精确兼顾 | 需融合排序 |
| C. + Rerank | Cross-Encoder 重排 | 精度最高 | 慢、需 rerank 模型（项目有 DashScope rerank）|

**重要提醒**：分块粒度与召回精度**非单调正相关**，切太细丢上下文反而降质量。简历别写"500字符大幅提升召回"，应表述为"带重叠分块平衡上下文与精度"，并用实验（召回率@k 对比）支撑。

**推荐**：分块 B 起步、可选 D；索引数据量大转 HNSW；检索用 B + 可选 C（项目已有 rerank 能力）。

## 9. 评测 Harness

### 目标
可量化验证系统正确性/质量，支持回归——当前**完全缺失**（只有手动 test 脚本）。

### 当前效果
无基准、无打分、无回归框架。

### 备选路线

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A. 属性测试（Hypothesis，推荐做核心逻辑）** | 生成大量输入验证不变量 | 覆盖广、发现边界 bug、体现质量意识 | 需定义好属性 |
| B. 固定用例集 + LLM 打分 | N 条 query + LLM-as-judge | 贴近真实、可比 | LLM 打分有噪声 |
| C. 黄金标准对比 | 人工标注参考答案 | 最准 | 标注成本高 |
| D. 指标采集 + 看板 | Prometheus/日志聚合 | 生产可观测 | 需基础设施 |

**推荐**：
- 工具层核心逻辑（注册/缓存/重试/校验/MCP 一致性）→ **A（Hypothesis，26 条属性）**，投入产出比最高、区分度最强。
- 研究质量 → B（小规模 LLM-as-judge）。
- 生产 → D（后期）。

## 10. 部署方案

### 目标
把系统跑起来（前后端 + 中间件）。

### 当前效果
本机 VT-x 关闭、无 Docker，已用原生部署跑通（PG15 + Redis7 + 后端 + 前端静态托管；Milvus 缺失）。

### 备选路线

| 路线 | 方式 | 优点 | 缺点 | 本机可行 |
|---|---|---|---|---|
| A. Docker Compose（官方） | 一键起 6 中间件 | 环境一致、标准 | 需 Docker（VT-x 关，不可用）；8GB 内存吃紧 | ❌ |
| **B. 原生部署（现状）** | PG/Redis 服务化 + 后端 venv + 前端静态 | 无需虚拟化、内存省 | 手动装、Milvus 装不了 | ✅ |
| C. WSL2 + Docker | 开 VT-x → WSL2 → Docker | 接近生产、能跑 Milvus | 需重启开 BIOS、内存更吃紧 | 需改 BIOS |
| D. 云服务器 | 租 Linux 云主机 | 全组件可跑、演示稳 | 花钱 | ✅（需付费）|

### 补全 Docker 化（若走 A/C）

| 待补 | 方式 |
|---|---|
| 后端 Dockerfile | 已有但悬空，需接进 compose 的 build |
| 前端 Dockerfile | 缺失，写 nginx 静态镜像 |
| compose 去重 | 根目录 + backend 两份合一 |

**推荐**：学习/演示阶段用 B（现状，已跑通）；要完整体验知识库+记忆 → C（开 BIOS 虚拟化）或 D（云主机）。想要简历"Docker 全栈容器化"可信 → 补全后端/前端 Dockerfile（文件可移植，有 Docker 的机器即可 `compose up`）。

## 11. Agent 能力微调（SFT）

### 目标
用领域数据微调基础模型，提升工具调用/规划准确性。

### 当前效果

### 备选路线

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. 全参微调 | 训练全部参数 | 效果上限高 | 需大显存、成本高 |
| **B. LoRA/QLoRA（推荐若做）** | 低秩适配 | 省显存、快、可多适配器 | 效果略低于全参 |
| C. 不微调，靠 prompt | few-shot/优化 prompt | 零训练成本、灵活 | 上限受限、token 开销 |

**工具**：LLaMA-Factory / trl（框架）、评估用 BLEU/ROUGE + 人工/LLM 打分。

**现实建议**：**除非有 GPU 且时间充裕，否则不做，简历删除 SFT**。它是深挖必崩的高危项（面试官会问数据量/base model/学习率/前后对比数字）。真要做走 B（LoRA），哪怕 200 条数据跑通拿到 loss 曲线也比纸面强。

## 12. 路线选择总表

| 功能 | 推荐路线 | 一句话理由 | 本机可行 |
|---|---|---|---|
| 工具层 | 自研 BaseTool + Pydantic | 贴合黑板、无重依赖、可定制横切 | ✅ |
| MCP 传输 | stdio 先做 + 后加 SSE/HTTP | 先验证再扩展 | ✅ |
| MCP 鉴权 | Bearer Token | 简单够用 | ✅ |
| 沙箱隔离 | 进程内轻校验 + MCP 时子进程隔离 | 本机无 Docker 的最优解 | ✅ |
| 容错 | tenacity 重试 + 模型降级 + 跳过降级 | 务实，不过度设计 | ✅ |
