# 第12课：AI Agent（上）——Agent的本质与运作原理

## 一、实战场景导入：一个“不聪明”的助手 vs “真正智能”的Agent（10分钟）

**目标**：通过对比冲击，建立对Agent价值的具象认知

- **反例演示（非Agent）** ：直接问GPT“帮我预订下周三去上海出差，预算1500元以内的酒店”，模型因为无法联网、无法操作App，只能给出通用建议（如“建议打开携程搜索”）。
- **正例演示（Agent）** ：真正的Agent接收指令后，自主执行：
  1. 调用**日历工具**查看下周三是否有会议冲突；
  2. 调用**差旅API**查询公司报销标准（确定1500元是否合规）；
  3. 调用**航班/酒店搜索工具**筛选符合条件选项；
  4. 调用**邮件工具**将备选方案发送给领导审批。
- **引导思考**：为什么传统LLM做不到这一点？差在哪里？

## 二、核心公式深度拆解：Agent = LLM + 工具 + 循环（20分钟）

**目标**：不仅记住公式，还要理解每个组件的“不可替代性”和“内部机理”

### 1. LLM在Agent中的本质角色——从“生成器”变为“调度器”

- **原理深挖**：在普通对话中，LLM的损失函数是**Next-Token Prediction**（预测下一个词）。在Agent架构中，LLM被微调为**Action Selector**（行为选择器），其输出的概率分布不再指向“词语”，而是指向 **“工具ID” + “参数JSON”** 组成的动作空间（Action Space）。
- **核心机制**：通过**System Prompt约束** + **Few-shot范例**，将LLM的推理能力锚定在“MDP（马尔可夫决策过程）”框架中——当前状态（State）下，选择能够最大化预期回报（Reward）的动作（Action）。
- **具体实例**：Agent内部推理日志（ReAct风格）展示——`Thought: 用户要订酒店，我需要先知道差旅标准，再调用搜索API。`

### 2. 工具（Tools）的本质——LLM的“传感器”与“执行器”

- **哲学层面**：纯粹的语言模型活在“文本空间”，而工具让LLM得以感知“物理/数字世界”并施加影响。
- **技术边界**：工具的核心是**确定性函数**（Deterministic Functions）。凡是能通过代码保证100%准确率的事（如加减乘除、数据库查询、发送HTTP请求），都必须交给工具，绝不依赖LLM的“猜测”。
- **实例说明**：计算“198*7.5%”时，LLM直接回答可能出错，但Agent调用`Calculator`工具返回`14.85`，这是确定性保障。

### 3. 行动循环（Agent Loop）——编程视角的“While True”与哲学视角的“知行合一”

- **技术原理**：Agent的运行态是一个永不退出的**事件循环（Event Loop）**，每次迭代消耗一次LLM推理的TTFT（首Token延迟）。
- **终止条件（Halting Problem）**：Agent如何知道该停下来？原理上通过三类机制：
  - **硬限制**：最大迭代步数（如10步）或最大Token数；
  - **软信号**：LLM在思考后输出`Final Answer`标志位；
  - **功能判定**：工具返回特定状态码（如`task_completed: true`）。

## 三、行动循环的微观解剖：Thought → Action → Observation（25分钟）

**目标**：把循环拆成细胞级精度的案例分析

### 场景案例：帮用户预订“下周三北京到上海的往返机票”

| 轮次      | 思考（Thought）                                              | 行动（Action）                                               | 观察（Observation）                                    |
| :-------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------- |
| **第1轮** | “不知道具体日期，先获取当前日期并推算下周三”                 | 调用`get_current_date()`                                     | 返回 `2026-07-15（周三）` -> 推算目标日为 `2026-07-22` |
| **第2轮** | “日期有了，查询当天早班机（去）和晚班机（回）”               | 调用`search_flights(departure="北京", arrival="上海", date="2026-07-22")` | 返回 12个航班列表（含价格、时间、航司）                |
| **第3轮** | “列表里最便宜且时间合适的航班是MU5102，需要预订，但用户没给身份证号” | 调用`ask_user_clarification(question="请提供乘机人身份证号")` | 用户输入身份证号                                       |
| **第4轮** | “信息齐备，执行下单，并生成行程单摘要”                       | 调用`book_flight(flight_no="MU5102", id_number="...")`       | 返回 `预订成功，订单号：XYZ123` -> **终止循环**        |

### 原理深挖：为何“观察”不是简单的“返回”？

- **观察（Observation）的深层作用**：它不仅携带结果，还携带**状态转移信息**。例如机票价格超出预算时，观察结果包含`price_limit_exceeded: true`，这会直接改变下一轮的**状态空间**，促使Agent从“预订模式”切换为“替代方案搜索模式”（如改签高铁）。

## 四、深度辨析：究竟什么样的系统才配叫“Agent”？（10分钟）

**目标**：用严格的学术定义排查市面上80%的伪Agent

- **伪Agent 1：工作流（Workflow）**
  - 特点：流程图写死（A→B→C），LLM只负责中间某一环的文本生成。
  - 判定标准：**是否具备路由自由度**。如果LLM无法选择跳过B步骤直接执行C，它就是工作流，不是Agent。
- **伪Agent 2：单纯加了RAG的聊天机器人**
  - 虽然调用了检索工具，但如果LLM没有“多步推理”和“根据观察修正动作”的过程，只是单次检索+生成，它只是**增强型LLM**。
- **终极判定法则（学术级）**：Agent必须满足 **“感知-规划-行动”闭环**，且**规划模块**可以动态推翻自己上一步的决策。

## 二、工具调用（Function Calling）原理深潜（25分钟）

**目标**：深入模型底层，讲解LLM如何“学会”调用工具，而不仅是“使用”工具

### 1. 模型底层的训练机制

- **原理深挖**：通用LLM（如GPT-3.5）不具备工具调用能力。OpenAI专门构造了包含 **<function_call>** 特殊Token的训练数据集。微调时，模型学习到：当用户问及实时信息时，输出概率应导向**工具Token**而非普通文本Token。
- **并行调用（Parallel Function Calling）** ：现代Agent支持单次推理返回多个工具调用。原理上，LLM在输出时生成**多个独立的工具调用对象数组**，系统并发执行。

### 2. 调用的全链路报文解剖（实例）

**用户输入**：“帮我查一下上海和深圳明天的天气。”
**LLM原始输出（非人类可读，模拟底层logit输出）** ：

json

```
{
  "tool_calls": [
    {
      "id": "call_abc123",
      "function": { "name": "get_weather", "arguments": "{\"city\": \"上海\"}" }
    },
    {
      "id": "call_def456", 
      "function": { "name": "get_weather", "arguments": "{\"city\": \"深圳\"}" }
    }
  ]
}
```



- **原理深挖**：系统收到此JSON后，**不会**把JSON发给模型，而是**在宿主机（Host）上直接执行Python函数**。模型只负责“口谕”，不负责“动手”。外部系统将结果（如“上海28度晴”）以`tool_response`角色重新注入下一轮对话上下文。

### 3. 工具调用的失败补偿机制

- **实例**：若Agent调用`send_email`工具失败（网络超时），观察（Observation）返回错误码`500`。
- **原理**：Agent的规划模块（LLM）会检测到错误状态，自动切换策略：不重复请求，而是改为调用`generate_offline_report`工具，将行程存为本地草稿，并通知用户。

## 三、规划能力（Planning）的算法级拆解（25分钟）

**目标**：从算法视角（搜索树、图遍历）理解规划，而非停留在“把任务拆成几步”

### 1. ReAct 模式：概率图视角

- **原理深挖**：ReAct不只是“想一步做一步”，其本质是**动态贝叶斯网络（DBN）** 的推理。每步推理`P(Action | Thought, Observation)`在动态变化。
- **关键缺陷与修正**：ReAct容易陷入**循环（Loop）**。解决方案是引入**访问历史哈希**，如果Agent发现某工具参数组合重复出现3次，强制触发`break`并调用`escalate_to_human`。

### 2. Plan-and-Execute vs LATS（树搜索）

- **实例场景**：规划“从北京去上海参加3个不同地点的会议，并赶在晚上回京”。
- **Plan-and-Execute原理**：LLM先生成`[订早班机, 去浦东开会, 去虹桥开会, 去静安寺开会, 订晚班机]`的线性列表。**致命弱点**：若静安寺会议超时，后续全盘崩溃（无法动态调整）。
- **LATS（Language Agent Tree Search）原理（高阶）** ：引入**蒙特卡洛树搜索（MCTS）** 变体。Agent同时模拟“改签晚班机”、“取消最后一站”、“呼叫网约车加速”3条路径，根据**预期延误成本**选择最优分支。讲解时可画一棵简单的**决策树**辅助理解。

### 3. 反思（Reflection）机制的内部原理

- **技术实现**：并非模型权重更新，而是将上一轮完整的`Thought-Action-Observation`链作为**负面样本**拼接进Prompt，要求LLM输出`Critique（批评）`。
- **实例**：Agent第一次订票因未选择“学生票”选项导致价格偏高。反思模块生成批评：“我忽略了用户邮箱后缀是.edu，下次查询需附带`sudent_discount=true`参数”。这一批评会写入短期记忆，直接影响下一轮行动。

## 四、记忆系统（Memory）的物理架构与检索算法（20分钟）

**目标**：讲解记忆不仅是“存起来”，涉及向量检索、注意力衰减和记忆 consolidation

### 1. 短期工作记忆（Working Memory）——Attention机制的数学本质

- **原理深挖**：大模型的上下文窗口就是短期记忆。但它并非无限，其遗忘曲线遵循 **Softmax(Q·K^T)** 的注意力权重分配。距离当前Token越远，其注意力得分受**位置编码（RoPE/ALiBi）** 影响，存在**有效衰减**。
- **实例**：在长达100页的对话中，Agent“忘记”第3页提到的用户姓名。这不是模型蠢，而是注意力分数被后面大量信息**稀释（Dilution）** 了。解决办法是通过**滑动窗口**或**关键信息抽取**（每次循环提取最相关的3个历史实体放入System Prompt）。

### 2. 长期记忆（Long-term Memory）——RAG背后的索引与检索

- **原理深挖（向量数据库）** ：长期记忆依赖Embedding模型将文本映射到高维空间。检索时采用**HNSW（分层可导航小世界图）** 算法，时间复杂度为 O(log N)。
- **具体实例**：用户半个月前说过“我喜欢希尔顿酒店，讨厌如家”。当前Agent预订时，系统将“预算内酒店列表”转为向量，与用户历史偏好向量做**余弦相似度（Cosine Similarity）** 匹配。阈值为0.8时，自动过滤如家，优先希尔顿。
- **写入策略（Memory Consolidation）** ：不是所有对话都存。系统设有**重要性评分器**（另一小模型），只有评分 > 0.7 的事件（如明确偏好、身份证号、重大决策）才会写入长期向量库，防止垃圾信息污染检索准确率。

## 五、终极综合案例：差旅Agent遭遇“突发雷暴”危机（10分钟）

**目标**：整合三大能力，展示复杂场景下的决策链路

- **初始任务**：预订北京-上海出差（已成功）。
- **突发事件（模拟外部输入）** ：起飞前2小时，天气API推送“上海雷暴，航班大面积延误”。
- **Agent响应链路**：
  1. **感知（环境记忆）** ：从短期记忆中提取当前订单号`XYZ123`。
  2. **工具调用**：自动调用`check_flight_status("XYZ123")`，返回“延误至22:00”。
  3. **规划（LATS决策）** ：同时评估三个方案——A. 等待（22:00到上海太晚，赶不上末班地铁）；B. 改签高铁（调用`search_highspeed_train`发现有余票）；C. 退票改明天（调用`calendar`发现明天上午有CEO会议，不可行）。
  4. **执行**：选择B，调用`refund_flight` + `book_train` + `send_sms_notification`（工具并行调用）。
  5. **记忆写入**：将“用户不喜欢红眼航班，遇延误偏好高铁”写入长期记忆，优化未来推荐。

- **终极洞察**：AI Agent本质上是一个**在连续动作空间上进行最大似然估计的决策系统**。它让我们第一次看到LLM从“鹦鹉”进化为“乌鸦”——不仅能模仿，还能**制造和使用工具解决开放性问题**。
- **课后挑战**：思考当Agent拥有**跨会话、跨用户的记忆池**时，隐私与安全边界该如何设计？（为后续高阶课埋点）

1.本质「自主闭环」

2.**普通大模型**vs**Agent**

普通大模型：「知识冻结」「不能行动」「没有持续状态」---每次调用之间它是完全失忆的（知识是死的，手脚是没有的，记忆也是断的）
Agent：核心运作闭环：

**感知 -> 规划 -> 行动 -> 再感知**（持续循环，不断调整，逐步逼近目标）

3.三个核心能力：工具调用、记忆机制、推理与纠错

**工具调用**：「说话」变成「做事」、Agent 能调用外部工具、不是模型自己执行，而是模型「告诉你该调什么」，你的代码去真正执行，结果再反馈给模型。模型始终只是大脑，不是手脚。

**记忆机制**：通常会设计短期记忆和长期记忆两层。短期记忆就是当前任务执行过程中的中间状态，比如第一步搜索到了什么、第二步计算结果是多少，这些都存在上下文里，保证 Agent 不会做到一半忘了前面发生了什么。长期记忆则是跨任务的，比如用户的偏好、历史操作记录，通常用向量数据库来存储，需要的时候做语义检索拿回来。

**多步推理和自我纠错**：「边做边反思」的能力，让 Agent 在面对复杂、不确定的任务时，表现远比死板的自动化流程好得多。

爆发的条件：1.大模型的能力：真的能「读懂」复杂指令并做出合理的多步决策

2.工具调用的标准化：工具调用的标准化，OpenAI 在 2023 年推出了 Function Calling 机制，让模型能以结构化的 JSON 格式输出工具调用请求，开发者才能方便地给模型接上各种外部能力

3.配套生态的完善：LangChain、[LlamaIndex](https://zhida.zhihu.com/search?content_id=789774029&content_type=Answer&match_order=1&q=LlamaIndex&zhida_source=entity) 这些框架把 Agent 的开发门槛大幅降低了，，向量数据库解决了长期记忆的存储问题，各种 API 服务让可调用的工具越来越丰富

**Agent 越来越多，它们之间怎么协作？工具越来越多，怎么统一管理？**

第一个是 Anthropic 在 2024 年底提出的 [MCP]模型上下文协议，你可以把 MCP 理解成 Agent 工具世界的「USB-C 接口」。

在没有MCP之前,每个Agent框架接每个工具都要写一套适配代码,假没有M个Agent框架和
N个工具,就需要MXN套适配逻辑,工程成本非常高。|MCP的做法是定义一套标准的JSON
RPC协议,工具提供方只要按这个标准暴露自己的能力(变成一个MCP Server),任何支持
MCP的Agent(通过内置的MCP Client)都能直接发现和调用这些工具,不需要额外写适配代码。

举例说明：MCP之前，agent框架有各自的调用方式和数据结构，各个工具有自己的api接口，需要写每个的适配代码。M*N.	

MCP之后：M+N:

解决思路：引入一个标准化中间层，流程变为：工具提供方：按照mcp标准，将自己的能力封装成一个MCPsever，懂mcp这个普通话。

agent框架：内置一个mcp client。懂mcp这个普通话。

**langChain 只需要编写一套代码（即它的 MCP Client），就能与任何符合 MCP 标准的 Server 通信**。当有新的工具出现，只需为该**工具**开发一个 MCP Server，所有支持 MCP 的 Agent 都能立刻使用，**无需为每个 Agent 单独适配**。

###  MCP 的核心：标准的 JSON-RPC 协议

```
{
  "jsonrpc": "2.0",      // 协议版本号
  "id": 1,               // 请求的唯一标识，用于匹配响应
  "method": "tools/call", // 要调用的方法名
  "params": {            // 方法所需的参数
    "name": "get_weather",
    "arguments": {
      "city": "北京"
    }
  }
}
```

MCP 通信主要围绕几个核心方法（`method` 字段）展开：

- `initialize`：客户端和服务端建立连接时的握手请求。
- `tools/list`：客户端向服务端请求所有可用工具的列表。
- `tools/call`：客户端请求执行一个具体的工具。

**MCP Server 返回给 Agent 的响应示例：**

json

```
{
  "jsonrpc": "2.0",
  "id": 1,               // 对应请求的 id
  "result": {            // 成功返回的结果
    "content": [
      {
        "type": "text",
        "text": "北京今天天气晴朗，温度 28°C。"
      }
    ]
  }
}
```
