前后端初步学习： 

核心原则与逻辑总结

- **关注点分离**：前端专注界面和交互，后端专注数据和业务。它们通过API解耦，可以独立开发、部署和扩展。
- **无状态通信**：HTTP协议是无状态的，每个请求都相互独立。这要求后端在设计时要保证每个请求都包含完整信息（如通过Token进行身份验证）。
- **数据格式标准化**：目前业界最通用的数据交换格式是 **JSON**。前端发送请求时把数据包装成JSON，后端解析JSON，处理完后也返回JSON。

### 一个核心比喻：点餐系统

理解前后端关系，最好的方式就是把它想象成**在餐厅点餐**：

- **前端（Frontend）**：你，顾客。负责“看菜单（界面）、点菜（操作）、等菜上桌（等待响应）”。
- **后端（Backend）**：厨房。负责“接收订单（处理请求）、炒菜（业务逻辑）、准备食材（操作数据库）”。
- **API（接口）**：服务员。是你和厨房沟通的桥梁，负责传递你的点单需求，再把做好的菜端给你。
- **协议（HTTP/HTTPS）**：你和服务员之间说的“普通话”，确保大家能听懂彼此。

总结起来就是：**前端负责界面交互和展示，后端负责业务逻辑和数据处理，API是连接它们的桥梁，HTTP是通信的“语言”**。

###  核心工作原理（一个请求的完整生命旅程）

当你在浏览器点击“登录”按钮时，背后发生了这些事：

1. **发起请求**：前端（浏览器）将一个包含用户名和密码的HTTP请求发送给后端的API接口（例如 `POST /api/login`）。
2. **路由分发**：后端的服务器（如Express, Spring Boot）接收到请求，根据 `/api/login` 这个路径，将其转发给专门处理登录逻辑的“控制器（Controller）”。
3. **业务处理**：控制器从请求中提取出用户名和密码，然后调用“服务层（Service）”进行校验。
4. **数据交互**：服务层去“数据访问层（DAO/Model）”查询数据库，看看是否存在这个用户，密码是否正确。
5. **返回响应**：后端将处理结果（成功/失败，用户信息等）包装成一个JSON对象，作为HTTP响应返回给前端。
6. **更新界面**：前端收到响应后，根据结果（成功则跳转到首页，失败则提示错误信息）更新用户界面（UI）。

“前端发请求 → 后端处理 → 返回数据”这个最小闭环

## 一、前后端交互的核心原理

### 1. 请求-响应模型

这是Web开发的基石。前端（浏览器/App）发起HTTP请求，后端（服务器）处理并返回HTTP响应。整个过程是**无状态**的，即每个请求都是独立的，服务器不会“记住”你之前的请求。

### 2. RESTful API设计

REST是目前最主流的API设计风格。它利用HTTP方法（动词）来操作资源（名词）：

- `GET /api/users`：获取用户列表
- `POST /api/users`：创建新用户
- `PUT /api/users/:id`：更新指定用户
- `DELETE /api/users/:id`：删除指定用户

### 3. 数据格式：JSON

JSON是前后端沟通的“通用语言”。前端发送JSON格式的请求体，后端处理后返回JSON格式的响应。它轻量、可读性强，是所有语言都支持的格式。

### 4. 三层架构（后端经典结构）

text

```
Controller（控制器层） → Service（业务逻辑层） → DAO/Model（数据访问层）
```



- **Controller**：接收请求、解析参数、返回响应。
- **Service**：编写核心业务逻辑（如计算、校验、调用外部API）。
- **DAO/Model**：与数据库交互（增删改查数据）。

这个分层能让代码清晰、可维护、易测试。
