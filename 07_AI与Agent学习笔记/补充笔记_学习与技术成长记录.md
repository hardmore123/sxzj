### 1. 具身智能.md
**位置**：`桌面\日志笔记记录\具身智能.md`
**内容**：探索具身智能领域的经验教训——用 codex 复现具身智能项目的反思。

**核心教训**（对今后用 AI 工具做开发极有价值）：
> 出了错就下意识地丢给 codex，而自己只知道运行出了 bug，却不知道具体在哪里出问题。带来的后果是：token 在哗哗地流，bug 却始终没有得到很好地解决。

**总结的 debug 工作流**：
```
遇到bug → 客观记录bug具体是什么 → 记录其在pipeline中的具体位置
→ 给出几种可能的原因及解决方案 → 让AI按几种不同方案尝试解决
→ 中间遇到其他bug按同样方式记录，直至有最终结果
```

**三条解决方案来源**：①花时间整理问题，问学长 ②让 GPT/codex 联网检索经验贴 ③自己对代码做静态分析（需先对 pipeline 有较高熟悉度）。

> **codex 对 sim 和 physic 的理解力很低，常常改来改去也抓不住重点，只会把解决不了的问题打个简化的补丁绕过去。**

### 2. 层数问题.md（146行）
**位置**：`桌面\日志笔记记录\层数问题.md`
**内容**：从底层数学理解神经网络"层数"概念——从传统ML到Transformer/LLM的演变。

**核心洞察**：
- 一层 = 线性变换（Wx+b）+ 非线性激活（σ）
- 增加一层 = 对信息空间进行一次"重塑和折叠"
- **层数就是信息进行"抽象和升维"的阶梯**：越浅看物理信号（像素/字词），越深看抽象逻辑/概念/规律
- 深度网络带来"指数级折叠"——用更少参数量换取更强大非线性表达能力

### 5. RAG相关.md（138行）
**位置**：`桌面\日志笔记记录\RAG相关.md`
**内容**：RAG 的本质、弊端与什么项目不该用 RAG。

**五类不该用 RAG 的场景**：
| 场景 | 为什么不用 | 替代方案 |
|---|---|---|
| 强结构化数据/精确统计（BI报表） | 向量库对 GROUP BY/SUM/JOIN 无能为力 | Text-to-SQL / Text-to-API |
| 全局宏观总结/跨文档洞察 | Top-K 召回永远是局部碎片 | Map-Reduce / GraphRAG |
| 全量静态且体积可控的知识库 | RAG 链路长、Chunking 切断语义 | 全量 Prompt 注入 + Context Caching |
| 强事实性零容错（医疗/金融/工业） | 大模型生成阶段仍有幻觉风险 | 规则引擎/专家系统兜底 |
| 超低延迟高吞吐 | RAG 是重型 I/O 组合拳，秒级延迟 | 知识蒸馏/微调/规则缓存 |

> **核心原则**：RAG 解决"信息检索与知识注入"问题。如果问题本质是**计算**、**全局洞察**或**严密逻辑推导**，RAG 往往是架构错配。

### 6. 提示词工程、.md
**位置**：`桌面\日志笔记记录\提示词工程、.md`
**内容**：许愿式编程 vs 命令式编程的对比。

> **许愿式**：主语开头（我想要、我需要、你应该…）—— 把问题分解甩给模型
> **命令式**：动词开头（读取、下载、写入、计算…）—— 人脑做问题分解和方案设计，让模型执行

> 命令式编程模式下，人脑承接问题分解和方案设计，把需求变成一条条可执行命令，甚至模块接口的命名都给它写好了。

### 7. 前后端初学.md（66行）
**位置**：`桌面\日志笔记记录\前后端初学.md`
**内容**：前后端交互核心原理——请求-响应模型、RESTful API、JSON、三层架构。

**核心比喻（点餐系统）**：
- 前端 = 顾客（看菜单、点菜、等菜）
- 后端 = 厨房（接订单、炒菜、备食材）
- API = 服务员（传递需求、端菜）
- HTTP = 普通话（确保听得懂）

**三层架构**：Controller（接收请求）→ Service（业务逻辑）→ DAO/Model（数据访问）
